The Harness Store desktop app, built with Electron + React + TypeScript ([ADR-0003](../../docs/adr/0003-typescript-electron-stack.md)).

- **Main process = the Runtime.** It installs **Harness Packages** (from the Store or a local folder), drives the **Declared Permission** consent step, launches and supervises each **Harness** as its own process and window according to its **UI Kind** (`web` or `terminal`), and hosts the **Model Gateway** from [`packages/gateway`](../../packages/gateway). It keeps installs, **Slot Bindings**, **Connections** and **Usage Records** in a local store. The Runtime contains no agent loop.
- **Renderer.** A sandboxed React UI (Library, Store, Models, Publish, Usage, Settings, first-run wizard) with `en` and `zh-CN` catalogs, talking to the Runtime only over typed IPC.
- It validates every **Manifest** with [`packages/manifest`](../../packages/manifest).

References: [`docs/tech/architecture.md`](../../docs/tech/architecture.md) §2 and §4. Specs: [`P0-03`](../../docs/delivery/specs/P0-03-connections-and-slot-bindings.md), [`P0-04`](../../docs/delivery/specs/P0-04-desktop-shell-i18n-first-run.md), [`P0-05`](../../docs/delivery/specs/P0-05-runtime-launch-and-supervise.md).

## Layout

| Path                             | What it holds                                                                                                                                                                                                    |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/main/index.ts`              | The Electron main process (the Runtime): app lifecycle, the main window, IPC registration. With `harness-windows.ts`, the only main code that imports Electron                                                   |
| `src/main/harness-windows.ts`    | The Harness windows (Electron `BrowserWindow`s), one per launch, driven by the Process Supervisor; tells main which launch a Harness window's call comes from                                                    |
| `src/main/runtime/`              | Startup and shutdown (`bootstrap.ts`), SQLite and its migrations, services, IPC handlers and the dispatcher, window state. Never imports Electron (an ESLint rule enforces it), so it is tested under plain Node |
| `src/preload/`                   | `index.ts` exposes `window.api`, built from the IPC method list, through the context bridge; `harness.ts` exposes a Harness window's `window.harness`. Each bundled as one CommonJS file for the sandbox         |

| `src/shared/harness-ipc.ts`      | The Harness window IPC contract: what a Harness window's own page may ask about its launch, and the events it gets                                                                                               |
| `src/shared/connection-input.ts` | The rules for what a User types into a Connection form (API key, base URL, custom endpoint name and id), used by the renderer for inline feedback and by the Runtime, which checks again                         |
| `src/shared/requirements.ts`     | `checkRequirements`: whether a model meets a Model Slot's Model Requirements, with what cannot be judged (a typed model, `json`) reported as unknown, never as failing                                           |
| `src/shared/permissions.ts`      | What Declared Permissions and launch facts mean in the User's words, on the low/medium/high scale: the consent dialog's lines, shared with the Store screens (P0-09, P0-10)                                      |
| `src/shared/i18n/`               | The `en.json` and `zh-CN.json` message catalogs (ICU), locale resolution, the translator with its fallbacks, and Intl formatting                                                                                 |
| `src/renderer/`                  | The React UI: hash routes, the shell (sidebar, page header), one module per screen, and `I18nProvider` with the `useI18n()` hook. `harness.html` is a Harness window's own page (top bar, xterm.js)              |

The renderer runs with `contextIsolation`, `sandbox` and no Node integration under a strict Content Security Policy (`src/renderer/index.html`). It sees only `window.api`: `await window.api.app.ping()` returns `{ ok: true, data: { version } }`. Set `HARNESS_STORE_USER_DATA_DIR` to run with a fresh profile.

## Runtime startup and data

On launch, before the window opens, the Runtime opens `harness-store.sqlite` in the userData folder (creating it and applying the migrations on first run), then starts the Model Gateway on `127.0.0.1` with a port the OS picks. If either step fails, the window shows a blocking error screen naming the step, with the details and Quit, instead of the app (`app.status`). Settings shows the app version, the Gateway's port and whether it answers now, the bundled Node's version, the data root and the database path (`diagnostics.get`). Quitting stops the Gateway, which writes its last Usage Records, then closes the database.

SQLite is Node's built-in `node:sqlite`, so there is no native module to rebuild. Migrations are plain SQL files in `src/main/runtime/migrations/` (`0001_…sql`, never edited once released), bundled into the main process and tracked with `PRAGMA user_version`; each runs in its own transaction. The first creates `settings` (key/value, JSON values: the language override, whether the first-run wizard has run, and the main window's size and position) and `usage_records` (one row per Usage Record from the Gateway). The second creates `connections`, `secrets` and `slot_bindings` ([data-model.md](../../docs/tech/data-model.md) §2); the fifth `installs` and `launches`.

## Installing from a folder

"Install this folder locally" sits on the Publish screen (docs/ux/flows.md F5), signed in or not and offline too: a Publisher runs their own Harness exactly as Users will, without uploading it. The order is validate, consent, install, so nothing touches the disk before the User consented. `installs.chooseFolder` opens the native folder picker in main; `installs.inspectFolder(path)` runs `validatePackage` over a `DirectorySource` (no publisher or published-version check) and answers `{ valid, manifestSummary, problems, warnings }`. An invalid folder shows every problem (path, then the `manifest.<messageKey>` text) with Re-check; a valid one opens the consent dialog (`src/renderer/src/install/ConsentDialog.tsx`, shared with P0-10): title "Install {name} {version}?", the Declared Permissions on the low/medium/high scale with an icon, a label and a sentence each, the facts (runtime kind, UI Kind, Workspace, platforms), the Harness ID, version and Entry, the no-sandbox sentence and the folder's warnings; Install is enabled after one second.

Install calls `installs.installFromFolder(path)` (`installer.ts`), which validates again: a folder that no longer validates, cannot be read, or whose Manifest is not the one last inspected answers `package_invalid`, and the screen inspects it again (a fresh dialog then says why it is back). A listed file the User's account cannot open while copying answers `file_unreadable` with its path, shown in the dialog. It refuses with `harness_running` while that Harness runs, and from that check until the install is done `launch.start` refuses that Harness with `harness_installing`, so no launch runs from a folder about to be replaced. It copies exactly the files of the validated listing (each opened without following a link) into `downloads/install-<uuid>/`, sets 0755 on every declared platform's binary Entry (macOS, Linux), then renames the folder to `harnesses/<publisher>/<slug>/<version>/`: the same version is replaced, and another version, higher or lower, replaces the installed one, whose folder is deleted once the `installs` row names the new one. The Data Directory `data/<publisher>/<slug>/` is created when missing and never touched by a reinstall. The row gets `source = 'local'` (also over a Store install), the Manifest, and its permissions as `consented_permissions`; a reinstall keeps `last_launched_at` and `last_workspace`. Installs run one at a time, and `installs.changed` tells the windows. An install the app quit or crashed in leaves its folders in `downloads/`: before the installer's first install or listing, a `replaced-*` folder whose row's install folder is missing is moved back, and every other `install-*` and `replaced-*` folder is deleted.

The Library lists `installs.list`: the most recently launched first, then by name. Each card has the icon (a `data:` URL read in main, as the CSP allows no file), name, Publisher (a link to their Store page) and version, the Local badge, when it was last launched (nothing when never), and its primary button (see Launching a Harness), or "Not available for your platform" when the Manifest does not declare this platform (`<process.platform>-<process.arch>`). Empty, it says "Nothing installed yet" with Browse the Store. The Model Gateway's `getManifest` reads `installs.manifest` on every request, so an installed Harness's Slots are declared.

## Installing from the Store

Install on a Store detail page (docs/ux/flows.md F2) runs the same install path as a folder: only where the files come from differs. It has two IPC phases, so nothing is unpacked before the User consented:

1. `installs.install({ harnessId, jobId })` (the renderer picks the job ID, a UUID) calls the Store's `download` function (`src/main/runtime/store-download.ts`) for the latest version on this platform with the anon key, which counts the download; the app counts nothing itself. The answer must be a ticket whose Manifest is valid (`store_error`) and names the requested Harness (`integrity_error`). The Harness's `installs` row is then written in a transient `state` (migration 0006: `downloading`, `verifying`, `awaiting_consent`, `unpacking`, then `installed`), and the package streams from the signed URL, with no header of its own, into `downloads/download-<jobId>.zip`, reporting `{ received, total }` on `progress:<jobId>`. More bytes than the Store's `size` stop the transfer; 120 s without a byte is `store_unreachable`; a transfer left early (too large, a file that cannot be written) is cancelled so its connection is not held. The checks then run in order: the size, the SHA-256 (`checksum_mismatch`), `validatePackage` on the zip through `ArchiveSource` (links, special files, `..` and absolute names refused as on publish), and the zip's Manifest deep-equal, as JSON values, to the Store's (`integrity_error`). It answers the consent dialog's facts once the row is `awaiting_consent`.
2. `installs.confirm(jobId)` unpacks the files of the validated listing into `downloads/install-<uuid>/`, each read whole so its CRC-32 is checked, then makes the Entries executable, puts the folder in place and writes the row `installed` with `source = 'store'`, exactly as a folder install does after its copy.

`installs.cancel(jobId)` aborts the download (`installs.install` answers `download_cancelled`) or discards one waiting for consent. A failed or cancelled install deletes its row and its download at once; `failed` and `cancelled` are never stored. `InstallStore.all()` and `get()` see `installed` rows only, so the Library, the Supervisor and the Models page never see a half-installed Harness. Only the main window's page knows its job IDs, so main cancels every job when that page closes, crashes or loads again (the installer's `cancelAll`, from `src/main/index.ts`), and at startup the installer deletes every transient row and `download-*` file before its first install or listing. A Harness with a Store install under way refuses another (`harness_installing`), and so does "Install this folder locally"; an installed Harness, local included, refuses a Store install (`invalid_input`). Downloads of different Harnesses run side by side.

In the renderer, `src/renderer/src/install/InstallJobsProvider.tsx`, mounted in the Shell, holds the jobs by Harness ID, so a download goes on and shows its progress again after the User leaves the detail page. Once the package is verified it opens the shared consent dialog over whatever screen is shown; while another dialog is open, the detail page offers "Review and install". A Cancel that crosses a download finishing in main still ends as cancelled, never as a consent dialog; the jobs still open when the provider unmounts are cancelled. A failure shows under the detail page's button, and Install downloads again. A minimal toast area (`components/Toasts.tsx`, an `aria-live="polite"` region that dismisses itself) says "Installed {name}" and "Download cancelled".

## Updates

The update check (`src/main/runtime/update-check.ts`, P0-10.2) runs 10 seconds after start and then every `update_check_interval` (Settings, P0-11.2: 1 hour, 6 hours by default, 24 hours, or Never, which skips the check 10 seconds after start too): it asks the Store's `latest_versions` (api.md) about every installed Store Harness, never a local install, in calls of at most 1000 IDs with the anon key, and is skipped while the Store is known to be offline; a call without an answer has connectivity checked again and is dropped silently. Per install it stores (migration 0007) `store_status` (`available`, `unpublished` or `taken_down`; `not_found` is kept as `unpublished`) and, only when the latest version is greater (semver) than the installed one and declares this platform, `available_version` and its full Manifest, `available_manifest`; otherwise both are cleared. An install of the Harness clears them too. Each row it changed is reported with `installs.changed`. `Runtime.updates.check()` runs one at once, and so does Settings' Check now (`installs.checkUpdates`), whatever the interval.

`installs.update({ harnessId, version, jobId, reconsented })` updates a Store install to the version the button offered (pinned, so the Manifest the prompt showed is the one installed): the same `download` call, transfer and checks as an install, then `diffForReconsent(installed, downloaded)` from `@harness-store/manifest`, the one definition of "widened": when it is `required` and `reconsented` is false the update is refused with `reconsent_required` before anything is unpacked. Then it unpacks into staging, puts the new version folder in place, switches the row and deletes the old folder, as an install does; the Data Directory is never touched. The row stays `installed` throughout, so whatever fails (checksum, integrity, Cancel, a crash) the old version stays installed and launchable. A running Harness is refused (`harness_running`) when Update is clicked and again just before the swap; launches may start meanwhile. `installs.cancel` cancels its download.

In the renderer the Library nav item shows how many installs have an update. A card (and a detail page) offers Update, or "Review update" when the update needs the User's consent again, with Launch as the secondary link. A simple update downloads at once, with its progress and Cancel on the button and the toast "Updated {name} to {version}. See the changelog in Version history."; "Review update" first opens the update prompt (`install/UpdatePrompt.tsx`): from → to, "What changed" (one "New:" line per item the diff adds, in the permission list's words, except a narrowed filesystem scope, which is not new access; when the Entry only lost a platform's path, a "No longer starts on {platform}" line instead, so the list is never empty), the changelog, the new version's trust block, and Not now / Update (enabled after one second). An update refused because the Harness runs says "Close the Harness to update", as does a card whose Harness runs while an update waits. A Harness the Store no longer offers has no Update: an Unpublished one has the note "No longer available in the Store", a taken-down one the red warning below.

A Store install the update check found `taken_down` (P0-12.2, `library/Takedown.tsx`) shows the red warning "A Store administrator took this Harness down. It may be harmful: launch it only if you trust it." on its Library card and its detail page, in place of that note; both read the install's `storeStatus`, not the detail page's own Store read. It stays launchable: Launch, in the shared `useLaunch`, first asks "This Harness was removed from the Store. Launch anyway?", and only "Launch anyway" goes on, recording it with `installs.acknowledgeTakedown` in the row's `takedown_acknowledged` (migration 0009), so the question comes once per Takedown, across restarts. An update check that changes `store_status` sets it back to 0, so a Harness reinstated and taken down again asks again. Bringing a running Harness's window to the front and a Harness window's Relaunch ask nothing, and main's `launch.start` does not enforce it. Only a whole-Harness Takedown shows: `latest_versions` reports the Harness's status alone, so a Takedown of the installed version only is not seen in P0.

## Uninstalling and the Library's controls

`installs.uninstall(harnessId)` (P0-10.3, docs/ux/flows.md F9) is refused while the Harness runs (`harness_running`) or while an install or update of it is under way (`harness_installing`), deleting nothing. From that check until it is done the Harness counts as installing, so `launch.start` refuses it. It deletes the install folder `harnesses/<publisher>/<slug>/<version>/`, then the Data Directory (`rm` never follows a link, so a link inside it to the User's own files deletes only the link), then, in one transaction, the `installs` row and the Harness's Model Overrides (`slot_bindings` of scope `harness:<id>`); the folders of the layout it leaves empty go too. A failure partway leaves the row, and uninstalling again finishes the job, as a folder already gone counts as deleted. Its launch logs, `launches` rows and Usage Records are kept: at each start, before the installer's first install or listing, the `*.log` files of a Harness no longer installed are deleted once 30 days old (by modification time), then its logs folder when empty; an installed Harness's logs are never touched. `installs.dataSize(harnessId)` answers the bytes of the regular files in the Data Directory, walked without following links (0 when it is missing).

In the renderer (`library/UninstallDialog.tsx`), Uninstall is the last item of a Library card's menu and the secondary action beside Launch on the detail page. The confirmation reads "Uninstall {name}?" and "This deletes its data directory ({size}). Files in your own folders are not touched.", the size read with `installs.dataSize` only when it opens, with Cancel and Uninstall; done, it shows the toast "Uninstalled {name}" (no Undo) and the card leaves the Library. While the Harness runs, or when main refused because it started meanwhile, the dialog says "Close the Harness first" with only Close.

Above the cards, a name filter (narrowing as the User types, case-insensitive), the views All, Updates available, Running and Local installs, and the sort Recently used (last launched first, then by name) or Name work on the list already loaded, with no call to main: a card left out is hidden, not unmounted, so showing it again calls nothing either. A view with no card says "No Harnesses in this view" with Clear filters.

## Launching a Harness

The Process Supervisor (`src/main/runtime/supervisor.ts`, Electron-free) launches installed Harnesses following the launch contract of [architecture.md](../../docs/tech/architecture.md) §4, one instance per Harness. It launches Harnesses of both UI Kinds with either runtime kind: a Node Harness's Entry runs on the Runtime's Node (below), a binary Harness's Entry for this platform (`entry[<platform>]`, the platform also listed in `platforms`) is run directly, with no Node wrapper and no `ELECTRON_RUN_AS_NODE`, and otherwise the same environment, working directory, windows, readiness, logs and shutdown. A binary Entry gets 0755 at install (macOS, Linux), so a Harness Package zipped on Windows still runs; Windows runs it as it is (a `.cmd` or `.bat` Entry gets no special handling).

`launch.start({ harnessId, workspace? })` answers at once with `{ outcome, launchId }`, and the launch reports each state as a `launch.state` event (`launch.status` lists the latest launch of each Harness): `preparing` → `spawning` → (`waiting-ready`, web) → `ready` → `stopping` → `stopped`, or `failed` with a reason (`spawn_error`, `ready_timeout`, `exit_nonzero`, `platform_unsupported`, `workspace_cancelled`). While a Harness's launch has not ended, `launch.start` answers `focused` and brings its window to the front. Before anything starts it refuses `not_installed`, and `slot_unbound` when no model can fill the Harness's `default` Model Slot (docs/ux/flows.md F3): the card then reads "Set up a model first" and opens Models. Preparing runs the contract's steps in order: the Entry for this platform (`platform_unsupported`, no token, no row), the Entry file (`spawn_error`), the Data Directory (created when missing), the Workspace (see below), then a Gateway Token from the Model Gateway (Harness ID, version, launch id, the app's locale, the Workspace when there is one) and a `launches` row, then the log file, then, for a web UI Kind, a free port. A launch of a Harness the platform does not run, whose model check refuses it or whose required Workspace was not chosen, leaves no `launches` row.

The Workspace (docs/ux/flows.md F3, step 3): Launch on the card of a Harness whose Manifest's `workspace` is `required` or `optional` first opens the Workspace sheet in the main window (`src/renderer/src/library/WorkspaceSheet.tsx`), "Choose a folder for {name}": the Harness's last Workspace preselected (`launch.lastWorkspace`, from `installs.last_workspace`), or "The last folder no longer exists"; Choose folder opens the native folder dialog in main (`launch.chooseWorkspace`), at the last Workspace while it exists; "The Harness can read and write files in this folder."; Cancel, which launches nothing, "Continue without a folder" for `optional`, and Continue, which sends the folder as `launch.start`'s `workspace`. Main checks the folder again (`invalid_input` when it is not an existing absolute folder). A `required` Harness launched without one ends `failed(workspace_cancelled)` before any token, window or process, and the card shows no error for it; a Harness whose `workspace` is `none` (or absent) never gets the sheet and ignores a `workspace` sent along. A launch with a Workspace runs with it as its working directory and `HARNESS_WORKSPACE` set to its absolute path, and saves it as `last_workspace` (launching without one keeps the last); without one the working directory is the Data Directory and `HARNESS_WORKSPACE` is absent, never empty, whatever the parent's environment held. Relaunch from a Harness window reuses its launch's Workspace without asking.

The terminal window (`harness.html` with xterm.js, 960×640, titled "{name} — Harness Store") opens next; once its terminal is on screen it reports its size, and the Harness starts in a pty of that size (node-pty, `TERM=xterm-256color`), with its Data Directory as its working directory. Its environment is the inherited one without `OPENAI_*`, `ANTHROPIC_*`, `GOOGLE_API_*`, `GEMINI_*`, `OPENROUTER_*` and `HARNESS_*` (case-insensitive), plus the contract's `HARNESS_GATEWAY_URL`, `HARNESS_GATEWAY_TOKEN`, `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `HARNESS_ID`, `HARNESS_VERSION`, `HARNESS_DATA_DIR`, `HARNESS_LOCALE` and `HARNESS_PLATFORM`. A Node Harness runs on the Runtime's own Node: Electron's executable with `ELECTRON_RUN_AS_NODE=1` (Electron 45 ships Node 24; the Manifest's `runtime.node` is `22`, and a separately bundled Node LTS is deferred). The pty's output streams to the window over the Harness window channel, keystrokes and resizes go back; on Windows and Linux, Ctrl+Shift+C and Ctrl+Shift+V copy and paste through main's clipboard, and the window has no menu bar so Ctrl+C reaches the Harness.

Closing the window stops the Harness: SIGTERM to its process group (`taskkill /T` on Windows), SIGKILL (`taskkill /T /F`) after 5 seconds when the Harness, or a process of its group (one it started that ignores SIGTERM), is still there, the launch recorded as ended at most 2 seconds later, and it ends `stopped`. A Harness that exits on its own ends `stopped` (code 0) or `failed(exit_nonzero)`; its window stays open and readable, the top bar shows "Exited with code N" with Relaunch and Close, and the title adds the code. A process a signal ended reports 128 + the signal number. Either way the Gateway Token is revoked (the Gateway answers 401 `invalid_token`) and the row gets `ended_at`, `exit_code` and `token_revoked_at`; rows a crash of the app left open are closed at the next start. Quitting stops every running Harness the same way, at most 10 seconds in all, before the Gateway and the database close. Installing over a running Harness answers `harness_running`.

A web window (`harness.html` too, titled "{name} — Harness Store", sized to the Manifest's `ui.window` hints, default 1100×760, plus the top bar) opens at once on its Starting state: "Starting {name}…" with the seconds since the launch began and Cancel, which closes the window and so stops the Harness (it ends `stopped`). The port comes from binding port 0 on `127.0.0.1` and releasing it at once; a port another running Harness has is never handed out again. The process starts with `child_process.spawn` (stdin ignored, stdout and stderr piped to the log; detached on macOS and Linux so it leads its own process group) with `HARNESS_PORT` added to the environment, and the launch is `waiting-ready` while the Runtime tries a TCP connection to `127.0.0.1:<port>` every 250 ms (127.0.0.1 only: a Harness listening on `localhost` that resolves to `::1` times out). Once one is accepted, the Harness's page `http://127.0.0.1:<port><ui.path ?? "/">` loads in a WebContentsView laid over the room under the top bar (the window's page reports where that room is), and the launch is `ready`; so the User never sees a refused connection. That view has no preload (page script reaches neither Node nor Electron IPC; checked by hand in Electron: `require`, `process`, `window.api` and `window.harness` are all undefined there), is sandboxed with context isolation, and has a session of its own per Harness, `persist:harness:<publisher>/<slug>`, which denies every permission request; its origin still changes with each launch's port, so storage the page keeps by origin does not carry over between launches (a known limitation). Only that exact origin stays in the view, for navigation, redirects and `window.open` (which replaces the page); any other http(s) URL, `localhost:<port>` included, opens in the User's browser with `shell.openExternal`, and every other scheme is blocked. The top bar adds Reload, which reloads the page in place while the process keeps running. A Harness that does not accept a connection within `ui.readyTimeoutSeconds` (5–120, default 30, counted from the spawn) is stopped with the shutdown sequence and ends `failed(ready_timeout)`; its `launch.state` carries `logTail`, the last 50 lines of its log kept in memory, and the window shows "{name} did not start in time" with them, Show logs, Relaunch and Close (no separate dialog). A web Harness that exits on its own, before or after it was ready, has its page taken away and the window shows "{name} stopped unexpectedly" with the exit code ("{name} could not start" when it never started), Show logs, Relaunch and Close. A web window learns that it gained focus from main (`window.focus`), since its page and not the top bar holds the focus, and reads its model chips again then.

Each launch logs to `logs/<publisher>/<slug>/<launchId>.log` in the app data root (outside the Data Directory): one line per output line, `<ISO-8601> [out|err|pty|runtime] <text>` (stdout and stderr for a web Harness, the pty for a terminal one), pty output raw, the Runtime's own lines for the spawn, signals and exit; never the environment or the token. A log stops at 10 MB with one line saying so, and each launch keeps the Harness's 20 newest logs. The window's top bar has the Harness's icon and name, one chip per Model Slot ("Model · default: qwen3:8b", read again when the window gains focus; a click opens `#/models?harness=<id>` in the main window, which opens again if it was closed; so does starting the app again, or the Dock icon on macOS), and Open logs (`shell.openPath` on this launch's log).

The Library card follows its Harness live from the `launch.state` events (no polling): Launch; "Starting…" (disabled) while it prepares, spawns and waits to be ready; "Running…" with "Show window", which both call `launch.start` and so only bring its window to the front (no second process); "Stopping…" (disabled) once its window closed. The card has no Stop, as docs/ux shows none: closing the Harness's window is how it stops, with the shutdown sequence above. A launch that failed `exit_nonzero`, `ready_timeout` or `spawn_error` shows an error line, "Exited with an error", "Did not start in time" or "Could not start", with Show logs and Dismiss (dismissed lines stay hidden while the app runs; renderer state only), and the button stays Launch, which retries; `workspace_cancelled` and `platform_unsupported` show nothing. The card's menu (⋯) has View in Store, Model Overrides (`#/models?harness=<id>`), Show logs, Open data folder and Uninstall. `launch.openLogs(harnessId)` opens, with `shell.openPath`, the Harness's latest launch's log, else the most recently written log of its logs folder (one from an earlier run of the app), else that folder, created; `launch.openDataFolder(harnessId)` opens its Data Directory in the OS file browser, created when missing. Main computes both paths from the Harness ID (`not_installed` for a Harness that is not), never from a path the renderer sends. When the OS cannot open the path (`shell.openPath` fails, say on Linux with no app set up for it), both answer `open_failed` with the path, shown on the card; so does Open logs in a Harness window, shown under its top bar (or in the overlay once a web Harness has ended).

The Harness window's page sees only `window.harness` (`src/preload/harness.ts`): calls about its own launch on their own channels (`src/shared/harness-ipc.ts`), which main routes to the launch whose window sent them; it never gets `window.api`. Events follow the same split: `launch.state` and `installs.changed` go to the main window only, and a Harness window gets its own launch's state as `window.state`, never another launch's. node-pty is the one native module: it ships N-API prebuilds that Node and Electron both load, stays outside the main bundle and, when packaged, outside the asar archive. Signals and the shutdown sequence are tested on macOS and Linux; the Windows paths (taskkill, ConPTY) are not tested yet.

## Connections

The Models page lists the User's Connections, one per Provider, plus any number of named custom OpenAI-compatible endpoints (`openai-compatible:<slug>`, the slug taken from the name when it is added and never changed). Add Connection opens a modal with every Provider of the Gateway's table (`providers.list`, letter monograms, no logos); picking a Provider that already has its one Connection opens that Connection to edit. Each row shows a status (Disabled, Connection failed with the Provider's text, Local, Connected, Not tested), Edit, Enable or Disable, and Remove, which names the Slot Bindings that use the Connection and deletes them with it.

Keys are encrypted with Electron's `safeStorage` (async API) behind the Electron-free `SecretCipher`, and stored in `secrets`; the renderer only ever sees `keyHint`, the last 4 characters (none for a key under 12 characters). When the OS offers no encryption (on Linux: no keyring, or the `basic_text` backend), a key is refused with `encryption_unavailable` and an explanation; it is never stored in plaintext, and keyless Connections still work.

Testing uses `testConnection` and `listModels` of `@harness-store/gateway` over Node's `fetch` (`RuntimeOptions.providerFetch`), the one the Gateway's upstream calls use, not Electron's `net.fetch`. `connections.add` and a new key or base URL in `connections.update` test first and save only a passing Connection, with that test recorded (`last_tested_at`, `last_test_ok`); `connections.test` re-tests a saved one and records the result either way, a failure with the Provider's text in `last_test_error`, shown verbatim on the row, or, for a timeout or an answer that is not the Provider's API (a wrong base URL), the IPC code in `last_test_failure`, shown in the catalogs' words (`provider_timeout`, `unexpected_response`, also what a failed `add`, `update`, `testDraft` or `connections.models` answers). `connections.testDraft` tests what the Add/Edit dialog holds without saving: Save is enabled once it passed (a rename or Enable/Disable needs no test). Zhipu, MiniMax and Doubao list no models and are not in the catalogue, so their test needs a "Model to test with" (`needsTestModel` on the preset; `testModel` in the draft). Anthropic and Google test with their catalogue's smallest model (the preset's `testModel`, the field's placeholder), and the Add/Edit dialog and the wizard let the User name another, so a key that cannot use it, or an aged catalogue, does not block adding the Connection. A passed test keeps the model it was named in `test_model` (`ConnectionSummary.testModel`), and every later test that names none (a row's Test, a new key) uses it again. A disabled Connection's row offers no Test, and a row's Edit, Enable/Disable and Remove wait while its own test runs.

`connections.models` lists a Connection's models: the app's catalogue for Anthropic and Google (`{ id, contextWindow, tools, vision }`), a live `GET /models` for the Providers that list them, kept in memory for 10 minutes per Connection (`model-cache.ts`; a passed test fills it, a failed listing is not kept, a new key or base URL or removing the Connection empties it), else nothing. The model picker (`src/renderer/src/models/ModelPicker.tsx`) groups the enabled Connections' models, annotates catalogue entries with their context window, tool calling and vision, and always offers "Type a model name" (`provider/model`, split at the first `/`). A typed or live-listed model has unknown capabilities: `checkRequirements` (`src/shared/requirements.ts`) answers `{ ok, unknown, failures }` and counts what it cannot judge as `unknown`, never as a failure.

`connections.detectLocal` looks for Ollama and LM Studio (`local-detection.ts`): `GET {baseUrl}/models` on each preset's default base URL (`http://127.0.0.1:11434/v1`, `http://127.0.0.1:1234/v1`), both at once over the same Node `fetch`, each bounded to 1.5 s, so it answers within about 1.5 s. A Provider counts as running only on HTTP 200 with a JSON `data` array, or `data: null`, which is how Ollama answers while no model is pulled yet (the Connection test accepts it the same way); it comes back with its models and `added`, whether it already has its Connection. Detection runs when the wizard's Local Providers step or the Models page opens and on "Detect again", never in the background, and never adds a Connection: the Models page's Local Providers panel offers Add per Provider (Added for one that has its Connection, so a custom base URL is never replaced), and the wizard adds the checked ones on Continue. Adding is an ordinary `connections.add` with the fixed id `ollama` or `lmstudio`, no key, and the default base URL stored as NULL. Tests point the probes elsewhere with `RuntimeOptions.localProbeTargets` (fake Providers on ports the OS picks, and port 2 for a target that must refuse), so no test depends on the machine's ports 11434 and 1234.

The Model Gateway reads Connections from SQLite on every request (`getConnection`, in `gateway-host.ts`), decrypting the key just for that call, so adding, disabling or removing a Connection applies to the next request without a restart; a disabled Connection answers 403 `provider_not_connected`.

## Default Models

The Default Models are the global Slot Bindings (`slot_bindings` rows with scope `global`, `provider_id` holding the Connection id). The Models page has a row for `default`, always, then one per other Slot name that has a Default Model or that an installed Harness declares (docs/ux F6), by name; each row's model picker offers the enabled Connections' models grouped by Connection, "Not set" and "Type a model name", and saves a choice at once with `bindings.setGlobal({ slot, target })` (`target: null` clears it; `bindings.ts`). It refuses a Connection that does not exist or is disabled (`provider_not_connected`) and a Slot or model name the Gateway would not accept (`invalid_input`); a model the Provider does not list is fine. A Default Model on a disabled Connection is kept and marked "Connection disabled", since resolution skips it. A Default Model is checked against the Model Requirements of the same-name Slot of every installed Harness: a known failure shows a yellow warning ("This model may not meet the requirements of Code Reviewer's `default` Slot (tool calling)."), a model whose capabilities are unknown a muted note; neither blocks anything. The wizard's Default model step saves the picked model as the `default` Slot Binding on Continue; Skip sets nothing.

The Gateway's `resolveBinding` (in `gateway-host.ts`), `bindings.resolveAll` and `bindings.resolveManifest` all call `resolveHarnessSlot` (`bindings.ts`), which reads the Harness's Model Overrides, its installed Manifest's Recommended Models (for `bindings.resolveManifest`, those of the Store Manifest it is given, so a Store detail page can say what each Slot of a Harness that is not installed would use), the global Slot Bindings and the enabled Connections on every request and asks the pure `resolveSlotBinding` (`slot-resolver.ts`) for the normative order of gateway-protocol §4: Model Override, then the first Recommended Model with an enabled Connection, then the Default Model of the same Slot name (source `default_same_name`; `default` for the `default` Slot), then the Default Model of `default`, else 409 `slot_unbound`. A binding whose Connection is disabled or removed counts as absent. A Recommended Model id is split at its first `/` and the part before it must be a Connection id (`recommendedTargets`): an unknown Provider id, or `openai-compatible/…` (custom endpoints are `openai-compatible:<name>`), is skipped. `getManifest` reads the installed Manifest (see Installing from a folder); for a Harness that is not installed a Slot name answers 404 `unknown_slot`. Explicit `provider/model` ids work regardless.

Model Overrides are `slot_bindings` rows with scope `harness:<id>`. Below the Default Models, Per-Harness Overrides has one expandable card per installed Harness, with a row per Model Slot of its Manifest: the Publisher's description, the Model Requirements ("Needs: tool calling and context window ≥ 100,000"), the Recommended Models, the model it resolves to now with a badge ("Uses: Override", "Uses: Recommended", "Uses: Default" for both `default_same_name` and `default`, "Unbound"), a picker with "No override" and "Type a model name", "Clear override" while one is set, and the same requirement warning. `bindings.setOverride({ harnessId, slot, target })` checks what `setGlobal` checks, plus that the Harness is installed (`not_installed`) and declares the Slot (`invalid_input`); it never checks the requirements, which only warn. `bindings.clearOverride({ harnessId, slot })` removes one, `bindings.getForHarness(id)` lists the rows (a row for a Slot a newer version no longer declares is kept, and ignored), `bindings.resolveAll(id)` answers `{ slot, binding }` for every declared Slot, `default` first. Removing a Connection names the Default Models and Model Overrides that use it. The deep link `#/models?harness=<encodeURIComponent(id)>` opens that Harness's card and scrolls to it.

## Offline

The Runtime checks whether the Store answers with `HEAD <Store base URL>` through Electron's `net.fetch` (so system proxies apply): any status below 500 is online; a network error, no answer within 5 s, or a 5xx is offline. The Store being down counts as offline, since the User meets the same problem. It checks at startup, when the User presses Retry, and, while offline, again after 15 s, 30 s, 60 s, then every 5 minutes (at most 4 checks a minute); while online it does not poll. Overlapping checks share one request. Each change is pushed to the window as the `connectivity.changed` event (`connectivity.get` and `connectivity.check` over IPC).

While offline, every main screen shows a banner ("You're offline. Library and Models still work."), and only the Store routes (`/store`, `/store/h/…`, `/store/p/…`) swap their content for an offline panel with Retry. Library, Models, Publish, Usage and Settings keep working. When Retry finds the Store again, the Store screen mounts afresh and loads its data.

The Store base URL is the `store_base_url` setting (Settings → Advanced → Store URL), else `http://127.0.0.1:54321`, the Supabase local stack. It is read at every check. To try it by hand, start the app without the local stack running (offline panel on Store), then serve anything on that port, for example `python3 -m http.server 54321`, and press Retry.

## Store sign-in

Only Publishers sign in, with GitHub, through the Store's Supabase Auth (P0-07.2; HTTP calls in [api.md](../../docs/tech/api.md), Publisher sign-in). `src/main/runtime/store-auth.ts` (Electron-free) runs the OAuth PKCE flow: `auth.signIn` opens the User's default browser with `shell.openExternal` (never a window of the app, so no GitHub password is typed into it) and waits up to 5 minutes for `harnessstore://auth-callback?code=…`. The app registers that scheme (`app.setAsDefaultProtocolClient`; `protocols` in electron-builder.yml for packaged builds; a bare Linux AppImage does not install its `.desktop` file, so it never receives the callback, a known limitation in the P0-07 spec) and passes the URL on from `open-url` (macOS) or the `second-instance` arguments (Windows, Linux), then brings its window to the front. The code is exchanged with the in-memory verifier, the profile (`github_login`, `display_name`, `avatar_url`) is read through PostgREST, and the session is stored encrypted with the `SecretCipher` (`safeStorage`) in the `secrets` row `store:session`; without OS encryption, sign-in is refused with `encryption_unavailable` before the browser opens. It survives a restart; a session the OS cannot decrypt right now (a locked keychain) counts as signed out but is kept for the next launch. The access token is refreshed when it expires within 60 s; a refused refresh, a 401 from a Store call (`sessionRejected(accessToken)`, which only acts while that token is still the stored one) or a profile that is gone deletes the session and emits `auth.changed` with `reason: session_expired`. `auth.signOut` deletes it and revokes it at the Store (best effort), refreshing an expired access token first since Auth's logout needs a valid one. `auth.whoami` reads the profile on each call and answers with the stored copy while the Store does not answer.

The Store's anon key is `LOCAL_STORE_ANON_KEY` (the local stack's, public by design) unless the build sets `HARNESS_STORE_ANON_KEY`; the base URL is the `store_base_url` setting. To try it by hand: start the local stack (`pnpm --filter @harness-store/store db:start`) with a real GitHub OAuth app in `apps/store/supabase/.env` (see `.env.example` there), then Publish → Sign in with GitHub. In development, `pnpm dev` registers the scheme for its own Electron and this app's entry script; the OS hands the callback to the running app through the single-instance lock.

## Publishing

The Publish screen (docs/ux/flows.md F5) shows a GitHub sign-in card signed out (with Cancel while the browser has not come back, disabled offline, and "Sign in again" after an expired session) and, signed in, the Publisher's avatar, login and Harness ID prefix with Sign out, then the tabs "New version" (P0-08.1) and "My Harnesses" (P0-08.3). Its state lives in `src/renderer/src/publish/PublishProvider.tsx`, above the screens, so leaving Publish keeps the tab, the folder, its validation and the review; a sign-out keeps the folder, and every sign-in validates it again.

A folder is chosen with `installs.chooseFolder` or dropped on the section (the preload's `window.api.pathForFile`, Electron's `webUtils.getPathForFile`; a dropped file answers `invalid_input` and the screen says "Drop a folder"). `publish.validateFolder(path)` (`src/main/runtime/publish.ts`) builds the Harness Package the upload will send, then validates that zip: `buildPackage` (`package-archive.ts`) walks the folder without entering excluded folders and writes a deterministic zip (files only, sorted by path, every timestamp 1980-01-01, each file's Unix mode, Deflate level 6, 64 KiB at a time with a yield to the event loop in between); links and special files go in as empty entries with their mode, so `validatePackage` reports them at their path. The exclusion rules live in `package-exclusions.ts`: `.git` and `node_modules/.cache/` at any depth, `.DS_Store`, `Thumbs.db`, `*.swp`, plus a root `.harnessignore` (gitignore syntax via the `ignore` package; it cannot bring back a fixed exclusion and is left out itself); `examples/*/scripts/excluded.mjs` keep a copy that a test compares. The CLI and "Install this folder locally" apply none of them. The zip is opened with `ArchiveSource` and checked by `validatePackage` with `publisher` (the signed-in login, `auth.login()`, read from the stored session) and, when the Harness ID's publisher segment is that login, `publishedVersions`: every row of the "Own versions" read for that ID (api.md), any status. A read that fails leaves them out and the screen says the Store checks on upload; a 401 ends the session. The answer carries the problems ordered by path, the warnings, the Manifest, the icon as a `data:` URL, the README, the exclusion list, the zip's size, and "New Harness" or the last version. Only the newest run counts, and main keeps only its zip. Main also watches the folder (`fs.watch`, recursive) and emits `publish.folderChanged` 500 ms after the last change outside the excluded paths; the screen then validates again, as Re-check does.

Problems show their path, the `manifest.<messageKey>` text and the code; warnings are listed apart and never block. Continue is enabled exactly when there is no problem and opens the review: the Manifest's facts (read-only), the changelog, what was left out, the size (a warning above 100 MiB), then the listing preview built from the shared listing components in `src/renderer/src/listing/` (`HarnessCard`, `ListingDetail` and `TrustBlock`, which the consent dialog and the Store detail page use too), with the README and changelog rendered as sanitised Markdown (see Store browsing); the preview's README images are dropped, as they are not in the Store yet. The CSP allows `https://avatars.githubusercontent.com` images for the avatar.

Publish, at the end of the review (P0-08.2), calls `publish.publish({ archiveId, jobId })`: the renderer names the job (a UUID) and subscribes to `progress:<jobId>` first. Main sends the zip the validation built, unchanged, to `<store_base_url>/functions/v1/publish` (`package-upload.ts`): a Node `http`/`https` request rather than `net.fetch`, which reports no upload progress, so the OS proxy settings do not apply to it. The body is multipart with the one part `package` (`<slug>-<version>.zip`, `application/zip`) and a Content-Length, sent with `apikey` and the session's `Authorization: Bearer`, 64 KiB at a time with a `{ sent, total }` report after each. The request says `Expect: 100-continue` and the body waits for the Store's `100 Continue` (at most 1 s, for a server that ignores it): the Store refuses 401, 413 by Content-Length and 429 before it reads the body, and a body already being written when it closes the connection would make Node drop the answer unread. An answer that arrived stands even if the connection then fails; 120 s without traffic either way is `store_unreachable`. `publish.cancel(jobId)` destroys the request while bytes are still being sent (`upload_cancelled`, back to the review, which says so); once all are sent the screen shows an indeterminate "Processing…" and Cancel is off, since the Store may already be saving the version. An archive that is not the latest validation's, or has problems, is `package_invalid`, and the screen validates again. The Store's refusals keep its code (`publisher_mismatch`, `version_not_greater`, `invalid_manifest`, `package_too_large`, `rate_limited`, `harness_taken_down`, `forbidden`, `not_found`; by status when it sends no known code), its English message as the fallback text and its `problems`, which the failed state lists by `manifest.<messageKey>` with the code; Retry sends the same archive again. A 401, or no session, is `unauthenticated` and ends the session: the sign-in card asks to sign in again, and signing in validates the same folder again and goes back to the review. A 5xx or no answer is `store_unreachable`; no answer also has connectivity checked again. Offline, Publish is disabled and says why. While it uploads, the folder can be neither changed nor re-checked, and a change on disk is validated once the upload failed or was cancelled. The success screen says published versions are immutable, with View listing (the in-app route the Store answers, `/store/h/<publisher>/<slug>`) and Publish another, which clears the folder; the folder is no longer watched after a success.

My Harnesses (P0-08.3, `src/renderer/src/publish/MyHarnesses.tsx`) calls `publish.myHarnesses` each time the tab opens, so a version just published is there. Main (`src/main/runtime/my-harnesses.ts`) makes api.md's "Own versions" read with the session (`manifest->>id=like.<login>/*`: every version of the Publisher's Harnesses in any status, the takedown note on taken-down ones), groups the rows by Harness (newest published first; the Harness is named after its newest version and its downloads are its versions' added up), then asks one `latest_versions` for each Harness's own status and current version. Each Harness shows its name, ID, downloads, current version or why the Store does not show it (no published version, taken down), and a table of its versions: status (Unpublished with its date, taken down with the administrator's note), published date and downloads. Unpublish, only on the published versions of a Harness that is not taken down and off when offline, opens a confirmation ("Unpublish {name} {version}?", "Existing installs keep working. This version can no longer be downloaded."); confirming calls `publish.unpublish({ harnessId, version })` once, which posts `{ harness_id, version }` to `<store_base_url>/functions/v1/unpublish`, then the list says so and is read again. The Store answers an already Unpublished version with a success, so a stale list or a second click shows no error; its refusals keep their code (`forbidden`, `not_found`, `harness_taken_down`). A 401 ends the session, and no answer or a 5xx is `store_unreachable` (with Retry on the list).

## Store browsing

The Store home, search, Harness detail and Publisher pages (P0-09) read the Store anonymously over api.md's PostgREST reads and RPCs at `store_base_url`, in main (`src/main/runtime/store-catalogue.ts`, Electron-free); the renderer never talks to the Store. `store.home` reads Featured, Most downloaded and New in parallel and keeps them 5 minutes in memory per Store base URL (Retry reads again); `store.search` calls `search_harnesses` with the platform main fills in; `store.detail` reads the Harness, its Publisher and its published versions newest first (each marked when its permissions differ from the next older one's), then its latest version's Manifest, README and screenshots, and, only when the Harness is not listed, `latest_versions` for why; `store.publisher` makes api.md's Publisher page read for a lower-case login (anything else is refused before any request), never cached, and answers `publisher: null` for a login with no profile. Avatars are kept only on `https://avatars.githubusercontent.com`, the one avatar host the CSP allows, so another one shows the monogram; a date that does not parse is dropped (no join date, or the version left out of the history). Every answer carries this machine's platform. A network failure or timeout is `store_unreachable` and has connectivity checked again (the offline panel); a 5xx or an answer that is not the expected shape is `store_error`, shown inline with Retry. Icons and screenshots come as `store-asset://harness-assets/<path>` URLs, which main serves from the Store's `harness-assets` bucket only (`src/shared/store-assets.ts`); the CSP allows that scheme for images.

The detail page (`src/renderer/src/pages/HarnessDetailPage.tsx`) is `ListingDetail`, so it reads like the Publish preview and the consent dialog: header, screenshots, trust block, Models (each Slot's "Will use" from `bindings.resolveManifest`, or "No Connection can fill this Slot"), README, version history, footer. Its primary button (`store/primary-action.ts`, `store/DetailAction.tsx`) is one of seven states: Removed from Store, Not available for your platform, Install, Launch (secondary: Uninstall), Update (secondary: Launch), a download's progress with Cancel, and "Review and install" for a download waiting for consent. Launch, also as Update's secondary, is the Library's own `LaunchAction` and `useLaunch`, so "Set up a model first" and Starting…, Running… and Stopping… behave as on a Library card. Install runs the Store install (see Installing from the Store), Update the update (see Updates) and Uninstall the uninstall confirmation (see Uninstalling and the Library's controls). An installed Harness the Store no longer offers keeps its page, built from the installed Manifest, with Launch and "No longer available in the Store".

The Publisher page (`src/renderer/src/pages/PublisherPage.tsx`, `/store/p/<login>`) shows the avatar (or a monogram), the display name or else the login, `@login` linking to GitHub, the join date, the bio as plain text and the downloads of the listed Harnesses added up, then those Harnesses as the same Store card as home and search; "No such Publisher" for an unknown login and "No published Harnesses" for a profile with none. Every Publisher name in the app links to it: the Store cards, the detail page's header (an installed Harness's page the Store no longer offers too) and the Library cards.

## Reporting a Harness

The Report dialog (P0-12.1, `src/renderer/src/report/ReportDialog.tsx`, flows F8) opens from the detail page's footer, for the version its header shows, and from a Store install's Library card menu, for the installed version; a local install, which the Store may not know, has no Report. It asks for a reason (one of the six `report_reason` values, none preselected), optional details and an optional contact email, and shows everything else that is sent before Submit, read from main each time it opens (`store.reportInfo`): the Harness ID, the version, the platform, the app version and a random install ID. Main (`src/main/runtime/store-report.ts`, Electron-free) sends it to the Store's `report` function with the anon key alone, whoever is signed in, and builds `client_info` itself from those three values, nothing else; the contact email goes first in `details` (`src/shared/report.ts`, shared with the dialog's counter), which is at most 2000 characters. The install ID is a UUID made the first time a Report needs it and kept in the `install_id` setting. At most 3 Reports of one Harness that the Store took may go from this install in 24 hours (`report_history`, also in `settings`; neither key is in `settings.get`): the dialog says "You've already reported this Harness recently" without calling `store.report`, and main checks again and answers `rate_limited` with no request. A failed submit keeps everything typed and offers Retry; a sent one shows the toast "Thanks, a reviewer will look at this."

READMEs and changelogs are Markdown from the Publisher, rendered in the renderer by `src/renderer/src/listing/render-markdown.ts`: `marked` (GitHub-flavoured, raw HTML dropped, an inline `<script>` or `<style>` together with its content), then DOMPurify with an allow-list of what Markdown makes (headings, paragraphs, lists, quotes, code, emphasis, links, images, tables) and no attribute but `href`, `src`, `alt`, `title`, `align` and `start`. Links keep only absolute http(s) targets and open in the User's browser (the main window refuses every new window and hands an http(s) one to `shell.openExternal`); fragment, relative and `mailto:` links keep their text only. Images load only from the Store's asset bucket or as raster `data:` images.

## Usage

The Usage page (`src/renderer/src/pages/UsagePage.tsx`, P0-11.1, docs/ux/flows.md F7) shows the Model Gateway's Usage Records on this machine; every number is summed in SQL in main (`src/main/runtime/usage.ts` over `usage-records.ts`), and the renderer only formats. `usage.query({ from, to, harnessId?, providerId?, groupBy })` takes half-open ISO-8601 UTC bounds (`null` for unbounded) and an ordered `groupBy` of `harness`, `provider`, `model` (which also groups by Provider) and `day` (`[]` is one total row); only whitelisted column expressions reach the SQL text. `requests` counts every record, `errors` every status but `ok`; the token sums cover only `ok` records that reported both counts, and `unknownCount` the `ok` ones that did not, so the page shows "—" with "This Provider did not report usage" instead of a 0 that stands for missing data. Days are the User's local days (SQLite `date(timestamp, 'localtime')`), and the renderer computes the period's start (Today, 7 days by default, 30 days, All) from local midnight on every query (`usage/period.ts`). Migration 0008 adds an index on `usage_records(timestamp)`, for periods over every Harness, which the `(harness_id, timestamp)` index cannot serve.

After each insert main emits `usage.recorded` (`{ harnessId }`) to the main window; the page queries again on it at once and then at most once every 2 seconds, only while it is shown and the window is visible, and once when the window shows again after missed records (`usage/live-refresh.ts`). `usage.export` takes the page's period and filters, asks for a file with the OS save dialog (default name `harness-store-usage-<YYYY-MM-DD>.csv`) and writes the rows grouped by Harness, Provider and model, and day, ordered by those columns: UTF-8 without a BOM, CRLF line ends, a header row, RFC 4180 quoting, raw IDs, the local day and `last_used_at` in ISO UTC, and a leading `'` on any cell starting with `=`, `+`, `-` or `@` so a spreadsheet never runs it as a formula. It answers `{ path }`, `null` when cancelled, or `internal_error` when the file cannot be written, which the page shows until the next export. `usage.clear` deletes every Usage Record after the `usage/ClearUsageDialog.tsx` confirmation; the page then shows its empty state, "Launch a Harness to see usage here".

## Settings

The Settings page (`src/renderer/src/pages/SettingsPage.tsx`, P0-11.2) applies every value the moment it changes, through `settings.set`, and every value persists in the `settings` table. Language switches the UI in place and sets `HARNESS_LOCALE` for later launches only. Check for Harness updates (1 hour, 6 hours, 24 hours, Never) reschedules the update check at once, the next check a whole interval later (`settings.ts` fires `afterUpdateIntervalChange`, which `bootstrap.ts` wires to `updates.reschedule()`), and Check now (`installs.checkUpdates`) checks whatever the interval, off while offline, then toasts how many installs have an update. Data location shows the data root, with Open folder and Open logs folder (`app.openFolder('dataRoot' | 'logs')`, through the same `openPath` as the Library card's Open data folder). The Store URL sits under Advanced and is the one value applied with a button, Apply, because applying it signs the Publisher out: main checks it (an absolute `http:` or `https:` URL, no credentials, query or fragment, at most 2048 characters as stored (percent-encoded), `invalid_input` otherwise, shown beside the field), signs out first so the session is revoked at the old Store, writes it without a trailing slash, then drops the Store home cache and checks connectivity against the new Store, aborting a check of the old one still under way (`connectivity.storeChanged()`); Use default removes it. While it is set, every main screen shows a banner naming it with a link to Settings, which cannot be dismissed. Re-run setup opens the wizard at Welcome. Clear usage data opens the Usage page's own confirmation. Diagnostics are read when the page opens and again on Copy diagnostics, which has main write them to the clipboard as plain text (`diagnostics.copy`); the Gateway status is a GET of its `/v1/models` without a token, any HTTP answer within 1 s counting as reachable.

## First run

On a fresh profile (`settings.onboardingDone` false) the app opens on the first-run wizard (`/onboarding`), which fills the window without the sidebar: Welcome and language → Local Providers → Remote Provider (optional) → Default model → Done, with a step list on top and Skip on every step ("Skip setup" on Welcome jumps to the summary). Back works on every step but Welcome. Reaching Done sets `onboarding_done`, so later launches open on the Library; Open Store lands on Store home. The steps are a pure reducer (`src/renderer/src/onboarding/wizard-reducer.ts`); progress is not kept, so quitting midway starts again at Welcome. Settings has "Re-run setup", which opens the wizard at Welcome and clears nothing.

The Local Providers step lists what `connections.detectLocal` found, each with an Add checkbox, on by default, and Continue adds the checked ones. A Provider that already has its Connection (setup run again) shows Added with no checkbox and is left alone, so Continue never re-enables a disabled Connection or replaces a custom base URL. When nothing is found it explains, links to install Ollama and LM Studio, and offers Detect again. The Remote Provider step saves a real Connection through `connections.add` (its list leaves out the local Providers), which tests it first. The Default model step is a model picker over the Connections added in this run; Continue saves the picked model as the global `default` Slot Binding (`bindings.setGlobal`) and stays on the step with the error if that fails, and Skip sets nothing, so a Default Model set before is kept. While it saves, Skip and Back wait too (as on every step whose Continue is running). The summary shows the Default Model saved in this run, and Back then Skip keeps it there, since that binding stays stored.

## Languages

Every string the User sees comes from `src/shared/i18n/en.json` and `zh-CN.json`: flat keys, ICU messages, rendered with `const { t } = useI18n(); t('section.library')`. A new string needs an entry in both catalogs. The UI follows the Settings override, else the OS locale (`zh*` → `zh-CN`, anything else → `en`), which main resolves and sends over IPC; switching applies at once. Runtime and Gateway errors are looked up as `error.<code>` and Manifest problems as `manifest.<messageKey>`, falling back to the English `message`. Two checks run in `pnpm test` and `pnpm lint`: catalog parity (same keys, valid ICU, same arguments; every Manifest messageKey and Gateway code covered) and an ESLint rule that rejects hard-coded JSX text. To see Chinese, start the app with `--lang=zh-CN` or set the OS language (`LANG` only matters on Linux).
