# @harness-store/manifest

The single source of truth for the **Manifest**, the declarative `manifest.json` at the root of every **Harness Package**. The Publish flow in the desktop app, the Store's `publish` Edge Function and the **Runtime**'s installer all import this package instead of re-implementing the rules, so a Publisher gets the same answer everywhere.

Normative reference: [`docs/tech/manifest-spec.md`](../../docs/tech/manifest-spec.md). Spec: [`P0-01`](../../docs/delivery/specs/P0-01-monorepo-and-manifest.md).

Status: P0-01.2 (schema, `Manifest` type, `validateManifest`, problem codes, fixtures) and P0-01.3 (`validatePackage` for a folder, a zip or files in memory, and `diffForReconsent`) are in. Still to come: the `harness-manifest validate` CLI in P0-01.4.

## API

```ts
import {
  validateManifest,
  manifestSchema,
  PROBLEM_CODES,
  MESSAGES_EN,
  interpolate,
} from '@harness-store/manifest';
import type { Manifest, Problem, ValidationResult } from '@harness-store/manifest';

const result = validateManifest(manifestJsonText, {
  publisher: 'alice',
  publishedVersions: ['0.1.0'],
});
if (result.ok) {
  result.manifest; // Manifest: typed, a copy, top-level x- keys removed
} else {
  result.problems; // every blocking problem at once
}
result.warnings; // never block
```

- `validateManifest(input, options?)`: `input` is JSON text, UTF-8 bytes (any `ArrayBuffer` view; a byte order mark is ignored) or an already parsed JSON value (validated as the JSON `JSON.stringify` would produce). Options: `publisher` (the signed-in Publisher's GitHub login, compared case-insensitively) and `publishedVersions` (every published Harness Version of this Harness). Malformed options throw a `TypeError`; a malformed Manifest never throws, however large or deeply nested: its work is bounded (see [How validation works](#how-validation-works)).
- `manifestSchema`: the JSON Schema (draft 2020-12), deep-frozen. The file itself is exported as `@harness-store/manifest/manifest-v1.schema.json` for editors.
- `Manifest` and its parts (`Platform`, `Entry`, `HarnessRuntime`, `UserInterface`, `ModelSlot`, `ModelRequirements`, `DeclaredPermissions`, ...): generated from the schema into [`src/manifest.generated.ts`](src/manifest.generated.ts) and checked in.
- `PROBLEM_CODES`, `MESSAGES_EN` (English templates by `messageKey`) and `interpolate(template, params)` for rendering a translated template.

### Whole Harness Packages

```ts
import { ArchiveSource, InMemorySource, validatePackage } from '@harness-store/manifest';
import { DirectorySource, openArchiveFile } from '@harness-store/manifest/node';

await validatePackage(await DirectorySource.open('path/to/harness')); // a folder (Node)
await validatePackage(await openArchiveFile('harness.zip')); // a zip file on disk (Node)
await validatePackage(await ArchiveSource.open(zipBytes), { publisher: 'alice' }); // anywhere
await validatePackage(new InMemorySource({ 'manifest.json': bytes /* ... */ })); // tests
```

- `validatePackage(source, options?)` returns a `Promise<ValidationResult>`: everything `validateManifest` finds in `manifest.json`, plus the archive-safety rules, the archive limits and the file rules of [manifest-spec.md §1](../../docs/tech/manifest-spec.md). Same options as `validateManifest`. It throws only for a caller bug (not a source, malformed options) or an I/O error from the source; a malformed or hostile package always gets problems.
- Sources implement one interface, `PackageSource`: `listFiles(): string[]` (regular files, as `/`-separated package paths), `readFile(path, { maxBytes }?): Promise<Uint8Array>` (reads stop at `maxBytes`) and `listEntries(): PackageListing` (every entry with its kind, `file`, `directory`, `symlink` or `special` (a device, a named pipe, a socket), its size and its name as stored, plus the archive's size; for a zip also the other names an unpacker could use and any bytes that belong to no entry). The rules only use this interface, so a folder and its zip give the same answer.
  - `ArchiveSource.open(bytes | reader)` (main entry, pure): a zip as bytes or as a `RandomAccessReader` (`{ size, read(offset, length) }`). Opening reads the central directory and every entry's local header, never any content; `readFile` inflates one entry into memory. Nothing is extracted or written anywhere. An archive that is not a readable zip still opens (its listing has `unreadable`), and `validatePackage` reports `archive_invalid`.
  - `InMemorySource(map)` (main entry, pure): a `Map` or object from path to bytes, for tests and for callers that hold files without their archive. Prefer `ArchiveSource` for a zip: a map cannot show links or the archive's size.
  - `DirectorySource.open(folder)`, `fileReader(path)` and `openArchiveFile(path)` (`@harness-store/manifest/node`): a folder, listed without following links, and a zip file on disk read by position (never loaded whole).
- `diffForReconsent(previous, next)` compares two valid Manifests and returns `{ required, reasons, added, removed }`. `reasons` are `permissions_widened` (filesystem scope up the ladder none < workspace < home < paths, a new path under an unchanged `paths` scope, `shell` false to true, a new domain, or a domain list to `any: true`), `entry_changed` (any change to `entry`) and `runtime_kind_changed`. Narrowing never requires re-consent. `added` and `removed` list the differences as Manifest paths with the value after the first `:` (`permissions.filesystem.scope:home`, `permissions.shell`, `permissions.network.domains:api.github.com`, `permissions.network.any`, `entry.linux-x64:bin/tool`, `runtime.kind:binary`), for the update prompt's "New:" and "Removed:" lines. Keys with no effect (`paths` outside scope `paths`, `domains` next to `any: true`) are ignored.
- `PACKAGE_LIMITS`: the limits of manifest-spec.md §1 and the bounds on the validator's own work, in bytes and counts.

`ValidationResult` is exactly the shape in the P0-01 spec:

```ts
type Problem = {
  path: string;
  code: string;
  message: string;
  messageKey: string;
  params?: Record<string, string | number>;
};
type ValidationResult =
  | { ok: true; manifest: Manifest; warnings: Problem[] }
  | { ok: false; problems: Problem[]; warnings: Problem[] };
```

- `path` is relative to the Manifest root: `name`, `models.slots.default`, `platforms[1]`, `entry.win32-x64`, `["a.b"]` for a key that needs quoting, `$` for the Manifest as a whole. For the `file_*`, `icon_dimensions`, `screenshots_too_many` and `archive_*` codes it is a path inside the Harness Package instead (`assets/icon.png`, or the entry name as stored, such as `../escape.txt`, cut at 1 024 characters), and `$` is the Harness Package as a whole. The two kinds of path share one field, so a file named `entry` and the Manifest key `entry` look alike: tell them apart by `code` (every code is always one kind or the other; `entry_missing_for_platform` and `schema_invalid_json` always use Manifest paths).
- `code` is stable and additive-only: a shipped code is never renamed or removed. `schema_*` codes name the JSON Schema keyword that failed (`schema_max_items` is `maxItems`).
- `messageKey` is the code itself or `<code>.<variant>` for a more specific wording (e.g. `schema_pattern.harnessId`). `message` is the English template with `params` filled in. The desktop app maps the same `messageKey` to zh-CN and calls `interpolate` with the same `params`. `actual`/`value` params are JSON renderings (strings keep their quotes), shortened to 60 characters.

## How validation works

Rules run in this order, and every rule runs even when an earlier one failed (only a failure to load the document stops early):

1. **Load**: parse JSON text or bytes and drop top-level `x-` keys. A document with more than 2 000 JSON values (`MAX_MANIFEST_VALUES` in `src/document.ts`) in the rest is rejected here as `schema_invalid_json.too_large`. Every list and map in the schema has a maximum size, so the largest valid Manifest has fewer than 200 values (`test/validate-manifest.test.ts` computes the bound from the schema and fails if a new list is unbounded); the limit keeps the work, the number of problems and the JSON Schema library's error list bounded for hostile input (the library gathers errors with `push(...errors)`, which overflows the call stack at around a hundred thousand of them). The walk is iterative, and values quoted in messages are rendered with a bounded JSON printer, so no nesting depth can overflow the stack. The same walk reports every number beyond the range of a 64-bit float (`1e400` in JSON text parses as `Infinity`, which the JSON Schema library accepts as an integer and `JSON.stringify` writes as `null`) as `schema_type.non_finite`; the other rules still run.
2. **JSON Schema** validation against `manifestSchema`, translated into problems. Should the library still run out of stack (possible only for a document with thousands of problems on a host with a very small stack, such as a worker), the result is a single `schema_invalid_json.too_many_problems` problem, not an exception. The schema encodes every rule about a single field (types, enums, patterns, lengths, counts, closed objects), so editors pointed at it catch the same mistakes.
3. **Semantic rules** that JSON Schema cannot express, or expresses too expensively for untrusted input: `entry` against `runtime.kind` and `platforms`, duplicates in lists (JSON Schema `uniqueItems` is evaluated pairwise, which is quadratic), strict semver through the `semver` library (numeric parts beyond `Number.MAX_SAFE_INTEGER`), the `changelog` limit in bytes, `network` needing `domains` or `any`, and the `ignored_key` warnings.
4. **Option rules**: `publisher_mismatch` and `version_not_greater`.

A finding detected by two rules is reported once, and a type problem hides format problems about the same value (not problems about the key it sits under, such as a Slot name). A key that has no effect gives an `ignored_key` warning, but its value must still be valid. `manifestVersion` problems are listed first; this validator understands version 1 only. No defaults are applied to the returned Manifest: keys with a default (`channel`, `workspace`, `ui.path`, `ui.readyTimeoutSeconds`) stay optional in the type and absent when the Publisher left them out.

## How package validation works

`validatePackage` runs these steps, and each runs even when an earlier one failed:

1. **Archive safety and limits**, from `listEntries()` alone, before any file content is read: links and special files, `..` and absolute names (every name an unpacker could use), paths that would unpack to the same place, `\` or `:` in names, encrypted, unsupported or inconsistent entries, bytes that belong to no entry, more than 20 000 files, more than 500 MB. An archive that is not a readable zip gives a single `archive_invalid` problem.
   A listing stops after 100 000 entries (`PACKAGE_LIMITS.maxListedEntries`): the package is then reported with the single problem `archive_too_many_files.not_counted`, and nothing else is checked, not even the entries that were listed. This is the one exception to "every rule runs": it keeps the work bounded for an archive that is rejected anyway.
2. **The Manifest**: `manifest.json` is read (at most 1 MB, `schema_invalid_json.file_too_large` above that) and checked by `validateManifest` with the same options.
3. **Files**: `README.md` (a warning over 50 KB, from its listed size), `assets/icon.png` (only its first 33 bytes are read: the PNG signature and the `IHDR` chunk, whose CRC must match), screenshots (the files directly in `assets/` other than the icon, hidden files ignored; the first 8 bytes of each are read) and the Entry files: the `entry` path of a `node` Harness, and the path of every declared platform of a `binary` Harness. Entry files are only looked for when `entry` has the shape `runtime.kind` asks for and holds well-formed paths; otherwise the Manifest problem already says what is wrong. Paths match exactly, including case, as a zip would.

A link where a required file or an Entry should be is reported once, as a link. Paths that differ only in letter case, Unicode form or trailing dots and spaces (`manifest.json`, `MANIFEST.json` and `manifest.json.`) are rejected in every source, even a folder on a case-sensitive Linux file system: macOS or Windows would unpack them onto one file, and the one written last, not the one checked, would be the Harness's `manifest.json`. For the same reason names with `:` are rejected (on Windows, `manifest.json::$DATA` is `manifest.json`). A folder and its zip give the same result, problem for problem, with one exception: a folder has no compressed size, so `archive_too_large` applies to the zip made from it. `npm install` puts links in `node_modules/.bin`: install with `--no-bin-links`, or remove them, before packaging.

The zip reader (`src/zip/`) is small and written for this package: it reads the end of central directory record (ZIP64 too; split archives are refused), the central directory (a larger one than 64 MB is refused unread), every local header, and one entry's content at a time. Names are read as UTF-8 when the entry is flagged as UTF-8 or its name is valid UTF-8 (macOS and most Unix tools write UTF-8 without the flag), and as CP437, the zip format's default, otherwise. A read inflates in slices sized to the bytes asked for (from 16 bytes, doubling up to 16 KB), so checking a signature costs kilobytes of inflating however well the entry compresses, stops as soon as an entry inflates past its declared size, and checks the size and CRC-32 of every whole file it reads.

**Every unpacker must see the same files.** Unpackers that read a zip from the start (Java's `ZipInputStream`, streaming unpackers for Node, `bsdtar` on a pipe) take names and sizes from the local headers and never read the central directory, so a zip can show them files that the central directory, and so the rules, never list. Opening an archive therefore checks that:

- every local header matches its central directory record: the same name bytes, compression method, encryption flag, CRC-32 and sizes (or zeros followed by a matching data descriptor, as streaming zip tools write); a local header's own Unicode Path name is checked for `..` too;
- the entries (local header, data, data descriptor) cover everything from the first byte to the central directory, without gaps or overlaps (overlapping entries are also how "overlapping files" zip bombs work), the central directory holds exactly the records its end record counts and ends where that record starts, and nothing follows the end record but its comment (tools that look for the last end record would otherwise find another one);
- a ZIP64 end record, when there is one, agrees with the plain end record (some tools read one, some the other).

Zips made by Info-ZIP `zip` (to a file or a pipe) and Python's `zipfile` (to a file or a stream) pass, as `test/sources.test.ts` checks when the tools are installed; so do those of Go's `archive/zip` and the JDK's `jar`, checked by hand. One ambiguity remains, and is left to the unpacker: an entry with a data descriptor (flag bit 3) ends, for a streaming unpacker, where its data says (the end of the Deflate stream, or a descriptor signature), which only inflating every entry would confirm. The Runtime's unpacker (P0-05) must therefore read the central directory, reusing `ArchiveSource`'s listing and names, never stream the archive.

## Why a hand-written zip reader and `fflate`

The rules need what a zip's central directory holds and most zip libraries hide or discard: the Unix mode in the external attributes (for links), the raw entry names, both names of an entry with an Info-ZIP Unicode Path field, the compressed size and the entry count before anything is inflated. They also need to stop reading early and bound every allocation for a hostile archive, and to run unchanged in the renderer, Node and Deno. The reader is about 850 lines, comments included, against the published zip format (APPNOTE), and tests read archives made by Info-ZIP `zip` and Python's `zipfile` next to the test writer's hostile ones. Inflating is [`fflate`](https://github.com/101arrowz/fflate) 0.8: pure JavaScript, no dependencies, no `eval`, a streaming `Inflate` that takes the compressed data a slice at a time, and the same behaviour everywhere (the Web platform's `DecompressionStream` would work too, but its errors and its handling of trailing data differ between Node, Deno and Chromium). A bundle takes only `Inflate` from it, about 6 KB minified. [`@zip.js/zip.js`](https://gildas-lormeau.github.io/zip.js/) (2.18) was the alternative: it exposes the external attributes too, but it is a much larger library (8 MB unpacked, against fflate's 0.8 MB) that uses Web Workers unless configured otherwise, and most of it (writing, encryption, extraction) is what this package must not do.

## Why `@cfworker/json-schema`

The validator must run in the Electron renderer (whose Content Security Policy should not allow `unsafe-eval`), in Node and in Deno for the Supabase Edge Function. [Ajv](https://ajv.js.org) compiles schemas with `new Function`, and its precompiled "standalone" output still loads runtime helpers with `require()` even in ESM mode ([ajv#2209](https://github.com/ajv-validator/ajv/issues/2209)), so it would mean checking in generated code plus a CommonJS runtime. [`@cfworker/json-schema`](https://github.com/cfworker/cfworker/tree/main/packages/json-schema) interprets the schema instead: no `eval`, no dependencies, ESM, draft 2020-12 (react-jsonschema-form offers a validator built on it for CSP-constrained apps for exactly this reason). Its speed (no code generation) is irrelevant for a document the size of a Manifest. Two quirks are handled in `src/schema-problems.ts`: it re-reports a known key with an invalid value under `additionalProperties: false`, and it cannot build a pointer for a key containing a lone UTF-16 surrogate (such keys are renamed with U+FFFD before validation, then reported as unknown).

`semver` (the npm library) is imported from `semver/classes/semver.js` only, which keeps the browser bundle small; strictness on top of it is enforced here. The whole entry point, zip reader and `fflate` included, bundles to about 100 KB minified.

## Runs everywhere

`src/` imports no Node built-in and uses no Node-only global; ESLint enforces this for `src/**` except `src/node/`, which is the `@harness-store/manifest/node` subpath export (`DirectorySource`, `fileReader`, `openArchiveFile`). `test/browser-bundle.test.ts` builds `src/index.ts` with Vite for the browser, failing on any Node built-in, then runs the bundle in a V8 context that has only ECMAScript built-ins plus `TextDecoder` and `URL` and checks every fixture there, as a Manifest, as a zip (`ArchiveSource`) and in memory, with bytes from another realm. Deno is not part of the test run yet; the package uses nothing Deno lacks (ESM, `import ... with { type: 'json' }`, `TextDecoder`, `URL`, and npm packages Deno imports through `npm:` specifiers). In the Store's Edge Function, `ArchiveSource.open(uploadBytes)` validates the upload without touching a file system.

## Fixtures

[`fixtures/`](fixtures) holds one folder per problem code (named after the code), valid packages (`valid-minimal-node`, `valid-binary-multi-platform`, `valid-web-ui-options`, `valid-with-screenshots`) and a few scenarios (`multiple-problems`, `runtime-python-rejected`, `entry-file-missing-node`, ...). Every folder is a whole Harness Package: `manifest.json`, `README.md`, `assets/icon.png` and the Entry files, unless the fixture is about one of them. Each also has an `expected.json`:

```json
{
  "description": "Why this fixture exists.",
  "options": { "publisher": "alice" },
  "problems": [{ "code": "publisher_mismatch", "path": "id" }],
  "warnings": [],
  "manifest": { "problems": [], "warnings": [] },
  "archive": {
    "recipe": { "symlinks": [{ "name": "a", "target": "/etc/passwd" }] },
    "problems": [],
    "warnings": []
  }
}
```

- `problems` and `warnings`: what `validatePackage` finds in the folder, in its zip and in memory alike (so also what the CLI prints). `test/package-fixtures.test.ts` checks all three, and that the folder and its zip give the very same result.
- `manifest` (optional): what `validateManifest` finds in `manifest.json` alone, when that differs (a fixture about a missing icon has a valid Manifest). `test/fixtures.test.ts` checks it for text, bytes and a parsed value.
- `archive` (optional): for failure classes a folder cannot hold (zip slip, links, a 500 MB archive, 20 000 files, a broken zip, a local header naming another file, an entry the central directory leaves out), a recipe that `test/support/packages.ts` (`hostileArchive`) applies to the folder's zip, and what `validatePackage` finds in the result. The folders of these fixtures are clean, so their top-level `problems` are empty: the codes they are about are in `archive.problems`. A tool that runs fixtures (the CLI tests of P0-01.4) must build the archive from the recipe to see them.

`fixtures/*/dist/` is test data and is not git-ignored like build output. The icons are the 512×512 PNG `test/support/images.ts` makes, without an image library.

## Changing the schema

1. Edit [`src/manifest-v1.schema.json`](src/manifest-v1.schema.json) and, if prose changes, [`docs/tech/manifest-spec.md`](../../docs/tech/manifest-spec.md) in the same change (`test/schema.test.ts` compares the tag list, platform list, slug and Slot-name patterns with the doc).
2. Run `pnpm --filter @harness-store/manifest generate` and commit `src/manifest.generated.ts`. `pnpm typecheck` fails while it is stale.
3. A new `pattern` goes in a named `$defs` entry with a `schema_pattern.<name>` message; a new keyword needs a translation in `src/schema-problems.ts`. The schema tests enforce both.
4. Never rename or remove a problem code; add a fixture folder for a new one.

## Scripts

| Command          | What it does                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm test`      | Vitest: fixtures (as Manifests, folders and zips), acceptance criteria, rules, zip reader, re-consent, property tests, browser bundle, drift |
| `pnpm lint`      | ESLint with the shared root config, plus the no-Node-in-`src/` rule                                                                          |
| `pnpm typecheck` | `tsc --noEmit` (sources and tests), then the generated-type drift check                                                                      |
| `pnpm build`     | Emits `dist/` (including the schema JSON) from `tsconfig.build.json`                                                                         |
| `pnpm generate`  | Regenerates `src/manifest.generated.ts` from the schema                                                                                      |
