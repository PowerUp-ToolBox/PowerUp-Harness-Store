# P0-08 Publish flow

## Problem Statement

A Publisher who has built a Harness has no way to get it into the Store short of hand-crafting API calls. They need to know before uploading whether their package is valid, see what the listing will look like, upload with feedback, and later manage the versions they published. The Store side (P0-07) already validates and stores; what is missing is the in-app path from a folder on disk to a live listing, and back to withdraw a version.

## Solution

A Publish screen in the desktop app implementing flow F5 in `docs/ux/flows.md`: GitHub sign-in (only here), pick a folder, an immediate local validation of the very Harness Package the upload will send (built from the folder by the Runtime, checked with the shared Manifest package exactly as the Store checks it), a read-only review with a preview of the listing derived from the Manifest, upload with progress through the Store's `publish` function, and a success state linking to the listing. The same screen lists the signed-in Publisher's Harnesses and versions with Unpublish, and keeps P0-05's "Install this folder locally" so a Publisher can test before publishing.

## User Stories

1. As a Publisher, I want to sign in with GitHub from the Publish screen, so that I only create an account when I actually want to publish.
2. As a Publisher, I want sign-in to happen in my system browser and return me to the app, so that I never type my GitHub password into a desktop app.
3. As a Publisher, I want to see which GitHub account I am signed in as (avatar and login) and sign out, so that I can switch accounts if I maintain more than one.
4. As a Publisher, I want to choose a folder by button or drag-and-drop, so that publishing starts from where my code already is.
5. As a Publisher, I want validation to run the moment I pick a folder, so that I find problems before I have filled in anything.
6. As a Publisher, I want each problem shown with the Manifest field path, a stable code and a plain-language message in my UI language, so that I can fix it quickly.
7. As a Publisher, I want validation to re-run when I press Re-check or when files in the folder change, so that I can iterate without re-picking the folder.
8. As a Publisher, I want the Continue button disabled until there are zero problems, so that I cannot upload something the Store will reject anyway.
9. As a Publisher, I want to see the Harness ID prefix the Store expects from me (my login plus a slash), so that a mismatch is explained before I upload.
10. As a Publisher, I want the app to check the Store for my earlier versions of this Harness before upload and tell me if my version is not greater, so that I do not wait for a full upload to learn that.
11. As a Publisher, I want a preview of my listing (icon, name, summary, tags, permissions with the trust block, Slots, platforms, README), so that I see what Users will see.
12. As a Publisher, I want the changelog from my Manifest shown in the review, so that I remember to write one.
13. As a Publisher, I want the app to build the zip for me from the folder, so that I do not have to worry about archive layout.
14. As a Publisher, I want the app to exclude obvious junk (`.git`, `.DS_Store`, editor swap files) and whatever my `.harnessignore` names from the archive and tell me what it excluded, so that packages stay clean.
15. As a Publisher, I want to see the archive size before upload and be warned when it is over 100 MiB, so that I can trim it.
16. As a Publisher, I want an upload progress bar and a Cancel button while the package is being sent, so that a large upload is not a black box.
17. As a Publisher, I want a Store refusal shown in my language with its code, the problems the Store found and a Retry button, so that a transient failure does not make me start over.
18. As a Publisher, I want a success screen with a link that opens my listing in the Store tab, so that I can check it immediately.
19. As a Publisher, I want to be reminded on the success screen that published versions are immutable, so that I understand I must publish a new version to change anything.
20. As a Publisher, I want a "My Harnesses" tab listing each Harness with its versions, status (taken down with the administrator's note) and download counts, so that I can manage what I have published.
21. As a Publisher, I want to Unpublish a version after a confirmation that names the version and says existing installs keep working, so that I can withdraw a release safely.
22. As a Publisher, I want to install the folder locally and launch it without publishing, so that I can test the real launch contract on my machine.
23. As a Publisher, I want locally installed Harnesses marked "Local" in the Library and excluded from Store update checks, so that they are not confused with Store installs.
24. As a Publisher, I want re-installing the same folder locally to replace the previous local install and keep its Data Directory, so that iterating is fast.
25. As a Publisher, I want Sign in, Publish and Unpublish disabled with an explanation while offline, so that I do not go through a flow that cannot be submitted.
26. As a Publisher, I want an expired session to prompt me to sign in again without losing my chosen folder, so that a long editing session does not cost me work.
27. As a Publisher, I want the Publish screen to keep my folder, its validation and my tab when I visit another screen and come back, so that I can look something up mid-publish.
28. As a User who never publishes, I want the Publish screen to explain in one paragraph that only Publishers need an account, so that I am not confused about why sign-in exists.

## Implementation Decisions

- **Auth and the sign-in card** (P0-08.1): P0-07.2 built the sign-in (Supabase Auth GitHub OAuth, PKCE in the system browser, the custom URL scheme callback, the session in the encrypted secrets store); this screen uses its IPC (`auth.signIn`, `auth.signOut`, `auth.whoami`, `auth.changed`) and replaces its placeholder. `auth.whoami` runs when the Publish screen opens, not at app start. Signed out: the one-paragraph explanation and "Sign in with GitHub"; while the browser is out, "Finish signing in in your browser…" with Cancel, which calls `auth.signOut`; Sign in is disabled offline. Signed in: the GitHub avatar (the renderer CSP's `img-src` allows `https://avatars.githubusercontent.com`), "Signed in as {login}", "Your Harness IDs start with `<login>/`" and Sign out. Any sign-out keeps the chosen folder.
- **Screen layout and state**: signed in, the tabs "New version" and "My Harnesses" (screens.md); signed out, only the sign-in card. "Install this folder locally" stays P0-05's standalone panel with its own picker in both states; it is not wired to the folder chosen for publishing (the demo places it next to Continue). The flow's state (tab, folder, validation, upload, job) lives in a provider at Shell level, so leaving the Publish screen and coming back keeps it, and the watcher keeps running meanwhile. The New version steps follow the demo: pick → checking → problems or clean → review → uploading → done, where review is a sub-step of `valid`:

  ```
  signed_out → signing_in → idle
  idle → validating → invalid | valid (pick, then review)
  valid → uploading → published | failed
  uploading → valid (cancelled while sending: back to review, "Upload cancelled")
  failed → uploading (Retry, same archive) | validating (folder changed: valid (edit))
  any → idle (choose another folder; "Publish another" clears the folder)
  session expired or 401 → keep folder and validation, "Sign in again"; signing in validates again and returns to review when still valid
  ```

- **Folder choice** reuses `installs.chooseFolder`. Drag-and-drop gets the dropped item's path from the preload's `pathForFile` helper (Electron's `webUtils.getPathForFile`, outside the IPC method table); the renderer calls `preventDefault` on `dragover` and `drop`, and main refuses a dropped item that is not a folder with `invalid_input` ("Drop a folder"). If the chosen folder itself turns into a file, that is `package_invalid`, not a refused drop.
- **Validate exactly what is uploaded**: `publish.validateFolder(path)` (also Re-check and the watcher) walks the folder without entering excluded folders, builds the zip the upload will send and validates that zip with `ArchiveSource.open(bytes)` and `validatePackage`, passing `publisher` (the signed-in login) and `publishedVersions` (below), so local results match the Store's. It answers `{ archiveId, problems, warnings, manifest | null, iconDataUrl, readme, excluded[], archiveSize, versionCheck, lastPublishedVersion | null, isNew }`, where `versionCheck` is `checked`, `skipped` or `failed`, `archiveId` is null when no zip could be built, and `readme` is the zip's README up to 1 MiB. The newest run wins (a sequence number; a replaced run stops between 64 KiB chunks, never asks the Store and never ends the session) and main keeps only the latest zip; `publish.publish` with an `archiveId` that is no longer the latest, or whose validation found problems, answers `package_invalid` and the renderer validates again.
- **Archive build**: deterministic, as the examples' pack script: files only (no directory entries), sorted by path, every mtime 1980-01-01, each file's Unix mode, Deflate level 6 fed 64 KiB at a time with a yield in between, so the main process (which hosts the Model Gateway) never blocks. It is written by a small writer around fflate's `ZipDeflate` (fflate's streaming `Zip` writes data descriptors, which validatePackage refuses on stored entries). Output past `PACKAGE_LIMITS.maxArchiveBytes` stops the build with one `archive_too_large` problem; a folder with more than `PACKAGE_LIMITS.maxListedEntries` files stops the walk with `archive_too_many_files`. Symbolic links and special files outside excluded paths go in as zero-length entries carrying their mode, so validatePackage reports `archive_symlink` or the special-file problem at their own path and Continue stays blocked; inside excluded paths they are ignored.
- **Exclusion rules** have one home, a desktop module, copied exactly by `examples/*/scripts/excluded.mjs` (which stay standalone; a desktop test imports both copies and checks them against it on a table of paths): `.git` at any depth (folder or file), `node_modules/.cache/` at any depth, `.DS_Store`, `Thumbs.db`, `*.swp`, plus an optional root `.harnessignore` in gitignore syntax (the `ignore` package). Its `!` cannot bring back a fixed exclusion, and `.harnessignore` itself is left out and listed. The review lists the topmost excluded paths: a folder as `dir/` without a file count, a file by its path. The Manifest API does not change.
- **Pre-flight version check** runs only when the Harness ID's publisher segment equals the signed-in login: api.md's "Own versions" read filtered by `manifest->>id=eq.<id>`, every row (any status) going to validatePackage as `publishedVersions`. So `version_not_greater` and `publisher_mismatch` come from validatePackage itself, before any upload, with its own `manifest.<messageKey>` text (naming the latest version, or the expected publisher), not the screens.md variant. Zero rows shows "New Harness", otherwise "Last published version: X" (the highest). A failed read (unreachable or 5xx) still finishes the validation without `publishedVersions` and shows a non-blocking note that the Store checks on upload; a 401 ends the session (`session_expired`). There is no pre-check for a taken-down Harness: the Store's `409 harness_taken_down` gets its own copy.
- **Problem list**: problems sorted stably by `path` (code-unit order); each row shows the path, the translated message (`manifest.<messageKey>` with `params`, never looked up by `code`) and the code as small secondary text. Warnings are listed apart and never block. Continue is enabled exactly when there is no problem.
- **Watcher**: one folder at a time in main, `fs.watch(folder, { recursive: true })` on macOS and Windows; on Linux, where Node emulates a recursive watch by watching the whole tree (excluded folders included), each folder the build listed gets its own non-recursive watch, replaced on every listing. The watch starts only once the build has listed the folder within the limit (a folder too large to list is not watched), is re-armed when it died, and ignores changes under excluded paths. 500 ms after the last change main emits `publish.folderChanged { path }`, and the renderer calls `publish.validateFolder`; during an upload that re-validation waits until the upload ends. After a success main stops watching before it answers, and `publish.stopWatching` stops it explicitly.
- **Review**: merges F5 steps 4 and 5: the read-only facts from the Manifest, the changelog, the exclusion list and the archive size (a warning above 100 MiB, 104 857 600 bytes, never blocking), then the listing preview, then Publish and Back. Offline (the app's connectivity state, beside the global offline banner), Publish is disabled with an inline explanation.
- **Listing preview and shared components**: the run builds the listing components P0-09 reuses: `HarnessCard`, `ListingDetail` and `TrustBlock` (Declared Permissions with severity, runtime kind, UI Kind, Workspace and the no-sandbox sentence). The consent dialog's permission list moved into `TrustBlock`, so the preview, the consent dialog and the Store detail page share one component. The preview shows the icon (a `data:` URL from the zip), name, the signed-in Publisher (login and avatar), summary, translated tag chips (`tag.<name>` keys in en and zh-CN for the schema's tags), platforms, 0 downloads, the trust block and the Slots (description, requirements, Recommended Models; no "Will use"). Screenshots are left out; README and changelog are plain pre-wrapped text until P0-09 brings the sanitised Markdown renderer.
- **Upload** (P0-08.2): `publish.publish({ archiveId, jobId })` sends the validated zip, unchanged, from main to `<store_base_url>/functions/v1/publish` (the base URL is the existing `store_base_url` setting) with a Node `http`/`https` request, since `net.fetch` reports no upload progress; so the OS proxy settings do not apply to it. The body is a hand-built multipart body with one part, `package` (`<slug>-<version>.zip`, `application/zip`), and an explicit Content-Length; headers `apikey` and `Authorization: Bearer <access token>`, plus `Expect: 100-continue`: the body waits for the Store's `100 Continue` (at most 1 s, for a server that ignores it), because the Store refuses 401, 413 by Content-Length and 429 from the headers, and a body already being written when it closes the connection would lose the answer. It is written in 64 KiB chunks with a `{ sent, total }` event on `progress:<jobId>` after each; the renderer names the job (a UUID) and subscribes before the call, which resolves only with the final outcome. 120 s without traffic is `store_unreachable`. An answer that arrived stands even if the connection then fails; any 201 is the version published, its Harness ID and version taken from the zip's Manifest when the body is cut off.
- **Cancel** works only while bytes are being sent: `publish.cancel(jobId)` destroys the request and the call answers `upload_cancelled`, returning to the review with an inline "Upload cancelled" (there are no toasts). Once everything is sent the screen shows an indeterminate "Processing…" with Cancel disabled, since the Store may already be committing. A cancelled or failed upload leaves no server state (P0-07).
- **Errors**: new `IpcErrorCode`s `unauthenticated`, `publisher_mismatch`, `version_not_greater`, `invalid_manifest`, `package_too_large`, `rate_limited`, `harness_taken_down` (a taken-down Harness, or for Unpublish a taken-down version), `forbidden`, `not_found` and `upload_cancelled`, each with `error.<code>` copy in en and zh-CN; the Store's code is kept (by status when it sends no known one). `IpcError` gains optional `problems` (the Store's problem list, sorted by path, malformed entries dropped); the Store's English message becomes `IpcError.message`, a fallback only. The failed state shows the translated message, the code and the Store's problems via `manifest.<messageKey>`, with Retry re-sending the cached archive. A 401 or no session is `unauthenticated` and ends the session (the "Sign in again" path, folder kept); a 5xx or no answer is `store_unreachable`, and no answer also runs `connectivity.check()`.
- **Success**: "Published! Versions are immutable; …", "View listing" to the returned `url` (the in-app `/store/h/<id>` route, a placeholder until P0-09) and "Publish another" (back to idle, folder cleared).
- **My Harnesses** (P0-08.3): `publish.myHarnesses` makes api.md's "Own versions" read with the session JWT, which now also selects `name:manifest->>name` and is filtered by `manifest->>id=like.<login>/*`: every version of the Publisher's Harnesses, published, Unpublished or taken down (with the takedown note), through the Publisher-only read policy P0-07.6 added. Rows are grouped by Harness ID, the groups ordered by newest `published_at`, each named after its newest version, its downloads the sum over its versions. One `latest_versions` call (without the Manifest) gives each Harness's own status and current version; there is no owner policy on `harnesses`. The list is read each time the tab opens, so a version just published is there (this is the refresh after a success). The read answers at most PostgREST's `max_rows` (1000) versions and is not paged.
- **Rows and Unpublish**: each Harness shows name, ID, downloads, its current version or why the Store does not show it, and a table of versions: status (Unpublished with `unpublished_at`, taken down with `takedown_note`), published date, downloads. Unpublish appears only on published versions of a Harness that is not taken down, and is disabled offline and while its own call runs. The confirmation reads "Unpublish {name} {version}?" / "Existing installs keep working. This version can no longer be downloaded." (demo copy); confirming calls `publish.unpublish({ harnessId, version })` once (a double click is guarded), then an inline status replaces the demo's toast and the list is read again. The Store answers an already Unpublished version with 200, so a repeat is no error. A refusal meaning the list is stale (`harness_taken_down`, `not_found`, `forbidden`) reads the list again; a 401 ends the session; no answer or a 5xx is `store_unreachable` with Retry.
- **IPC**: `publish.validateFolder(path)`, `publish.stopWatching()`, `publish.publish({ archiveId, jobId })`, `publish.cancel(jobId)`, `publish.myHarnesses()`, `publish.unpublish({ harnessId, version })`, and the event `publish.folderChanged` (in `isIpcEventName`); `progress:<jobId>` carries `{ sent, total }`. api.md lists them.
- **Local install** reuses P0-05's "install from folder" unchanged.
- **Copy**: every user-facing string exists in `en` and `zh-CN`.
- **Dependencies**: fflate, ignore and semver are desktop devDependencies, like every other bundled dependency of the app (only node-pty ships as a runtime dependency).

## Testing Decisions

- **Seams**: the Runtime's publish module over IPC against a fake Store on a real HTTP port (no Docker in the root `pnpm test`): the pre-flight read, the `publish` function (it parses the multipart body, runs validatePackage and keeps the version for the detail read, answers 401, 413 and 429 from the headers like the real function, and honours `Expect`), and the reads and `unpublish` with the read policies applied (scoping by session and login filter, statuses, the note, the latest version moving back). A fake `fs.watch` seam drives the watcher. Renderer component tests under jsdom, in en and zh-CN. A store seam test (`test:store`, run by the CI store job against the local stack) checks the exact "Own versions" read as the owner, another Publisher and anon across two Harnesses. No new SQL.
- **Good tests, as built**: the exclusion rules and the examples' copies agree on a table of paths; the same folder zips to identical bytes, and excluded files are absent from what is sent; a link yields its problem at its path and no request at all; a version equal to the last published shows `version_not_greater` before any upload (no `publish` call); a failed pre-flight read leaves a note, a 401 ends the session; a replaced validation run neither asks the Store nor ends the session; the watcher re-arms after an error and ignores excluded paths; progress events, Cancel mid-body (the Store must see the body end short), early 401, 413 and 429 on an 8 MiB package with nothing sent, a 201 cut off mid-body, a 422 with problems out of order; My Harnesses grouping, statuses, the confirmation copy, one call on a double click, idempotent and concurrent Unpublish, the re-read after a stale-list refusal.
- **Not built here**: the Playwright for Electron smoke journey is left to P0-13, whose acceptance journey publishes through the Publish screen; P0-01's package fixture tests are not repeated; the integration tests run against the fake Store, not P0-07's local Supabase harness.
- **Prior art**: Store tests from P0-07; renderer component tests from P0-04; the Runtime seams of P0-05.

## Out of Scope

- GitHub repository import (`owner/repo@tag`) and webhook auto-publish (P0.5-03, P1-09).
- Editing listing metadata independently of the Manifest (everything comes from the Manifest in P0).
- Beta Channel selection (P1-02).
- Publisher analytics beyond raw counts (P1-05).
- Automated content scanning at publish time (P1-07).
- The `harness-manifest validate` CLI and "Install this folder locally" (which copies the folder's whole listing) apply no exclusions.
- Markdown rendering of README and changelog, screenshots in the preview and the real listing page behind "View listing" (P0-09).
- Paging My Harnesses beyond `max_rows`; the OS proxy for the upload.
- Not built from the design demo: "Install this folder locally" next to Continue on the publishing folder, toasts, several windows per Harness, model picking inside the install dialog, desktop shortcuts, a simulated Dock.

## Further Notes

- This spec introduces no schema change: the Publisher-only RLS read policy on own versions (any status, with the takedown note) was added by P0-07.6.
- A CLI publish path is deliberately not in P0; the folder picker is the single supported path.
- Deviations from the tickets as written: validation runs on the built zip, not on the folder as a directory; the pre-flight check is the "Own versions" read, not `latest_versions`, and `publisher_mismatch`/`version_not_greater` come from validatePackage's options rather than synthetic problems; messages are looked up by `messageKey`, not by code; a cancelled upload returns to the review, not idle; the upload sends `Expect: 100-continue`; on Linux the watcher is per folder rather than one recursive watch; My Harnesses is refreshed by reading it when its tab opens.
- The hosted Edge Function's request size limit (api.md, Known limitations) is not repeated in the UI copy.
