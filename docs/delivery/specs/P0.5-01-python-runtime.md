## Problem Statement

Most agent code in the wild is written in Python, but in P0 a Harness can only be a Node program or a pre-built native executable (Manifest `runtime.kind` is `node` or `binary`). A Python author who wants to list on the Store today must either rewrite in TypeScript or freeze their program into per-platform binaries, which is brittle, large, and beyond what most authors will do. The supply side of the Store is therefore artificially small, and Users cannot install the Python agents they already know.

## Solution

The Runtime learns a third runtime kind, `python`. A Publisher ships ordinary Python source with a `pyproject.toml` or `requirements.txt`; the Runtime bundles `uv`, creates an isolated per-install virtual environment, installs the declared dependencies on first install (and on update when the lock or dependency declaration changed), and launches the declared Entry with the bundled interpreter. Installation progress and failures are shown in the Library with actionable messages. The launch contract, Gateway access, UI Kinds, Workspace and Data Directory behave exactly as for Node Harnesses, so nothing else in the platform changes.

## User Stories

1. As a Publisher, I want to declare `runtime.kind = python` in my Manifest, so that I can publish my existing Python agent without rewriting it.
2. As a Publisher, I want to declare the Python version my Harness needs (e.g. 3.11, 3.12, 3.13), so that the Runtime provisions an interpreter my code was tested against.
3. As a Publisher, I want dependencies read from `pyproject.toml` (preferred) or `requirements.txt`, so that I can keep my normal project layout.
4. As a Publisher, I want to include a `uv.lock` so that installs are reproducible and Users get exactly the versions I tested.
5. As a Publisher, I want the Entry to be either a module (`-m mypkg.main`) or a script path, so that both package-style and script-style projects work.
6. As a Publisher, I want the Manifest validator to tell me before upload if my Python declarations are inconsistent (missing dependency file, unsupported Python version, entry not present), so that I do not publish a broken version.
7. As a Publisher, I want to test my Python Harness with "Install from folder" before publishing, so that I can see exactly what Users will experience.
8. As a User, I want installing a Python Harness to feel like installing any other Harness, so that I never have to know or care what language it is written in.
9. As a User, I want to see dependency installation progress (resolving, downloading, installing) in the Library, so that a slow first install does not look frozen.
10. As a User, I want dependency installation to happen once at install time rather than at every launch, so that launching is fast.
11. As a User, I want an install that fails because of a network error to be retryable with one click, so that a flaky connection does not leave a half-installed Harness.
12. As a User, I want an install that fails because a dependency cannot build on my platform to show the relevant `uv` output and a "Report to Publisher" link, so that I understand it is not my fault and can act on it.
13. As a User, I want a Harness that failed dependency installation to be clearly marked "Not ready" in the Library and never launchable in that state, so that I do not hit confusing runtime errors.
14. As a User, I want updates to reuse the existing environment when dependencies did not change, so that updates are quick.
15. As a User, I want the Python environment to be removed when I uninstall the Harness, so that disk space is reclaimed.
16. As a User, I want Python Harnesses to receive the same environment variables and Gateway Token as Node Harnesses, so that any model I bound works with them.
17. As a User, I want a Python Harness to never touch my system Python or global site-packages, so that installing agents does not break my own development setup.
18. As a User, I want Python Harnesses to work offline after installation, so that a local-model workflow needs no network.
19. As a User on Windows, I want Python Harnesses to work without me installing Python or build tools, so that the Store promise holds on every platform.
20. As a User, I want the Runtime to show which Python version a Harness uses on the detail page and in Library, so that I can understand what is running on my machine.
21. As a Store administrator, I want packages that declare `python` but ship compiled native wheels only for some platforms to be limited to those platforms in the Manifest, so that Users on other platforms are not offered a Harness that cannot install.
22. As a developer of the platform, I want the Python provisioning to be a separate module behind the same "prepare install" and "build launch command" interfaces as Node and binary, so that adding runtime kinds later stays cheap.

## Implementation Decisions

- **Manifest extension** (extends `manifest-spec.md` §3): `runtime: { kind: "python", python: "3.11" | "3.12" | "3.13", dependencies?: "pyproject" | "requirements" }`. `dependencies` defaults to `pyproject` when `pyproject.toml` exists, otherwise `requirements`. Entry for Python is a string in one of two forms: a relative path to a `.py` file, or `module:<dotted.module>` executed as `-m`. The Manifest package rejects a Python Manifest when the dependency file or the entry target is absent from the archive, or the Python version is outside the supported set.
- **Provisioning**: the Runtime bundles `uv` per platform inside the desktop app. On install (and on update when `pyproject.toml`, `requirements.txt` or `uv.lock` changed by content hash), it runs `uv python install <version>` (cached in the app data root, shared across Harnesses) and `uv sync` or `uv pip install -r` into a virtual environment stored **outside** the unpacked package directory, under the install root for that Harness Version, so that the package stays pristine and the environment is dropped with the version.
- **Install state machine** (decision-encoding snippet):
  ```
  downloaded → verified → unpacked → preparing_env (progress events) → ready
                                              └─ env_failed (retryable; reason: network | build | unsupported)
  ```
  `ready` is required for Launch. Library shows `preparing_env` with a progress bar fed by parsed `uv` output and `env_failed` with the captured log.
- **Launch**: the Supervisor builds the command from the environment's interpreter and the Entry, sets `PYTHONUNBUFFERED=1` and `PYTHONDONTWRITEBYTECODE=1`, and otherwise applies the launch contract unchanged (architecture §4), including stripping inherited vendor credentials and injecting Gateway variables. `cwd` rules are unchanged.
- **Isolation**: no system Python is ever used; `uv` is invoked with flags that ignore user-level configuration and global site-packages. Interpreters are the `uv`-managed standalone builds.
- **Offline**: once `ready`, launching performs no network access on the platform side. `uv` cache is retained so re-installs of the same versions are offline-capable on a best-effort basis.
- **Windows**: no compiler is provided. Dependencies requiring source builds on Windows fail with reason `build`; the failure message recommends the Publisher provide wheels or restrict `platforms`.
- **Detail page and Library** show "Python 3.12" alongside the existing runtime kind display.
- **Timeouts**: environment preparation has a 15-minute ceiling; exceeding it yields `env_failed` with reason `timeout`.

## Testing Decisions

- Good tests observe external behaviour: the install state transitions, the environment's existence, the launched process's observable environment and Gateway calls, not `uv` internals.
- Primary seam: **Supervisor seam** (architecture §8, item 3). Fixture Python Harnesses: a minimal one with no dependencies, one with a pure-Python dependency, one with a deliberately unresolvable dependency, one with a missing entry. Assert state transitions, retry behaviour, log capture and that `ready` Harnesses launch and can reach the fake Provider through the Gateway.
- **Manifest validation seam**: fixtures for each Python-specific rejection code.
- Add the Python fixtures to the **Desktop E2E seam** smoke journey behind a flag so CI on all three OSes proves at least the no-dependency and pure-Python cases end to end.
- Prior art: the Node and binary fixture Harnesses and their Supervisor tests from P0-05.

## Out of Scope

- The Python SDK (P0.5-02).
- Native build toolchains, conda, or system-package dependencies.
- Running arbitrary post-install scripts from the Harness.
- Sandboxing (ADR-0004 still applies).
- Background Harnesses (P1-08).

## Further Notes

Shared interpreter downloads mean the first Python Harness a User installs pays a one-time cost; subsequent installs of the same Python minor version are fast. The Store detail page should set that expectation in copy ("First install downloads Python 3.12, about 30 MB"). The `uv` binary is a third-party dependency of the app itself; pin its version and record the upgrade procedure in the repository's contributor notes.
