# P0-05 Runtime: install from folder, launch and supervise Harnesses

## Problem Statement

A Harness is a program; someone has to start it correctly, give it the environment the launch contract promises, open a window for it, keep exactly one instance alive, stop it when the User closes the window and clean up its Gateway Token. Publishers also need to run their own Harness locally, before the Store exists, exactly the way Users will run it, or they will publish things that do not launch.

## Solution

The Runtime's Process Supervisor and local installer. "Install this folder locally" (Publish screen) validates a local Harness directory like a Store package, asks for consent, then installs it, marked Local in the Library. Launching checks that a model can fill the `default` Slot, resolves Entry for the platform, prepares the Data Directory and the Workspace the User chose, issues a Gateway Token, spawns the process with the documented environment on the Runtime's Node or the binary directly, and opens a Harness window: for a web UI Kind a Starting state that shows the Harness's page once its port accepts connections, for a terminal UI Kind an embedded terminal at once. It enforces one instance per Harness and implements the shutdown sequence, log capture and error surfacing. `docs/tech/architecture.md` §4 is normative for the launch contract.

## User Stories

1. As a Publisher, I want to install my Harness from a local folder, so that I can test it exactly as Users will before publishing.
2. As a Publisher, I want validation problems shown if my folder is not a valid Harness, so that I fix them first.
3. As a Publisher, I want locally installed Harnesses marked as "Local" in Library, so that I can tell them from Store installs.
4. As a Publisher, I want to reinstall from the same folder to pick up changes, so that iteration is quick.
5. As a User, I want to click Launch and see the Harness open as its own window, so that it feels like a separate app.
6. As a User, I want a web-UI Harness's window to show a Starting state with the elapsed time and load the Harness's page only when it is actually ready, so that I never see a connection-refused page.
7. As a User, I want a terminal-UI Harness to open in a proper terminal window with colours, resizing, scrollback, copy and paste, so that TUI Harnesses are pleasant.
8. As a User, I want a Harness that needs a Workspace to ask me for a folder, remembering my last choice, so that project-based Harnesses are quick to start.
9. As a User, I want a Harness with an optional Workspace to let me pick one or skip, so that I control access.
10. As a User, I want launching an already-running Harness to focus its window instead of starting a second copy, so that state is not duplicated.
11. As a User, I want closing the window to stop the process, so that nothing keeps running or spending in the background.
12. As a User, I want a Harness that crashes to keep its window readable with the exit code, Show logs and Relaunch, and its Library card to say it exited with an error, so that I can report it.
13. As a User, I want a Harness that never becomes ready to time out with a clear message and its last output, so that I am not stuck on a spinner.
14. As a User, I want a Harness to be unable to see my shell's `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`, so that it cannot bypass the Gateway with my own credentials.
15. As a User, I want the Harness's private data to survive updates and be deleted on uninstall, so that state is predictable.
16. As a User, I want to open a Harness's data folder and its logs from Library, so that I can inspect or back up.
17. As a User, I want the app to tell me when a Harness is not available for my platform instead of failing at launch, so that I am not misled.
18. As a User, I want quitting the app to stop all running Harnesses gracefully, so that nothing is orphaned.
19. As a User, I want a Harness window to have a minimal top bar with the Harness name, the model each Slot uses, Reload (web) and Open logs, so that I can recover from a stuck page and see what runs.
20. As a User, I want the web window to block navigation to external sites (opening them in my browser instead), so that a Harness UI cannot hijack the window.
21. As a Harness author, I want `HARNESS_PORT` to be free and reserved for me, so that I can bind without retries.
22. As a Harness author, I want my current working directory to be the Workspace when one is chosen and my Data Directory otherwise, so that relative paths are predictable.
23. As a Harness author, I want SIGTERM before SIGKILL with a few seconds' grace, so that I can flush state.
24. As a Harness author, I want stdout/stderr captured to a log file even for web-UI Harnesses, so that my own debugging output is available.
25. As a Harness author, I want my Node Harness to run on the Runtime's Node without any system Node installed, so that Users have zero prerequisites.
26. As a Harness author of a binary Harness, I want the executable bit set on macOS/Linux after unpack, so that zips created on Windows still launch.
27. As a developer, I want the Supervisor testable without a display, so that lifecycle tests run in CI.
28. As a developer, I want each launch recorded (start, end, exit code, token revoked), so that Usage and debugging can correlate.
29. As a User, I want Launch to say "Set up a model first" and take me to the Models page when no model can fill the Harness's `default` Slot, so that a Harness never starts only to fail on its first model call.

## Implementation Decisions

- **Install from folder** (P0-05.1): "Install this folder locally" sits on the Publish screen (flows F5), where it works signed out and offline although the rest of that screen needs sign-in; the Library has no entry point (its empty state offers only Browse the Store). The order is validate → consent → copy → record, so nothing touches the disk before consent and Cancel leaves nothing behind (the original copy → record → consent order is replaced). `installs.chooseFolder()` opens the native picker in main (a path or null). `installs.inspectFolder(path)` runs `validatePackage` over a `DirectorySource`, with no `publisher` or `publishedVersions` options, and answers `{ valid, manifestSummary, problems, warnings }`; problems are listed with their path and their `manifest.<messageKey>` text from the i18n catalogs, warnings are shown too, with Re-check. `installs.installFromFolder(path)` validates again and answers `{ harnessId, version }`, or `package_invalid` when the folder no longer validates, cannot be read, or its Manifest differs from the one inspected (consent always covers what is installed; the screen inspects again), `file_unreadable` with the file's relative path when a listed file cannot be opened while copying, and `harness_running` while that Harness has an active launch. It copies exactly the files of the validated listing (no ignore list, no link followed) into a temp folder under `downloads/`, sets mode 0755 on every declared platform's binary Entry (macOS, Linux), then renames it into `harnesses/<publisher>/<slug>/<version>/`. One version per Harness (`installs` is keyed by Harness ID): the same version is replaced; any other version, higher or lower, switches the row and then deletes the old version folder; a local install over a Store install of the same ID replaces it and becomes `source = 'local'`. Once the row is written the install has succeeded; cleaning up replaced folders is best effort. Leftover temp and replaced folders of an install the app quit or crashed in are restored or deleted before the installer's first install or listing. The Data Directory is created at install when missing (and again at launch), and a reinstall never touches it and keeps `last_launched_at` and `last_workspace`. `consented_permissions` stores the Manifest's `permissions`. Installs run one at a time, and from an install's running check until it is done `launch.start` refuses that Harness with `harness_installing`. Success shows an inline confirmation, "Installed {name} {version} from the folder. It is marked Local in the Library.", with a link to the Library (there is no toast system yet).
- **Consent dialog**: built here as the minimal shared component P0-10 reuses (screens.md, Install consent dialog), shown on every local install: "Install {name} {version}?", the Declared Permissions on the red/yellow/green scale, each with icon, label and sentence (a pure shared module turns permissions into catalog keys, copy from the design demo, for P0-09 and P0-10 to reuse; an explicit `filesystem.scope: paths` counts as high, since a listed path may be `~` or a disk root), a facts row with runtime kind, UI Kind, Workspace and platforms plus the ID, version and Entry, the folder's warnings, a note when this platform is not declared, and the no-sandbox sentence. Install is enabled after 1 s.
- **Library (minimal)**: cards from `installs.list`, most recently launched first, then by name: icon (a `data:` URL read in main, since the renderer's CSP allows only `img-src 'self' data:`), name, Publisher, version, the Local badge, the primary button and an overflow menu. Empty: "Nothing installed yet" with Browse the Store. No sort or filter controls, Uninstall, View in Store or Report (P0-10).
- **Platform**: the current platform is `<process.platform>-<process.arch>` and must be listed in `platforms` for both runtime kinds. A folder that leaves it out still installs; its card shows the disabled "Not available for your platform", and a launch ends `failed(platform_unsupported)`. A binary Entry resolves only when the platform is listed and has an `entry` key; an entry for an undeclared platform is ignored, as in the Manifest.
- **Launch state machine** (decision-encoding snippet):
  ```
  idle → preparing (platform, Entry file, Data Directory, Workspace, token + launches row, log, port) → spawning → [web: waiting-ready → ready] | [terminal: ready]
  preparing | spawning | waiting-ready | ready → stopping (window closed, Cancel, app quit, ready timeout: SIGTERM, 5 s, SIGKILL) → stopped
  any → failed(reason) : spawn_error | ready_timeout | exit_nonzero | platform_unsupported | workspace_cancelled
  exit nobody asked for: code 0 → stopped, else failed(exit_nonzero); an exit after a requested stop → stopped; a ready timeout → failed(ready_timeout)
  ```
  Only one instance per Harness ID (no multiple windows per Harness): `launch.start` while a launch has not ended answers `focused` and brings its window to the front, restoring it when minimized; during `stopping` it does nothing and answers that launch (the card's button is disabled then). When a previous launch's window is still open on its exit, it is closed and the new launch gets a new window.
- **Model check before launch** (follows docs/ux F1, F3 and design-principles §3 instead of the former "warning only, does not block"): when the `default` Slot resolves to nothing through the P0-03 resolver, the card's button reads "Set up a model first" and opens `#/models?harness=<id>`, and `launch.start` refuses with the IPC error `slot_unbound` (`{ slot: 'default' }`) before anything starts. No other Slot is checked. F3's desktop notification for a Slot found unbound during a model call is P0-10.
- **Launch order** (architecture §4): the model check, then the platform, the Entry file (`spawn_error` when missing), the Data Directory (created when missing), the Workspace, the Gateway Token with a `launches` row, the log file, the port (web), the window, the spawn. Failures before the token step get no token and no `launches` row: `platform_unsupported`, `workspace_cancelled` and the model check's refusal; none of them puts an error on the card, which returns to Launch.
- **Entry resolution and Node**: `runtime.kind = node` runs the Entry on Electron's own Node, `process.execPath` with `ELECTRON_RUN_AS_NODE=1` (set only for Node Harnesses); packaged builds keep Electron's RunAsNode fuse on. Electron 45 ships Node 24 while the Manifest still accepts only `runtime.node: "22"`; the Manifest rule stays, and the separately bundled Node LTS under resources is deferred. `binary` runs `entry[platform]` directly with no Node wrapper; a `.cmd` or `.bat` Entry gets no special handling.
- **Environment**: start from the inherited environment, delete keys matching `^(OPENAI|ANTHROPIC|GOOGLE_API|GEMINI|OPENROUTER)_` and `^HARNESS_` (case-insensitive, for Windows; so a stray parent `HARNESS_WORKSPACE` can never appear), then set the contract variables of architecture §4. `HARNESS_GATEWAY_URL` uses the Gateway's actual port; `HARNESS_WORKSPACE` is set only with a Workspace and never empty; `HARNESS_PORT` only for web; a terminal Harness also gets `TERM=xterm-256color`. The environment and the token are never logged.
- **Gateway Token**: issued per launch with the claims P0-02 shipped (`harnessId`, `harnessVersion`, `launchId`, `locale`, `workspace` when there is one) and revoked with `revokeLaunch` on every end state. The Gateway's `getManifest` reads `installs.manifest` and its `resolveBinding` reads the Harness's Model Overrides and Recommended Models on every request (P0-03.5).
- **Port**: bind port 0 on `127.0.0.1` and release it before spawn; the Supervisor claims each offered port synchronously, so a port another running or preparing Harness holds is never handed out twice. The port source is injectable.
- **Workspace** (P0-05.4): a modal sheet in the main window before launch (screens.md, Workspace picker): "Choose a folder for {name}", the last folder preselected or "The last folder no longer exists", Choose folder (`launch.chooseWorkspace(harnessId)`, the native dialog in main, opened at `last_workspace` when that folder exists), "The Harness can read and write files in this folder.", Cancel (launches nothing), Continue, and for `optional` "Continue without a folder". There is no "why this Harness needs a folder" line: the Manifest has no field for it. `launch.lastWorkspace(harnessId)` answers `{ path, exists } | null` for the sheet. `launch.start({ harnessId, workspace?: string | null })` takes the chosen folder; this input is the folder-picker seam. Main checks it again with an async stat (`invalid_input` unless it is an existing absolute folder); null or absent for a `required` Harness ends `failed(workspace_cancelled)`; a `workspace` sent for a `none` Harness is ignored. `last_workspace` is saved whenever a folder is used and never cleared by skipping. Relaunch from a Harness window reuses its launch's Workspace without asking.
- **Spawning**: web Harnesses use `child_process.spawn` with stdin ignored and stdout/stderr piped to the log; terminal Harnesses use node-pty, spawned only once the terminal window reports ready with its fitted columns and rows (nothing is buffered). On macOS and Linux the child leads its own process group (detached, or a pty session) and signals go to `-pid`, so the whole tree stops; when a web Harness exits on its own and members of its group remain, the shutdown sequence stops them. On Windows the graceful stop is `taskkill /T /PID` and the forced stop `taskkill /T /F /PID`.
- **Readiness (web)** (P0-05.3): the window opens at once on its Starting state ("Starting {name}…" with elapsed seconds and Cancel); the Runtime tries a TCP connection to `127.0.0.1:<port>` every 250 ms until one is accepted or `ui.readyTimeoutSeconds` (counted from the spawn) passes. Only `127.0.0.1` is probed, as the Manifest requires Harnesses to bind there; one that binds `localhost` resolving to `::1` times out. Once ready, `http://127.0.0.1:<port><ui.path ?? "/">` loads in the window's content view. On timeout the process is stopped with the shutdown sequence and the launch ends `failed(ready_timeout)` carrying `logTail`, the last 50 log lines kept in memory; the window's overlay shows the timeout message, those lines in a scrolling monospace block, Show logs, Relaunch and Close (F3's separate "did not start in time" dialog is not built). Cancel while starting runs the stop sequence and ends `stopped`.
- **Harness windows**: one renderer page serves both UI Kinds, with its own preload and IPC channel exposing only calls scoped to its launch (info, slots, reload, layout, openLogs, relaunch, close, openModels, terminal ready/input/resize/copy/paste) and its events (its own state, focus, terminal data); main checks that each call comes from that launch's window, and the main window's API is never exposed there. Cancel is a close. Top bar: icon, name, one chip per declared Slot ("Model · {slot}: {model}" or "Not set", from `bindings.resolveAll`, refreshed when the window gains focus, no bindings event; a click opens `#/models?harness=<encodeURIComponent(id)>` in the main window, re-created if it was closed), Reload (web, reloads the page while the process keeps running) and Open logs. Title "{name} — Harness Store", plus the exit code for a terminal after exit. Web content uses the `ui.window` hints (default 1100×760) plus the top bar; terminal windows are 960×640.
- **Web content security**: the Harness's page is a WebContentsView under the top bar with no preload, `sandbox` and `contextIsolation`, in a session partition per Harness, `persist:harness:<publisher>/<slug>`, so a reused port never exposes another Harness's storage (storage still changes with the port on each launch: a known limitation). Every permission request is denied. In `will-navigate`, `will-redirect` (main frame only) and `setWindowOpenHandler` only the exact origin `http://127.0.0.1:<port>` stays in the window, and a same-origin `window.open` navigates the same view; other http(s) URLs, `localhost:<port>` included, go to `shell.openExternal`; every other scheme is blocked. Downloads from the page stay allowed through Electron's default save dialog (there is no `will-download` handler), because the Harness process is unsandboxed anyway and blocking them would break export.
- **Terminal**: node-pty in main (1.2.0-beta.15, whose N-API prebuilds for macOS, Linux and Windows load in both Node and Electron; allowed in the workspace's `allowBuilds`, external to the main bundle, a runtime dependency unpacked from the asar archive when packaged) and xterm.js in the Harness window; data flows over the window's channel and resizes are forwarded. Scrollback 5000 lines; font size fixed at 13 px until P0-11 adds a Settings key. Copy and paste: on macOS the app menu's Edit roles; on Windows and Linux Ctrl+Shift+C/V through xterm's key handler and main's clipboard (a sandboxed preload has none), and terminal windows have no menu bar there so Ctrl+C reaches the pty.
- **Shutdown**: closing a Harness window (or Cancel, or quitting) closes it at once and stops the process in the background, the card showing `stopping`: SIGTERM, then after 5 s SIGKILL when the process or any member of its group remains, then up to 2 s for the exit, after which the launch is recorded as ended either way. Every end revokes the token and writes `launches.ended_at`, `exit_code` and `token_revoked_at`. A process a signal killed is recorded and shown as exit code 128 + the signal number. There is no `launch.stop` and no Stop button: docs/ux show none, and closing the window is the stop.
- **Exit without a request**: the window stays open and readable instead of closing (docs/ux, the demo). A terminal window's top bar shows "Exited with code N" with Relaunch and Close. A web window's overlay shows "{name} stopped unexpectedly" with the exit code (Crashed: a non-zero exit, before or after ready), "{name} has exited" with the code for a code 0 exit, or "{name} could not start", each with Show logs, Relaunch and Close. No error dialog.
- **Launches**: migration `0005_installs_and_launches` adds `installs` (data-model.md plus `source`: `store` | `local`) and `launches` (`launch_id` PK, index on (`harness_id`, `started_at`)); P0-10 adds its own `state`, `store_status` and consent columns later. A `launches` row is written with the token. At startup every row with `ended_at IS NULL` (an app crash) gets `ended_at` and `token_revoked_at` set to now, `exit_code` left NULL.
- **Folders and logs**: the app data root is Electron `userData` (which still honours `HARNESS_STORE_USER_DATA_DIR`); `harnesses/`, `data/`, `logs/<publisher>/<slug>/` and `downloads/` sit directly under it. Each launch logs to `logs/<publisher>/<slug>/<launchId>.log`, never inside the Data Directory, as P0-10 keeps logs after uninstall. One line per output line: `<ISO-8601> [out|err|pty|runtime] <text>`; pty output raw (ANSI codes kept); runtime lines record the spawn and pid, signals sent and the exit. A log is capped at 10 MB, after which one truncation line is written and the rest dropped; each launch start prunes the Harness's logs to the newest 20.
- **Library card states**: preparing, spawning and waiting-ready show "Starting…" (disabled); ready shows "Running…" and "Show window", which both call `launch.start` and so only focus the window; stopping shows "Stopping…" (disabled); idle and stopped show Launch. Failed shows an error line, "Exited with an error" (`exit_nonzero`), "Did not start in time" (`ready_timeout`) or "Could not start" (`spawn_error`), with Show logs and Dismiss (renderer-only state, for the app's session), and the button stays Launch, which retries. The card menu has Model Overrides (the deep link), Show logs and Open data folder (story 16, although docs/ux do not list it; creates the Data Directory when missing); P0-10 adds the rest.
- **Open logs and data folder**: `launch.openLogs(harnessId)` calls `shell.openPath` on the Harness's latest launch's log, else the newest log in its logs folder, else that folder (created); a Harness window's Open logs opens its launch's log. `launch.openDataFolder(harnessId)` opens the Data Directory. Main computes every path from the Harness ID, never from a renderer-supplied path; both answer `not_installed` for a Harness that is not, and `open_failed` with the path when the OS opened nothing. The demo's in-app log viewer is not built.
- **IPC**: `installs.chooseFolder/inspectFolder/installFromFolder/list`; `launch.start({ harnessId, workspace? }) → { outcome: 'started' | 'focused', launchId }`, `launch.chooseWorkspace(harnessId)`, `launch.lastWorkspace(harnessId)`, `launch.status()`, `launch.openLogs(harnessId)`, `launch.openDataFolder(harnessId)`. `launch.status()` returns `{ harnessId, launchId, state, reason?, exitCode?, startedAt, logTail? }[]` (the latest launch of each Harness since the app started), and the `launch.state` event carries the same shape. Events use the shipped dot style: `launch.state`, `installs.changed` and `app.navigate`, sent to the main window only; a Harness window gets its own launch's state on its own channel, never another launch's or install changes. New IPC error codes `package_invalid`, `file_unreadable`, `harness_running`, `harness_installing`, `not_installed` and `open_failed`, each with `error.<code>` in both catalogs; validation problems never travel in an `IpcError`.
- **App quit and the main window**: `before-quit` runs the Supervisor's `stopAll()` (10 s cap), after which launches are refused, before the existing shutdown (Gateway close, then database close). `window-all-closed` still quits the app. The model-indicator deep link, the macOS `activate` event, a second app start and a `harnessstore:` URL re-create the main window when it was closed while Harnesses run.
- **Code placement**: the Supervisor, installer, log writer, port picker and pty wrapper are Electron-free and reach Electron through injected interfaces (`HarnessWindows`, `openPath`, `pickFolder`, `nodeCommand`, the port source); BrowserWindow, WebContentsView, dialog and clipboard code lives in one main-process module, the one the ESLint rule names.

## Testing Decisions

- Seam: **Supervisor seam** (architecture §8, item 3). Real processes, the real readiness probe and real ptys under plain Node (node-pty's prebuilds load there, so the root `pnpm test` runs them on Linux CI without a display); window creation is the `HarnessWindows` interface, faked in tests (a fake terminal window reports ready at once); the folder picker is the `workspace` input; the port source is injectable. Scripts `test:install` and `test:launch` in the desktop package, beside the existing `test:<area>` scripts.
- Fixture Harnesses (`examples/hello-*` stay untouched for P0-06): `fixture-web` (listens on `127.0.0.1:$HARNESS_PORT` at once, echoes its environment, calls the Gateway, exits or hands off to a helper on request), `fixture-term` (prints its environment, cwd and size, reports input, resizes and SIGTERM), `fixture-crash` (exits 3), `fixture-hang` (prints 60 lines, never listens; `readyTimeoutSeconds` 5, the schema's minimum, so the timeout test expects about 5.0–5.6 s), `fixture-hang-on-sigterm` (ignores SIGTERM), `fixture-slow-ready` (listens after 2 s), `fixture-leaves-helper` (leaves a helper in its group that ignores SIGTERM and SIGHUP), `fixture-workspace-required/optional/none`, and `fixture-binary-term`/`fixture-binary-web`, whose Entry is a POSIX `sh` script checked in without the executable bit that execs the test's Node (named in an environment variable the test sets) on the shared fixture script.
- Good tests, as built: "launch fixture-web → ready only after the port accepts, and the page reports the exact env contract"; "`OPENAI_API_KEY` and `HARNESS_WORKSPACE` in the parent env are absent in the child"; "close → SIGTERM received (fixture logs it), the token is rejected by the Gateway with 401 `invalid_token` and the row has `token_revoked_at`", also for `failed(exit_nonzero)` and `spawn_error`; "fixture-hang → failed(ready_timeout) with the last 50 lines"; a second Launch focuses with one process; a helper left in the group is killed; two launches preparing at once get different ports; the Workspace cases (required cancel and chosen, optional chosen and skip, none, last folder reused and gone, Relaunch); install rules (validation problems per rule, a Manifest changed since inspection, version change, same version, local over Store, the executable bit, unreadable files, crash leftovers).
- Gateway integration via the **Gateway HTTP seam**: fixture-web calls the Gateway with its token against the fake Provider and gets a completion; a fixture Harness installed from a folder declares its Slots to `/v1/harness/context`.
- Renderer: jsdom tests of the Publish panel, the consent dialog, the Library cards and menu, the Workspace sheet and the Harness window page (both UI Kinds, every state), in en and zh-CN.
- There is no Electron E2E setup yet, so flows a ticket asked to check with Playwright for Electron are covered through the Supervisor seam and jsdom. That the web content view reaches neither Node nor IPC, denies permissions and sends external links to the browser was checked by hand in Electron 45 on macOS, besides the window-options and navigation-rule unit tests; opening the OS file browser was not checked by hand.
- Platforms: signal, process-group, pty and binary tests ran on macOS and Linux; binary tests skip on Windows. Since P0-13 the Supervisor and installer tests also run on windows-latest in CI, covering `taskkill /T`, ConPTY and the pty pid, which node-pty fills in only once ConPTY connects (the Supervisor reads it at each stop step).

## Out of Scope

- Downloading from the Store, sha256 verification, update flow (P0-10); the full consent dialog design beyond the minimal shared component built here, Uninstall, Library sort, filter and update badges, and the `slot_unbound` desktop notification (P0-10); SDK and example Harnesses (P0-06, they double as manual test subjects); terminal font size from Settings (P0-11); Python runtime (P0.5-01); background Harnesses (P1-08); sandboxing (never in P0).
- Not built from the design demo: several windows per Harness (`ui.instances`), the in-app log viewer, model picking inside the install dialog, desktop shortcuts.

## Further Notes

- Deviations from the requirements as written: R-0503's window opens at once on a Starting state and shows the page when the port is ready; R-0506's window stays open after the process exits on its own, showing the exit code, instead of closing; R-0507's Node is Electron's own (Node 24), not a separately bundled Node LTS 22.
- Windows process-tree termination and pty behaviour are the riskiest parts; P0-13's windows-latest CI job covers them. On Windows the tree cannot be looked up once its root has exited, so helpers a Harness leaves behind may survive there.
- A separately bundled Node adds size per platform (acceptable per ADR-0003) and would close the gap with the Manifest's `runtime.node: "22"`.
