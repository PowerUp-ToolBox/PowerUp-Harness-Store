# P0-13 End-to-end acceptance, CI and unsigned builds

## Problem Statement

Each P0 spec is tested at its own seam, but nothing proves the product promise as a whole: that a new User can go from a fresh install to running a Store Harness on their own model in under ten minutes, and that a Publisher's upload really reaches a User's machine and runs. There is also no continuous integration that runs every seam's tests on each push, and no installable artifact for the three platforms. Without this, "P0 done" cannot be demonstrated.

## Solution

A CI pipeline that runs unit, Gateway conformance, Supervisor, Store (Supabase local) and Playwright-for-Electron smoke tests on every push and pull request, with real-Provider conformance on a nightly schedule; a single end-to-end acceptance journey that exercises sign-in → publish → discover → install → launch → model call through the Gateway → usage visible → uninstall through the app's real screens, with only the services around the app faked (Ollama, GitHub) and a wall-clock budget; a Store-less smoke journey of the same steps on all three OSes; and unsigned distributable builds (macOS dmg, Windows nsis, Linux AppImage), each smoke-run once headless, produced as CI artifacts on the main branch and on tags, with a draft release on tags. A root command runs the same sequence locally, and a maintainer guide (`docs/guides/local-e2e-testing.md`) gives the automated run and the same journey by hand against the local Store. Code signing and notarisation are explicitly deferred.

## User Stories

1. As a maintainer, I want every push to run the full test suite across seams, so that regressions are caught before merge.
2. As a maintainer, I want the CI matrix to include macOS, Windows and Linux runners for the desktop tests, so that platform-specific breakage (paths, pty, executable bits) is caught.
3. As a maintainer, I want the Store tests to run against a Supabase local stack started in CI, so that Edge Functions and RLS are tested for real, not mocked.
4. As a maintainer, I want the Gateway conformance suite to run against the fake Provider on every push and against real Providers on a nightly schedule using secrets, so that adapter drift is caught without making every PR depend on external APIs.
5. As a maintainer, I want one acceptance journey that proves the ten-minute promise, so that the P0 definition of done is a test, not an opinion.
6. As a maintainer, I want the acceptance journey to publish a reference Harness through the real Publish path, so that the Publisher side is covered end to end.
7. As a maintainer, I want the acceptance journey to run with a fake Ollama so it never needs a real model, so that CI is deterministic.
8. As a maintainer, I want the acceptance journey to assert a Usage Record exists after the Harness's model call, so that the Gateway attribution is proven.
9. As a maintainer, I want the acceptance journey to fail if it exceeds the wall-clock budget, so that performance regressions in install or launch are visible.
10. As a maintainer, I want unsigned builds for all three platforms as downloadable CI artifacts, so that I can hand a build to an early tester today.
11. As a maintainer, I want builds on tags to attach artifacts to a GitHub release draft, so that versioned builds are easy to find.
12. As a maintainer, I want each build's Node runtime (in P0 Electron's own Node, see `docs/tech/architecture.md` §4) verified by a smoke launch of the terminal reference Harness, so that "Node Harnesses just run" is true on every platform with no system Node.
13. As a maintainer, I want CI to fail if `en` and `zh-CN` catalogs have missing keys, so that translations never silently regress.
14. As a maintainer, I want lint and type checks to run before tests, so that cheap failures fail fast.
15. As a maintainer, I want flaky-test detection (retry once, report flakiness), so that intermittent failures are visible without blocking.
16. As a maintainer, I want a documented local command that runs the same suite as CI, so that contributors can reproduce failures.
17. As a maintainer, I want a step-by-step guide to run the acceptance journey locally, automated and by hand with my own GitHub account and the admin CLI, so that I can test the whole P0 product myself on a fresh checkout.
18. As an early tester on macOS, I want a note in the release describing how to open an unsigned app, so that Gatekeeper does not look like a broken build.
19. As a Publisher, I want the acceptance journey to double as a living example of the launch contract, so that I can read a real end-to-end script.

## Implementation Decisions

- **CI provider**: GitHub Actions. Workflows: `ci` (on push and PR), `nightly` (real-Provider conformance with repository secrets; schedule and manual dispatch only, never on PRs), `build` (on pushes to main, `v*` tags and manual dispatch; never on PRs).
- **`ci` jobs**: `lint-typecheck` (ubuntu: build, lint, typecheck, then the catalog check). Every other job needs `lint-typecheck` and nothing else, so a lint failure skips them all and they otherwise run in parallel (the job order is read as "lint first", not a serial chain): `unit` (the whole root test suite, Gateway conformance included), `gateway-conformance` (the conformance suite against the fake Provider; its live part skips, since no `ci` job sees a secret), `store-tests` (starts the Supabase CLI local stack, resets and seeds it, serves the Edge Functions, runs the store tests, always stops the stack), `supervisor-tests` (matrix macOS, Windows, ubuntu; the desktop launch and install tests: Supervisor seam, pty, extraction, executable bits, paths), `e2e-smoke` (matrix macOS, Windows, ubuntu; the Store-less Playwright journey) and `acceptance` (ubuntu only; the whole journey on the local stack). Matrices do not fail fast. Each job installs from the lockfile and builds itself, since packages export their build output; the pnpm cache is setup-node's, keyed on the lockfile.
- **Required checks**: "required for merge" is a branch-protection setting no file can set; the root README lists the check names to mark as required (one per matrix OS), never `nightly` or `build`.
- **Nightly**: builds the Gateway and its dependencies and runs the live conformance suite. The repository secrets are named like the variables the suite reads (`CONFORMANCE_ANTHROPIC_API_KEY`, `CONFORMANCE_OPENAI_API_KEY`, `CONFORMANCE_OPENAI_COMPATIBLE_*`; model overrides are repository variables) and reach the conformance step alone, not setup, install or build. A Provider without its secret is skipped, not failed; the job summary names which Providers ran. Not a required check. No test or script reads credentials from a developer's local shell.
- **Catalog check**: a root command runs the existing P0-04 catalog parity test, which fails naming each key missing from `en` or `zh-CN`; only the desktop catalogs are checked, not the examples' inline string tables.
- **Cross-platform**: checkouts keep LF line endings on Windows; the pty screen helpers strip OSC window titles and tolerate ConPTY's re-rendering (cursor-forward for spaces, a dropped blank after the prompt); tests that are inherently POSIX (signals, POSIX-sh binaries, shebang scripts) skip on Windows with a reason.
- **Acceptance journey** (one Playwright-for-Electron test, `@acceptance`): the app is the built, unpackaged app (so `app.isPackaged` is false), on a new temporary profile per attempt (`HARNESS_STORE_USER_DATA_DIR`), with an environment reduced to the OS's own variables (PATH, home, temp, display, session bus) plus the test's, so no shell credential reaches the app or a Harness. Steps: re-seed the Store → start the fake Ollama (the P0-02 fake Provider advertising `qwen3:8b` as an echo, on port 11434) → launch → first-run wizard detects Ollama, the Default Model step picks `qwen3:8b` (the fake also lists its own models first) and binds `default` → Publish screen: Sign in with GitHub as the Publisher `harness-store` (the publisher of `hello-web`'s Harness ID), choose the `hello-web` build folder, publish → Store search "Hello Web" finds it and the journey opens the card whose Publisher is `harness-store` (the seed's `alice/hello-web` has the same name) → Install → consent → launch from the Library → the Harness page sends one message carrying a random nonce → assert the reply is the fake's echo of the nonce, the page reports `ollama/qwen3:8b`, and the test-owned fake recorded exactly one chat completion for `qwen3:8b` → Usage shows Requests 1, one Hello Web row and one "qwen3:8b via <Ollama Connection>" row with 1 request (before uninstall, since afterwards the label falls back to the Harness ID) → uninstall until the Library shows its empty state.
- **Sign-in in the journey**: no app-side backdoor. The test replaces `shell.openExternal` in main to capture the authorize URL, plays the browser against the real Supabase Auth PKCE flow and the store tests' fake GitHub, and delivers the `harnessstore://` callback through the app's `open-url` event, which reaches the same handler on every OS. The only other stand-ins are the OS folder picker (`dialog.showOpenDialog`) and closing the Harness window as its close button would.
- **Store for the journey**: a Playwright setup project, not `globalSetup`, so the smoke project never starts Docker: it stops any running stack keeping its volume, starts it with the fake GitHub's Auth values in the environment (taking precedence over a maintainer's own OAuth app in the Store's local env file), applies migrations, serves the Edge Functions and starts the fake GitHub; a teardown project stops it all. Each attempt re-runs the seed, so a retry can publish 0.1.0 again. After a run, the stack must be started again to use a real OAuth app.
- **Smoke journey** (`@smoke`, the spec's Playwright smoke): the same step helpers without a Store: wizard with the fake Ollama → "Install this folder locally" with `hello-web` → launch → chat → Usage → uninstall. It runs on macOS, Windows and ubuntu.
- **Fake Ollama port**: `E2E_OLLAMA_PORT`, default 11434; a taken port fails the journey with a message naming that variable. When it is not 11434 the test sets `HARNESS_STORE_DEV_OLLAMA_URL`, which the app honours only when unpackaged (a loopback `http` URL, else startup fails) and which moves only the Ollama local-detection target.
- **Budget and logs**: the 10-minute budget is the per-attempt test timeout (app launch to uninstall, the per-attempt seed included); stack startup, image pulls and the Electron binary download (a Playwright `globalSetup`) are outside it. Every step prints its ISO time and the time since the journey began when it starts and ends. Locally each journey takes under 10 s, about 35 s with the stack restart. CI jobs allow 30 minutes for one retry.
- **Linux runners**: Chromium's sandbox stays on (never `--no-sandbox`; Playwright's own default is overridden): the jobs lift Ubuntu 24.04's unprivileged user-namespace restriction and run under a virtual display (`xvfb-run`). For OS encryption the acceptance job runs inside a D-Bus session with an unlocked GNOME Keyring, and the test sets `HARNESS_STORE_DEV_PASSWORD_STORE=gnome-libsecret`, which the app, unpackaged only, applies as Chromium's password store (Playwright's loader would force `basic`, on which the app refuses to keep a session); the journey checks the `safeStorage` backend right after launch.
- **Failure artifacts**: Playwright's `trace` and `screenshot` options do not reach an Electron app, so the journey records its own trace on the app's context; a failed attempt keeps `trace.zip`, a screenshot of the main window, the profile's `logs/` and the Edge Functions log, which CI uploads.
- **Builds**: electron-builder targets dmg arm64 (macos-latest) and x64 (macos-15-intel), nsis x64 (windows-latest) and AppImage x64 (ubuntu-latest), each on its native runner so its smoke runs natively. Unsigned: `CSC_IDENTITY_AUTO_DISCOVERY=false`, macOS `identity: null`, no ad-hoc signing, no notarisation. Artifacts are named `harness-store-<version>-<os>-<arch>.<ext>`; main builds stay version 0.0.0, tag builds take the version from the tag. Each installer is checked to exist and exceed 50 MB, then uploaded per platform. On tags a final job (the only one with `contents: write`) creates a draft GitHub release with the four builds and release notes: macOS right-click Open, Privacy & Security, or removing the quarantine attribute (the reliable way on Apple Silicon); Windows SmartScreen "More info → Run anyway"; Linux `chmod +x` and the P0-07 AppImage sign-in limitation; and that builds point at the local-stack Store default, as no hosted Store exists in P0. The build workflow runs alongside `ci`, not gated on it.
- **Node runtime in builds**: no separate Node LTS binary ships. Node Harnesses run on the app's own executable with `ELECTRON_RUN_AS_NODE` (P0-05, `docs/tech/architecture.md` §4), so no system Node is needed; Electron's RunAsNode fuse stays enabled, and the post-build smoke proves the runtime on every build.
- **node-pty**: no native rebuild; its N-API prebuilds ship for every target arch. "Rebuilt per target arch" is met by packaging and smoke-running each target on its native runner.
- **Post-build smoke**: started by environment variables only: `HARNESS_STORE_SMOKE_HARNESS` (a Harness folder) requests it, and it is refused unless `HARNESS_STORE_SMOKE_PROVIDER_URL` is an `http` URL on a loopback host; no command-line flag, so a `harnessstore:` URL cannot start it. It runs the Electron-free smoke module of the Runtime instead of the app, on a new temporary profile deleted afterwards (a failed deletion is logged and never changes the exit code), with no window, no single-instance lock and no scheme registration, no Store and no stored secret: the real Runtime adds an `ollama` Connection at that URL, binds `default` to `qwen3:8b`, installs the `hello-term` reference Harness from its build folder, launches it in a pty behind headless Harness windows that keep only the terminal output, types one line with a nonce and waits for its echo and exactly one Usage Record. Exit 0 on success, 1 on any failure (with the terminal output and the launch log) or after 120 s. The build job's smoke script starts the fake Provider on an OS-chosen port and runs the unpacked app electron-builder produced (not an installed dmg, nsis or AppImage) with a scrubbed environment, also checks the fake got one chat for `qwen3:8b`, and gives up after 150 s; it runs under `xvfb-run` on Linux.
- **Flakiness**: Playwright retries 1 in CI (0 locally); a summary step lists journeys that passed only on retry (flaky) or failed in the job summary.
- **Local parity**: root `pnpm ci:local` runs the `ci` jobs once on the current OS in workflow order (build once; a `lint-typecheck` failure skips the rest), or only the jobs named. Jobs needing the stack check for Docker first with a clear message, stop any stale stack, give the stack the fake GitHub values, and always stop it at the end (also after Ctrl-C); the full run deletes the local stack's data, which the README says. `CONFORMANCE_*` variables of the shell are never passed on. It uses the installed dependencies (no install). Root `pnpm e2e` builds, then runs both journeys. Root `pnpm test` needs neither Docker nor Playwright.

## Testing Decisions

- **Seams**: this spec sits at the Desktop E2E seam (architecture §8, item 5) and orchestrates all lower seams in CI; it adds no new seams. The post-build smoke's module also runs under Node in the Supervisor tests (a passing run, a missing and a broken Node runtime, a stalled Provider, an unserved model, ConPTY-style output, a profile removal that throws), so all three OSes run it in `supervisor-tests`.
- **Good tests** here are journeys phrased entirely in User-visible terms (screens, buttons, text) with assertions on observable outcomes (window opened, text shown, Usage row visible); no reaching into internal state. The fake Provider's request log is the test's own fixture, not the app's state.
- **Fixtures**: seeded Store (re-seeded per attempt), the P0-02 fake Provider as Ollama, reference Harnesses from P0-06 (`hello-web` for the journeys, `hello-term` for the post-build smoke), the fake GitHub of the P0-07 store tests behind the real Supabase Auth flow.
- **Repo checks**: the workflows have contract tests (triggers, job graph, `needs`, matrices, secrets only on the nightly conformance step, no `continue-on-error`, the sandbox kept, unsigned builds, the release job's permissions, the README's required-check names, `ci:local` parity with `ci` and its credential filter); in-page links in the READMEs and guides must point at a heading.
- **Not automated, left as steps of the manual guide**: the P0-09 browse journey (home → search → detail → Publisher → back), the P0-10 update journey and Open data folder / Show logs opening real OS paths, the P0-11 language switch, and the P0-12 launch of an install after a Takedown.
- **Verified only by CI**: everything off macOS arm64: the Windows and Linux Supervisor, smoke and post-build smoke runs (ConPTY, `taskkill`, profile cleanup), the Linux sandbox and keyring backend, the macOS x64, Windows and Linux builds, and the draft release.
- **Prior art**: the smoke tests introduced by P0-04, P0-08 and P0-10.

## Out of Scope

- Code signing, notarisation, auto-update of the desktop app itself, and store submission (deferred by the product owner; tracked on the roadmap under "before public launch").
- A separately bundled Node LTS binary, and a hosted Store URL in builds.
- Registering the `harnessstore:` scheme for a bare AppImage (no `.desktop` file at first run, no deb target).
- Performance benchmarking beyond the wall-clock budget.
- Real-Provider tests on PRs.

## Further Notes

- The acceptance journey is the P0 definition of done from `docs/product/prd.md`; keep it green and keep it honest (no shortcuts that bypass real screens).
- The manual guide (`docs/guides/local-e2e-testing.md`, linked from the root and docs READMEs) covers prerequisites, the automated run, a GitHub OAuth app for the local Store through the Store's gitignored local env file (callback on the local Auth), the Store URL check in Settings → Advanced, publishing copies of the reference Harnesses under the maintainer's own login (editing the copied Manifest's Harness ID), a Connection, install, launch, Usage, update, uninstall, Report, a Takedown with the admin CLI after marking the account as admin, the deferred journeys above, and troubleshooting (keychain prompt, ports 11434 and 54321–54324, profile logs, resetting the local database, the sign-in callback on macOS dev builds, and that a temporary profile breaks the sign-in callback on Windows and Linux).
- Deviations from #81: the job order is "lint first, then in parallel"; required checks are documented, not set; `ci:local` does not run `pnpm install`.
- Deviations from #82: the acceptance journey runs on ubuntu only, not macOS too, because GitHub's macOS runners have no Docker for the Supabase stack (macOS, Windows and ubuntu run the smoke journey); the stubbed OAuth session is the real PKCE flow against the fake GitHub, not an injected session; the Store starts in a setup project, not `globalSetup`; the CLI's environment-over-env-file precedence was verified on one CLI version only; the deferred journeys above stay manual.
- Deviations from #83: no separate bundled Node (Electron's own Node, fuse kept); no node-pty rebuild (N-API prebuilds, native runners); `build` is not gated on `ci`; the smoke runs the unpacked app, not the installers; builds keep the local Store default; the AppImage sign-in limitation stays documented; Linux's executable is `harness-store`.
