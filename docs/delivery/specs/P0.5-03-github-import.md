## Problem Statement

In P0 the only way to publish is to pick a local folder. Publishers who develop in the open already have a tagged release on GitHub; making them build a folder locally, then pick it in the app, is duplicate work and disconnects the listing from its source. Users, meanwhile, have no reliable way to see the source behind a Harness they are about to trust with their machine.

## Solution

The Publish page accepts a GitHub reference of the form `owner/repo@tag` (optionally with a subdirectory). The **desktop client** downloads the tag's archive from GitHub, extracts the referenced directory, runs the same Manifest and package validation as the folder flow, and then uploads through the same publish path. The Store records the source repository and tag, and the detail page shows a "Source" link to that exact tag. No server-side fetching, no webhooks, no background jobs: this is a client-side shortcut onto the existing pipeline.

## User Stories

1. As a Publisher, I want to type `owner/repo@v1.2.0` on the Publish page and publish from it, so that my GitHub release and my Store listing are the same artifact.
2. As a Publisher, I want to specify a subdirectory (`owner/repo@v1.2.0:packages/my-harness`) for monorepos, so that I do not need a separate repository per Harness.
3. As a Publisher, I want the client to tell me immediately if the tag does not exist or the repository is not reachable, so that I can fix the reference before waiting on a download.
4. As a Publisher, I want to import from a private repository using my existing GitHub sign-in when it has access, so that I can publish Harnesses whose source is not public.
5. As a Publisher, I want the same validation problems list I get from the folder flow, so that there is one mental model for what a valid package is.
6. As a Publisher, I want the Manifest's `sourceRepo` to be filled in automatically (or checked for consistency if I already set it), so that the listing points at the right place.
7. As a Publisher, I want the publish confirmation to show the resolved commit SHA for the tag, so that I can be sure which code I published.
8. As a Publisher, I want a warning if the tag name and the Manifest `version` disagree (e.g. `v1.2.0` vs `1.3.0`), so that I do not publish mismatched metadata by accident.
9. As a Publisher, I want the client to remember my last import reference so that publishing the next version means changing only the tag.
10. As a Publisher, I want a `.harnessignore`-style exclusion to be respected the same way as in the folder flow, so that development files do not end up in the package.
11. As a Publisher, I want large repositories to show download progress and be cancellable, so that a mistake does not tie up the app.
12. As a Publisher, I want the import to fail clearly if the archive exceeds package limits, before uploading, so that I do not waste time.
13. As a User, I want the detail page to show "Source: owner/repo @ v1.2.0" linking to the tag, so that I can review the code before installing.
14. As a User, I want to see when a listing has no linked source, so that I can weigh that in my trust decision.
15. As a Store administrator, I want the source reference stored per Harness Version, so that a Report can be checked against the exact code that was published.
16. As a platform developer, I want the import to reuse the folder flow's validation and upload steps unchanged, so that there is one publish pipeline to maintain.

## Implementation Decisions

- Reference grammar: `owner/repo@ref[:subdir]`. `ref` must be a tag (branches are rejected with a message explaining that only immutable references are allowed). The client resolves the tag to a commit SHA via the GitHub API before downloading.
- Download uses the GitHub archive endpoint for the resolved SHA (not the tag name), so the imported bytes are pinned to the commit shown to the Publisher.
- Authentication: unauthenticated for public repositories; for private ones the client uses the Publisher's GitHub OAuth token from the Store sign-in, which requires adding the `repo` read scope as an **incremental** consent step only when a private import is attempted.
- The extracted directory is treated exactly as a picked folder: the same validation entry point, the same metadata form, the same upload function. The only additions are pre-filling `sourceRepo` and passing `source_ref` metadata (`owner/repo`, tag, SHA) to the publish function.
- Store changes: `harness_versions` gains nullable `source_repo`, `source_ref`, `source_sha` columns; the detail page reads them. No new tables.
- Version/tag mismatch is a warning, not an error, because tag conventions vary.
- Package limits, exclusions and the no-symlink/no-absolute-path rules are enforced by the shared package validation from P0-01, unchanged.

## Testing Decisions

- Tests observe the publish result and the validation problems, not GitHub API internals.
- Primary seam: the Publish flow's validation and upload path exercised through the **Store seam** (architecture §8, item 4) with GitHub replaced by a local HTTP fixture serving tag metadata and archives, including cases: valid public tag, missing tag, branch reference, subdirectory, oversize archive, version/tag mismatch, private repository requiring scope upgrade.
- **Manifest validation seam** already covers the package rules; add one fixture proving an imported archive with a nested top-level folder (GitHub's archive layout) validates correctly after normalisation.
- One **Desktop E2E** journey: import a fixture reference, publish, open the detail page, see the Source link.
- Prior art: P0-08 Publish flow tests.

## Out of Scope

- Server-side fetching, webhooks or auto-publishing on tag push (P1-09).
- Building or compiling inside the import (the tag must already contain the runnable package, including `node_modules` for Node Harnesses; the guide explains release-branch or release-asset patterns).
- Importing from GitLab or other forges.
- Verifying that the Publisher owns the repository; source is informational, ownership is the GitHub login in the Harness ID.

## Further Notes

Because Node Harnesses must ship dependencies inside the package, many Publishers will tag a build artifact rather than raw source. The authoring guide should recommend a `release/` branch or a CI job that commits the built output to the tag, and note that P1-09 will add release-asset support.
