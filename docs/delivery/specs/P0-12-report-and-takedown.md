# P0-12 Report and Takedown

## Problem Statement

Harness Store runs third-party code without a sandbox and publishes listings without pre-review. The only enforcement in P0 is reactive: Users must be able to flag a harmful or misleading Harness, an administrator must be able to remove it, and Users who already installed it must be warned. Without this loop the listing policy in `docs/tech/security.md` is unenforceable.

## Solution

A Report dialog reachable from the detail page's footer and from a Store install's Library card menu (flow F8 in `docs/ux/flows.md`), submitted anonymously through IPC to the Store's `report` function; a minimal administrator path to list and dismiss Reports and to take down a version or a whole Harness through the `admin/takedown` function, all from a small admin CLI in the Store app (no admin UI in P0); and client behaviour for an installed Harness that was taken down: it is gone from Store discovery, shows a red warning in the Library and on its detail page, has no Update, and stays launchable after a one-time confirmation. When only the installed version was taken down, the update check learns it from an extended `latest_versions`, and the install shows the same warning and confirmation naming that version while Update to a newer published version stays offered. `docs/tech/api.md` gives the IPC calls, the update check's RPC and the CLI's Store calls, `docs/tech/data-model.md` the settings keys and the `installs` columns, and `docs/ux/screens.md` the dialog, the warning and their copy.

## User Stories

1. As a User, I want a Report link on every detail page of a Harness the Store has, so that I can flag a Harness where I found it.
2. As a User, I want to report a Store install from the Library card menu too, so that I can flag a Harness that misbehaved after install.
3. As a User, I want to choose a reason (malicious behaviour, bypasses the Model Gateway, broken, inappropriate content, spam, other; a misleading listing goes under other), so that reviewers can prioritise.
4. As a User, I want a free-text details field with a sensible limit and an optional contact email, so that I can describe what happened and be reached.
5. As a User, I want to submit without an account, and anonymously even when signed in, so that reporting has no barrier.
6. As a User, I want the report to include the Harness version and my platform and app version automatically, so that I do not have to look them up.
7. As a User, I want to see everything that is sent besides what I typed before I submit, and nothing else to be sent, so that reporting feels safe.
8. As a User, I want a confirmation after submitting, so that I know it went through.
9. As a User, I want repeated reports of the same Harness from my install to be gently rate-limited, so that the system is not abusable while I am not punished for a double click.
10. As a User, I want an offline or server error to be shown with Retry and my text preserved, so that I do not have to retype.
11. As a User who installed a Harness that was later taken down, whole or only the version I installed, I want a clear red warning on its Library card and detail page, so that I can decide whether to keep using it.
12. As a User, I want a taken-down Harness to remain launchable after I confirm once, so that the platform does not delete my tools remotely.
13. As a User, I want a taken-down Harness to have Update hidden and to never reappear in Store lists or search, so that removal is complete on the discovery side.
14. As a Store administrator, I want to list Reports, or only open ones, grouped by Harness with counts per reason and the latest details, so that I can triage.
15. As a Store administrator, I want to take down a single version or a whole Harness with a note, so that I can respond proportionately.
16. As a Store administrator, I want takedown to resolve the related open Reports, so that the queue stays clean.
17. As a Store administrator, I want to dismiss a Report as unfounded with a note, so that the queue reflects decisions.
18. As a Store administrator, I want takedowns to be logged with who did it and when, so that actions are auditable.
19. As a Publisher, I want a taken-down status visible on my own Harness list with the administrator's note, so that I know what happened and can appeal by email.
20. As a security reviewer, I want reports and takedowns to be impossible to perform through direct table writes with the anon key or a Publisher JWT, so that the only path is the validated function.
21. As a Store administrator, I want the CLI usable in under a minute from a fresh checkout with secrets only in my shell's environment, so that I can respond fast without leaking keys.

## Implementation Decisions

### Report (#79)

- **Entry points**: the detail page's footer, on both the Store-backed page and the page built from an installed Manifest; and a Library card menu item Report, before Uninstall. Report is offered only where the Store knows the Harness: hidden for a local install (the Store may answer `404`) and absent from the "no longer available" page.
- **Reason**: the six `report_reason` values `malware`, `bypasses_gateway`, `broken`, `inappropriate`, `spam`, `other`, already identical in the Store, api.md, data-model.md and docs/ux, so the `report` function, its migration and its tests are unchanged. Labels follow screens.md (Malicious behaviour / 恶意行为, Bypasses the Model Gateway / 绕过 Model Gateway, …), not the ticket's example wording. Nothing is preselected; Submit waits for a reason. No seventh value for a misleading listing: it is Other.
- **Details and contact email**: details is optional free text; the contact email is its own optional input, as docs/ux shows it, with a loose `x@y` check of at most 254 characters. Main puts a trimmed email first in `details` as `Contact: <email>`, a blank line, then the details (no separate column in P0); blank details with no email leave `details` out. The combined text is at most 2000 characters: the textarea's counter shows what is left (or how many too many), and main refuses longer with `invalid_input`.
- **Version**: the installed version from a Library card; from the detail page, the version in the page's header (the Store's latest, or the installed Manifest's on a page built from the install). An unknown version is left out, so the Report covers the whole Harness ("All versions").
- **Client info**: main builds `client_info` itself and the renderer never supplies it: `install_id`, `platform` (`<process.platform>-<process.arch>`, the Manifest platform string on a supported machine, always sent) and `app_version` (the app's version). Nothing else is sent: no paths, machine IDs or account. `install_id` is a random UUID made the first time a Report needs it and kept in the main-only settings key `install_id`, which `settings.get` never answers.
- **Disclosure**: the dialog reads `store.reportInfo` (a Harness ID → `{ installId, platform, appVersion, rateLimited }`, no Store request) each time it opens and shows, before Submit, one line naming what else is sent (Harness ID, version, platform, app version, a random install ID) with those values, and "No IP address or account is stored". If that read fails, the dialog shows the error with only Close.
- **Submission**: IPC `store.report` (`{ harnessId, version, reason, details, contactEmail }`) posts to the `report` function at the configured Store URL with the anon key as `apikey` and bearer, whoever is signed in, so the Report is anonymous. Answers: `201` a toast "Thanks, a reviewer will look at this." and the dialog closes; `429` (the Store's or the local limit) the rate-limited state; `400` `invalid_input`; `404` `not_found`; no answer within 15 s `store_unreachable`, with connectivity checked again; anything else `store_error`. Every error except `429` keeps all input and turns Submit into Retry; Submit is not disabled while offline.
- **Client-side rate limit**: at most 3 Reports of one Harness per install in 24 hours. The main-only settings key `report_history` maps Harness ID to the ISO times of Reports the Store took (`201` only), pruned of entries older than 24 hours on every write. `store.reportInfo` answers `rateLimited`, and the dialog then shows "You've already reported this Harness recently" without calling `store.report`; main checks again (Reports in flight counting) and answers `rate_limited` with no request. The Store's `429` shows the same state, not the publish-worded rate-limit error, but without the "up to 3 times in 24 hours" hint, since the Store's limit is per IP address or install across Harnesses; focus moves to Close. Server-side limits stay as api.md states them.

### Takedown (#80)

- **Schema**: no Store migration for the administrator side. `admin_actions` (RLS shutting out anon and authenticated), `harness_versions.takedown_note`, the Publisher read policy on their own versions and `report_reason` already exist from P0-07.6; the ticket's "introduced by this ticket" follows the older plan. One Store migration extends the update check (below).
- **`admin/takedown`** is unchanged: it sets the version or the whole Harness to `taken_down`, copies the note to `takedown_note`, resolves Reports and appends one `admin_actions` row. A version Takedown resolves every open Report on the Harness, not only those on that version, as api.md states normatively; this is the reading of "every open report for that target".
- **Admin CLI** in the Store app, run from the administrator's machine after a build of the Store and the packages it imports, as a package script. Commands:
  - `reports list [--open]`: service-role PostgREST reads of `reports` embedding the Harness ID and version, newest first, every status or only `open`; grouped by Harness with the count and the count per reason, the latest Report's details, then one line per Report (ID, time, version or "all versions", reason, status, the first 120 characters of its details). Control characters and bidi overrides in Report text are printed escaped. It reads a page of 1000 at a time by keyset on (`created_at`, `id`) until an empty page, because PostgREST's `max_rows` cuts a single answer short without saying so; this replaces the planned single read. No JSON output.
  - `reports dismiss <id> --note "..."`: the ID must be a UUID and the note 1 to 2000 characters, not blank. A service-role update of that `open` Report to `dismissed` with `resolution_note` and `resolved_at`; zero rows is "No open Report <id>". The Harness is untouched and nothing is written to `admin_actions`, whose actions are Takedowns only.
  - `takedown <harness_id> [--version <v>] --note "..."`: calls `admin/takedown` with the service-role key as `apikey` and, as bearer, a 5-minute HS256 session JWT the CLI mints for the profile named by `STORE_ADMIN_LOGIN` after checking its `is_admin` with the service role (GitHub OAuth is the only sign-in, so there is no other quick way to get an admin JWT). It prints the Harness, whether a version or the whole Harness was taken down, and the number of resolved Reports.
- **CLI secrets**: `STORE_URL` and `STORE_SERVICE_ROLE_KEY` for every command, plus `STORE_JWT_SECRET` (the project's HS256 JWT secret) and `STORE_ADMIN_LOGIN` for `takedown`, read from the environment only, never committed and never printed; a missing one is named. Exit codes: 0 done, 1 the Store refused or did not answer (status, the API's code and message only), 2 a usage error or a missing variable.
- **Discovery**: no client or Store code. RLS already hides a taken-down Harness or version from the Store home rows, `search_harnesses` and the Publisher page, which store tests prove through those exact reads.
- **Publisher visibility**: already built by P0-08 (My Harnesses shows the taken-down status and the note).
- **Client warning**: the only source is the install's `storeStatus` and `installedVersionTakenDown` from P0-10's update check, on both the Library card and the detail page; the detail page's live Store status keeps its existing meaning (the neutral note). For `taken_down` a red warning, "A Store administrator took this Harness down. It may be harmful: launch it only if you trust it." / "该 Harness 已被商店管理员下架，可能有害。仅在你信任它时启动。", replaces the neutral "No longer available in the Store", which Unpublished installs keep.
- **Installed version taken down**: the Store migration `latest_versions_installed_version` replaces `latest_versions(harness_ids)` with `latest_versions(harness_ids text[], installed_versions text[] default null)`: the same rows plus `installed_version_status` (`published`, `unpublished`, `taken_down`, or null when not asked or unknown) of the version at the same position, the arrays of equal length or `400`, still at most 1000 IDs, never the takedown note; called with `harness_ids` alone it answers as before (the new column null), so the detail page and My Harnesses are unchanged. The update check sends each Store install's version and stores the answer in the new `installs.installed_version_taken_down` column (desktop migration `0010`; `InstalledHarness.installedVersionTakenDown`), kept apart from `store_status` so a Takedown of only the installed version leaves the Harness `available` and its newer published version offered as Update, the remedy. The install then shows the same red warning in place of any neutral note, naming the version ("A Store administrator took down the installed version, {version}. …" / "已安装的版本 {version} 已被商店管理员下架，……"), and the same once-per-Takedown confirmation ("The installed version, {version}, was removed from the Store. Launch anyway?" / "已安装的版本 {version} 已从商店移除。仍要启动吗？"); a whole-Harness Takedown wins when both are. The column goes back to 0 when a check finds the version otherwise and when another version is installed (an update) or a local install replaces the row; an answer about a version the install has since left is not applied to it.
- **Update hidden**: no new code; the update check stores no available version unless the Harness's status is `available`. A Takedown of only the installed version keeps Update.
- **Launch confirmation**: the shared Launch action (Library card and detail page) first asks "This Harness was removed from the Store. Launch anyway?" with the warning, Cancel and "Launch anyway"; only "Launch anyway" records it, through the new IPC `installs.acknowledgeTakedown` (a Harness ID → null, emitting `installs.changed`), in the new `installs.takedown_acknowledged` column (desktop migration `0009`). `InstalledHarness` gains `takedownAcknowledged`. It is asked once per Takedown across restarts: the update check resets it whenever `store_status` or `installed_version_taken_down` changes, and an install of another version or a local install replacing the row resets it too. Show window of a running Harness, a Harness window's Relaunch and main's `launch.start` are not gated.
- **Copy** in `en` and `zh-CN` for every new string, listed in screens.md (下架 for taken down, 撤下 for Unpublish).

## Testing Decisions

- **Store seams** (local stack, the CI store job, not root `pnpm test`): the existing `report` tests already cover the anon PostgREST insert refused, the row stored with its reason and no IP, and the 6th Report from one install within an hour refused; the per-IP counter has unit tests. New: the admin CLI against the stack: `reports list` with and without `--open`, past 1000 Reports sharing one `created_at`; `dismiss` (note, `resolved_at`, Harness and `admin_actions` untouched, a second dismiss refused); `takedown` of a version and of a whole Harness (statuses, `takedown_note`, resolved Reports, exactly one `admin_actions` row naming the administrator); a non-admin or unknown login refused; function errors; no secret ever printed; after each kind of Takedown the Store home rows, `search_harnesses` and the Publisher page no longer show it. The takedown tests add anon, other-Publisher and owner `PATCH` of `harness_versions.status` refused by RLS. `latest_versions` with `installed_versions`: a version taken down while the Harness stays active answers `installed_version_status` `taken_down` with `store_status` `available` and the newer latest, and no takedown note; each position's status, null where none or no such version was given; `taken_down` with no published version left; arrays of unequal length refused; the one-argument call unchanged.
- **Store unit** (no Docker): the CLI's argument and environment parsing, output layout and escaping, the minted JWT, exit codes, and paging against a fake PostgREST capping answers at 1000 and 400 rows.
- **Desktop main seams** over IPC with real SQLite against a fake Store on a real HTTP port: the exact Report request and headers, the stable install ID kept out of `settings.get`, the 4th Report blocked with no request (after a restart and for concurrent calls too), the 24-hour window and pruning, each answer's mapping, an unreachable Store then Retry, refused inputs; `taken_down` from the update check marks the install, drops the update, the Store's download refuses it while the old version stays and launches; the acknowledgement persists, survives a check with the same status and resets on a new one; the check sends the installed version, a Takedown of only that version marks the install while Update to a newer version stays offered and the Harness still launches, updating clears the mark and the acknowledgement, and reinstating the version clears it. Update-check unit tests: the installed versions sent aligned with the IDs, the mark stored apart from the Store status, an unknown installed version status skipped, an answer about a version since left not applied.
- **Renderer** component tests in jsdom in `en` and `zh-CN`: both Report entry points and the client info per context, reason required, the counter and email check, a failed submit keeping input and Retry succeeding, the local limit with no `store.report` call and its hint, the Store's `429` without the hint and with focus kept, the failed client-info read; the warning on the card and the detail page, Cancel and Escape recording nothing, "Launch anyway" acknowledging then launching, no question once acknowledged, for an Unpublished install or for Show window; for a Takedown of only the installed version, the warning naming it on the card and the detail page with Update kept, in place of the neutral note too, the confirmation once, and a whole-Harness Takedown winning over it.
- **Not built here**: Desktop E2E (an existing install still launching after a Takedown in the real app) is left to P0-13.
- **Fixtures**: the seed is unchanged; store tests create their own open Reports and administrator with the service role. No real credentials.
- **Prior art**: P0-07 store tests; P0-10's update-check tests.

## Out of Scope

- Web admin dashboard and Publisher analytics (P1-05).
- Automated scanning (P1-07).
- Appeals workflow beyond an email address in the takedown note.
- Ratings and reviews (P1-04).
- JSON output from the admin CLI; logging dismissals in `admin_actions`.

## Further Notes

- Even though enforcement is reactive, response time matters: the admin CLI is usable in under a minute from a fresh checkout, documented in the Store app README. The README builds with the Store's workspace dependencies included, since the Store's own build alone fails on a fresh clone without the Manifest package's build output.
- Deviations from #79: the contact email is a separate input rather than typed into details; reason labels follow screens.md; Report is not offered for local installs or the "no longer available" page; the dialog shows the install ID too.
- Deviations from #80: no `admin_actions` or `takedown_note` migration (P0-07.6 added them); a version Takedown resolves every open Report on the Harness; a Takedown of only the installed version reaches it through an extended `latest_versions` (a follow-up of #80) and keeps Update, unlike a whole-Harness Takedown; `reports list` pages its reads; the Installer E2E part of How to verify 4 is deferred to P0-13.
