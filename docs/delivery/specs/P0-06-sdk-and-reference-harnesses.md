# P0-06 Harness SDK and reference Harnesses

## Problem Statement

The launch contract and Gateway protocol are documented, but a Publisher starting from a blank folder still has to read three documents, get environment variables right and handle `slot_unbound` themselves. The Store also needs its first listings, and the test suites need realistic Harnesses. Without a tiny SDK and two complete examples, the first Publishers will make the same mistakes and the platform will launch with an empty Store.

## Solution

`@harness-store/sdk` for Node: a few functions that read the launch environment, hand back the official OpenAI client pointed at the Gateway, wrap the Gateway's own endpoints with plain `fetch`, expose Slot constants and typed Gateway errors including `SlotUnboundError`. Two reference Harnesses built with it, `harness-store/hello-web` (UI Kind web) and `harness-store/hello-term` (UI Kind terminal), each built into a self-contained, publishable Harness folder, localized, and run end to end through the real Runtime in tests. Plus an authoring guide, in English and zh-CN, that walks a Publisher from an empty folder to a Store-ready Harness.

## User Stories

1. As a Publisher, I want to install one package and call one function to get an OpenAI client that already talks to the Gateway, so that my first model call is three lines.
2. As a Publisher, I want `getContext()` to give me Harness ID, version, Data Directory, Workspace, locale, platform and port as typed values, so that I never parse environment variables.
3. As a Publisher, I want a clear exception when I run outside Harness Store (missing environment), naming the missing variables and telling me to use "Install this folder locally", so that I am not confused by connection errors.
4. As a Publisher, I want a `SlotUnboundError` I can recognise and render as "please bind a model in Harness Store", so that Users get an actionable message.
5. As a Publisher, I want helpers to list my Slots and their current bindings, so that I can show which model is active.
6. As a Publisher, I want a helper to build a `http.Server` bound to `HARNESS_PORT` on loopback, so that web Harnesses do not get the host/port wrong.
7. As a Publisher, I want the SDK to work with plain `fetch` too (a `gatewayFetch` that adds the token), so that I am not forced to use the OpenAI SDK.
8. As a Publisher, I want streaming examples in the guide, so that I copy a working pattern.
9. As a Publisher, I want a starter template I can copy (`hello-web`), so that I start from a passing baseline.
10. As a Publisher, I want the examples to show how to bundle the Entry and its dependencies into one file, so that no `node_modules` is shipped and my package validates and installs fast.
11. As a Publisher, I want the examples to show reading `HARNESS_LOCALE` and shipping en/zh-CN strings, so that my Harness fits the app's language.
12. As a Publisher, I want the examples to show `workspace: optional` handling, so that I know how to behave with and without a folder.
13. As a Publisher, I want the guide to explain Slots and Recommended Models with a worked example, so that I declare requirements correctly.
14. As a Publisher, I want the guide to state plainly what the platform does not do (no sandbox, no credential access, no fallback), so that I design accordingly.
15. As a User, I want two working Harnesses in the Store on day one, so that I can try the platform immediately.
16. As a User, I want `hello-web` to show a simple chat page that uses my bound model and displays which model answered, so that I can verify my setup.
17. As a User, I want `hello-term` to run a short interactive loop in the terminal window, so that I see the terminal UI Kind works.
18. As a developer, I want the examples installed and launched through the real Runtime in tests (and by P0-13's E2E journeys), so that they cannot rot.
19. As a developer, I want the SDK to have no runtime dependency on Electron or the Gateway package, so that it is a small pure-Node library.
20. As a developer, I want the SDK versioned independently and published to npm later, so that Publishers can depend on it.

## Implementation Decisions

- **SDK API** (decision-encoding snippet, as built):
  ```ts
  getContext(): HarnessContext              // { harnessId, harnessVersion, dataDir, workspace?, locale: 'en' | 'zh-CN', platform: string, port? }
  createOpenAIClient(opts?): OpenAI         // official client; baseURL + apiKey from env; maxRetries 0 unless opts set it
  gatewayFetch(path, init?): Promise<Response>
  listSlots(): Promise<SlotInfo[]>          // GET /v1/models → { name, resolvedModel: string | null }[], Manifest order
  getGatewayContext(): Promise<GatewayContext> // GET /v1/harness/context, wire field names
  createServer(handler): http.Server        // listen(HARNESS_PORT, '127.0.0.1'), returned synchronously
  Slots = { default: 'default', fast: 'fast', smart: 'smart' } as const
  class NotInHarnessStoreError extends Error { missing: string[] }
  class GatewayError extends Error { status: number; code: string; slot?: string }
  class SlotUnboundError extends GatewayError { code: 'slot_unbound'; slot: string; static from(err): SlotUnboundError | undefined }
  isSlotUnbound(err): boolean
  ```
- **Environment**: every function reads `process.env` at call time, never at module load. `getContext()` throws `NotInHarnessStoreError` naming every missing or empty variable of the seven the Runtime always sets (`HARNESS_GATEWAY_URL`, `HARNESS_GATEWAY_TOKEN`, `HARNESS_ID`, `HARNESS_VERSION`, `HARNESS_DATA_DIR`, `HARNESS_LOCALE`, `HARNESS_PLATFORM`); its message points at "Install this folder locally" on the Publish screen (the label docs/ux show, not "Install from folder"). An unrecognised locale reads as `en`; `platform` is a plain string; a `HARNESS_PORT` that is not an integer from 1 to 65535 throws a plain `Error`.
- **Chat completions** go only through the client `createOpenAIClient()` returns; there is no separate chat helper. `openai` (^7.45.1) is the SDK's only runtime dependency; everything else uses plain `fetch`. Retries default to 0, applied after the caller's options so an explicit `maxRetries: undefined` still means none, because the OpenAI SDK's default retries on 409 and 5xx would repeat a `slot_unbound` and write several Usage Records for one `provider_error`.
- **`gatewayFetch`**: the path is relative to `HARNESS_GATEWAY_URL`, which already ends in `/v1` (`gatewayFetch('/models')` calls `<base>/models`); slashes are joined without doubling and `/v1` is not special-cased. The Gateway Token replaces any `Authorization` header the caller set; other headers are kept. The `Response` comes back untouched whatever its status. It is async, so missing variables reject rather than throw.
- **Errors**: `listSlots()` and `getGatewayContext()` throw `GatewayError` on any non-2xx, with the Gateway's error code, or `unknown` when the body carries none. `isSlotUnbound(err)` checks the shape, never `instanceof` on OpenAI classes: true for a `SlotUnboundError` or any object with `status === 409` whose `code` or `error.code` is `slot_unbound`. `SlotUnboundError.from(err)` turns such an OpenAI SDK error into the typed error, `slot` taken from `err.error.slot`.
- **`createServer`**: reads only `HARNESS_PORT`; listen errors arrive as `'error'` events on the returned server. Without `HARNESS_PORT` it throws a plain `Error` saying the Harness is not UI Kind `web`. The SDK adds no Host or CSRF checks (those are the Harness's, see hello-web).
- **SDK types and packaging**: the `/v1/harness/context` types are defined locally, so the SDK has no dependency on `@harness-store/manifest`; `@harness-store/gateway` and `@harness-store/manifest` are dev dependencies only, for integration tests. ESM only, version 0.1.0, private until an npm pipeline exists. It runs on the Node Harnesses run on: on macOS and Linux Electron's Node, via `ELECTRON_RUN_AS_NODE`; on Windows the `node.exe` of the same Node version that the app ships (architecture §4).
- **The Harness folder is a build output**: an example's source folder is not installable (`DirectorySource` lists everything, and `src/` plus pnpm's symlinked `node_modules` would fail validation; the Publish flow does not exclude them either). Each example's `build` runs `tsc --build` first (kept for repo checks), then bundles the Entry with rolldown (1.2.11, already locked, no install script; ESM, platform node, target node22, one unminified file without sourcemap) into `dist/index.mjs`, and copies `manifest.json`, `README.md` and `assets/` beside it in the example's `out/` folder (gitignored). `out/` is what is validated, installed and zipped, and what P0-13's "Publish `examples/hello-web`" means. The `.mjs` extension makes the format independent of any `package.json`; the Manifest's `entry` is `dist/index.mjs`. The root build's topological order builds the SDK and the Manifest package (both dev dependencies of each example) first, so the `harness-manifest` bin exists.
- **Pack**: `pnpm --filter <example> run pack` (plain `pnpm pack` is pnpm's tarball command) zips `out/` with fflate into the example's `dist/<slug>-<version>.zip`, deterministically (sorted entries, 1980-01-01 timestamps). It applies the Publish flow's exclusion list (`.git/`, `node_modules/.cache/`, `.DS_Store`, `Thumbs.db`, `*.swp`) but not `.harnessignore`; `build` filters `assets/` with the same list, so `out/` and its zip always agree. Each example carries its own build and pack scripts so a copied example stays self-contained.
- **Shared Manifest choices**: IDs `harness-store/hello-web` and `harness-store/hello-term`, version 0.1.0 (the example's `package.json` version matches), names "Hello Web" / "Hello Term", the demo's summaries, `tags: ["education"]`, MIT, `sourceRepo` pointing at the example's directory, all six platforms, `runtime: { kind: node, node: "22" }`, every Declared Permission at its most restrictive value. One Model Slot, `default` ("Writes chat replies" / "Answers in the terminal"), `requirements: { tools: false }`, no Recommended Models (the guide shows those with a separate worked example; the demo's `fast` Slot is not built). One `README.md` per example is both the Store description and the package README, written for Users first. `assets/` holds only a 512×512 `icon.png` (initials in the demo colours: HW on #0F766E, HT on #33363C) and `screenshot-1.png`, a real session against the fake Provider, both rendered once on macOS; any other file there would count as a screenshot.
- **hello-web**: UI Kind web with `ui: { "kind": "web" }` (default path and ready timeout), `workspace: none`. `createServer()` serves `GET /` (one HTML string with inline CSS and script, nothing resolved at runtime since the cwd is the Data Directory, no request off its own origin) and `POST /chat`; any other route, including an unparsable request-target, is 404. The page posts to its own backend, never to the Gateway (gateway-protocol.md §1), and never sees the Gateway Token or URL. `/chat` takes `{ messages: [{ role, content }] }` (the page keeps the history, the server holds none), answers 403 unless Host is `127.0.0.1:<port>` or `localhost:<port>` and 415 unless the body is `application/json` (blocks cross-site and DNS-rebinding callers; not authentication), 413 above 1 MB, 400 for a body that is not a conversation, and otherwise always `200 text/event-stream` with `token { text }`, then `done { model }` (the resolved `provider/model`) or `error { code, message }`; the page localizes errors by code, `slot_unbound` as "bind a model on the Models page of Harness Store". When the page disconnects the server aborts the Gateway call with an `AbortController`. `GET /` sends a Content-Security-Policy with `default-src 'self'` and `connect-src 'self'`, inline script and style only. The page reads the stream with `fetch` and a body reader (EventSource cannot POST), disables Send while an answer streams, shows "Answered by <provider/model>", and drops an unanswered message from the history. The server writes `HARNESS_LOCALE` into `<html lang>`; both string tables and the en/zh-CN Language menu are client-side, and the choice is not saved. Stable ids `#message`, `#send`, `#reply` and `#model` are for P0-13.
- **hello-term**: UI Kind terminal, `workspace: optional`. A readline loop that streams each answer from `default`, keeps the conversation in memory for the session, and works with a pty or piped stdin. The banner is "Hello Term <version>", then the Workspace path when there is one, then a hint, in en or zh-CN from `HARNESS_LOCALE`; `/model` (prints `<slot> → <provider/model>` per declared Slot, or a localized "unbound" with where to bind one) and `/quit` stay English. `/quit`, Ctrl-C at the prompt and end of input all exit 0 (piped lines already read are still answered). A `slot_unbound` or other Gateway error prints a localized message and the loop continues; `NotInHarnessStoreError` at startup prints its message and exits 1. On exit the window stays open in its exited state (architecture.md §4, docs/ux), so a `/quit` ends the launch `stopped` with code 0; the Runtime does not close the window.
- **Guide**: `docs/guides/authoring-harnesses.md` and its Simplified Chinese twin `docs/guides/authoring-harnesses.zh-CN.md` (user-facing product docs are bilingual), each linking to the other and both linked from the docs map. The two are kept in sync: the same sections in the same order, the zh-CN terms from the fixed glossary in docs/ux/design-principles.md §5, and every code block byte-identical; a change to one lands in the other in the same commit. Nine sections: what a Harness is, folder layout (source folder apart from the built Harness folder), the Manifest field by field on both examples' Manifests quoted exactly, the launch contract table reproduced verbatim from architecture.md §4 (including `OPENAI_BASE_URL` and `OPENAI_API_KEY`) and linked as normative, SDK usage with streaming and a web server snippet (Host check first on every request, JSON-only bodies on routes that act, `connect-src 'self'`), Model Slots and Recommended Models with a worked example, what the platform does not do (one sentence each for no sandboxing, no access to real credentials, no automatic Provider fallback), testing locally with "Install this folder locally", and publishing (links to flows.md F5 and the P0-08 spec only). It builds a small terminal Harness, First Harness (`alice/first-harness`), along the way; until the SDK and Manifest packages are on npm it builds them from a checkout and installs `pnpm pack` tarballs. It says "Publisher", never "author".
- **Publishing**: the two examples are published under the `harness-store` Publisher account as the first Store listings and marked Featured (P0-08/P0-09). With GitHub sign-in, that needs a GitHub account named `harness-store`.

## Testing Decisions

- SDK: unit tests with a stubbed launch environment for `getContext` parsing and errors, the error shapes and `isSlotUnbound`/`SlotUnboundError.from`, `createServer`'s bind address and `EADDRINUSE`, and `maxRetries` (including an explicit `undefined`); integration tests of the client, `listSlots`, `getGatewayContext` and `gatewayFetch` against a real in-process Gateway whose `ollama` Connection points at the fake Provider (no real keys). A package test asserts `openai` is the only runtime dependency and that sources import nothing else but `node:` built-ins. The built SDK was smoke-run once under Electron's Node (24) on macOS.
- Guide: every ```ts block is byte for byte a type-checked, linted file in the SDK's tests, asserted both ways; each snippet runs as a module against a real Gateway with the fake Provider bound to `default` (context print and the not-in-Harness-Store exit, a chat answer and its resolved model, First Harness streaming from piped stdin, unbound Slots, `listSlots`, and the web snippet's page, locale, CSP, streamed answer, Host and Content-Type refusals, split multi-byte bodies and dropped uploads). Every Manifest in the guide validates with no problems or warnings, the examples' Manifests are quoted exactly, the nine headings and the three "does not do" sentences are pinned, and the guide's install-time trust claim is checked against the consent dialog's strings. The zh-CN twin has the same headings at each level and the same fenced code blocks, byte for byte and in order, and the two link to each other. Shell commands and the build script were checked once by following the guide literally in a scratch folder (not committed).
- Examples: package tests run `validatePackage` and the `harness-manifest validate` CLI on `out/` and on the zip, asserting zero problems and zero warnings; `out/` holds exactly the five expected files with no strays (also when `assets/` holds some); the Entry imports only `node:` built-ins; the zip is byte-identical across runs with every entry dated 1980-01-01; a copy of `out/` outside the repository runs without `node_modules` (no launch environment → exit 1 naming "Install this folder locally"; hello-web serves its page in the given locale without the token; hello-term answers several piped lines in order against a stub Gateway). Model round trips otherwise live only in the desktop end-to-end test.
- End to end through the **Supervisor seam** (the reference-Harness launch test in the desktop app, beside the terminal launch tests): the real Runtime installs each `out/` through `installs.installFromFolder` and launches it with a real Gateway whose `default` Slot is bound as the Default Model to the `ollama` Connection to the fake Provider (`model-a` → `fake/echo`). hello-term runs in a real pty (node-pty under the test's Node): streamed answer, `/model` printing `default → ollama/model-a`, `/quit` ending `stopped` with exit code 0 and the window left open, zh-CN, the Workspace line, history with Ctrl-C, and a Slot unbound mid-session. hello-web: the page is shown only once the port answers; driven in jsdom with its fetch going to the real server, a message streams into `#reply`, `#model` reads `ollama/model-a` and the page requested only its own `/chat`; zh-CN, the localized `slot_unbound` and the menu; a Provider message with `$` patterns shown as written; raw `/chat` events, no token or Gateway URL in any response, 403/415/400/413/404 never reaching the Gateway, both Host forms, malformed request-targets answered 404 with the launch still ready, and the Provider call aborted when the client leaves. "Resolved model equal to the fake Provider id" means the bound `provider/model` the Gateway reports (`ollama/model-a`). A Usage Record has no launch id, so "attributable to its launch" means exactly one new `usage_records` row with this Harness ID, slot `default`, status `ok`, timestamped inside the launch's `started_at`..`ended_at`; no column was added. The test fails with "run `pnpm build`" when `out/` is missing, never skips, and the desktop app takes no dependency on the examples.
- No headless browser (Playwright is P0-13): hello-web's no-off-origin-request guarantee is the CSP header plus the jsdom request log and the token/URL absence checks.
- Platforms: everything above, including the pty paths, ran on macOS only; Windows and Linux runs come with CI. The icon and screenshot rendering and the "How to verify" direct runs (bundle under Node with a hand-set launch environment, `curl -N` on `/chat`) were run once from a scratch folder and are not committed.

## Out of Scope

- Python SDK (P0.5-02); npm publication pipeline (later); a declarative "chat runtime" Harness (not planned for P0); Store listing mechanics (P0-08/P0-09); installing the packed zip (P0-05 installs folders only, zip installs are P0-10); the demo's `fast` Slot, multiple windows per Harness and other demo-only features.

## Further Notes

- The SDK is intentionally tiny; resist adding agent-loop helpers, which would recreate ADR-0001's rejected direction.
- Deviations from the tickets as written: `SlotUnboundError` extends `GatewayError` (still an `Error`); rolldown instead of esbuild; the end-to-end test installs `out/`, not the zip, which is checked by the validators instead; `/quit` leaves hello-term's window open in its exited state rather than the Runtime closing it; the CSP replaces the headless-browser network check; the hello-web `error` event's message is the server's English text, localized by code in the page; the guide uses "Install this folder locally" for "Install from folder".
- hello-web's `GET /` serves only a static page with nothing private, so it skips the Host check the guide recommends on every request; `/chat` does both checks.
