# P0-07 Store backend (Supabase schema, auth, storage, edge functions)

## Problem Statement

Publishers have nowhere to put a Harness where other people can find it, and Users have nowhere to get one from. Without a hosted Store there is no catalogue, no immutable Harness Versions, no Publisher identity behind a Harness ID, and no download counts. Everything downstream (publishing, browsing, installing, reporting) needs a backend that validates what it accepts with the same rules the desktop app uses, keeps packages private until requested, and never learns anything about a User's models or conversations.

## Solution

A Supabase project (Auth, Postgres, Storage, Edge Functions) that is the single source of truth for Harnesses, Harness Versions, Publishers, Reports and download counts, as specified in `docs/tech/data-model.md` and `docs/tech/api.md`. Reads go through PostgREST under row-level security; every write goes through an Edge Function that authenticates the caller, validates with the shared Manifest package, and enforces immutability and ownership. GitHub OAuth is the only sign-in and only Publishers ever sign in. Packages live in a private bucket and are handed out through short-lived signed URLs by a `download` function that also records the download. A local development stack with seed data lets every other P0 spec be built and tested without touching production.

## User Stories

1. As a Publisher, I want to sign in with GitHub, so that my GitHub login becomes the publisher segment of my Harness IDs without any extra identity setup.
2. As a Publisher, I want my profile (login, display name, avatar) created automatically on first sign-in, so that I can publish immediately.
3. As a Publisher, I want to upload a Harness Package and have the Store validate it with exactly the rules the desktop app applied, so that a package that passed locally never fails server-side for a different reason.
4. As a Publisher, I want the Store to reject a package whose `id` publisher segment is not my login, so that nobody can publish under my name and I cannot accidentally publish under someone else's.
5. As a Publisher, I want the Store to reject a version that is not greater than every version I already published, so that version history is monotonic.
6. As a Publisher, I want a published Harness Version to be immutable, so that Users who installed it can trust that what they reviewed is what they run.
7. As a Publisher, I want to Unpublish a version, so that I can withdraw a bad release without breaking existing installs.
8. As a Publisher, I want the Store to keep serving my Harness's previous published version after I Unpublish the latest, so that Unpublishing is not a takedown.
9. As a Publisher, I want a clear structured error (field path, code, message) when my package is rejected, so that I can fix it without guessing.
10. As a Publisher, I want a rate limit that stops runaway scripts from publishing hundreds of versions a day, so that a mistake in my CI does not flood the Store.
11. As a User, I want to browse and search the Store without an account, so that I am never asked to sign up just to look.
12. As a User, I want to download a Harness Package without an account, so that installing has no registration wall.
13. As a User, I want the Store to only ever show me active Harnesses and published versions, so that unpublished or taken-down content never appears in lists, search or detail pages.
14. As a User, I want the download endpoint to give me the checksum and size along with the URL, so that my app can verify integrity before unpacking.
15. As a User, I want the download endpoint to refuse a platform the version does not support, so that I do not download something that cannot run.
16. As a User, I want the download endpoint to resolve "latest published version" for me when I do not name one, so that install and update logic on the client stays simple.
17. As a User, I want my downloads counted without my identity or IP being stored, so that Publishers get numbers and I keep my privacy.
18. As a User, I want to report a Harness anonymously, so that I do not need an account to flag something harmful.
19. As a User, I want repeated reports from the same source rate-limited, so that the reports queue is not spammable.
20. As a Store administrator, I want to take down a version or a whole Harness, so that harmful content disappears from lists, search and download immediately.
21. As a Store administrator, I want takedown to resolve the related open Reports, so that the queue reflects reality.
22. As a Store administrator, I want to mark a Harness as Featured with an explicit rank, so that the Store home can show a curated row.
23. As a Store administrator, I want RLS to prevent any anon or Publisher key from writing to catalogue tables directly, so that the only write path is a validated Edge Function.
24. As a developer on the desktop app, I want a `search_harnesses` RPC that returns ranked results with everything a list card needs, so that the client does not join tables itself.
25. As a developer on the desktop app, I want a `latest_versions` RPC that returns, for a batch of installed Harness IDs, the latest published version plus its Manifest (permissions, runtime and Entry), so that the client can decide whether an update needs re-consent without downloading the package.
26. As a developer, I want a Supabase local stack with migrations and seed data (at least three Harnesses with published versions, one Unpublished version, one Featured), so that every downstream spec has realistic data to develop and test against.
27. As a developer, I want the Edge Functions to import the shared Manifest package rather than reimplementing validation, so that the rules cannot drift.
28. As a developer, I want the Store to return a consistent `{ error: { code, message } }` shape and documented HTTP statuses, so that the client can map errors to translated UI copy by code.
29. As a security reviewer, I want packages in a private bucket and assets in a public read-only bucket, so that only the intended files are ever publicly reachable.
30. As a security reviewer, I want signed download URLs to expire quickly, so that a leaked URL is worthless within a minute.

## Implementation Decisions

- **Tables, enums, triggers and buckets** are exactly those in `docs/tech/data-model.md` §1. Migrations are checked into the Store app (`apps/store/supabase/migrations`) and applied with the Supabase CLI (the pinned `supabase` devDependency of `apps/store`); there is no manual schema editing. `harnesses.harness_id` and `harnesses.search` are maintained by triggers, not generated columns: a generated column cannot read another table (`profiles`, `harness_versions`).
- **Profile creation**: a trigger on new auth users (and on Auth writing their app metadata) inserts a `profiles` row with `github_login` taken from the OAuth identity (`user_name`), lower-cased, only when `raw_app_meta_data->>'provider' = 'github'`, which users cannot set. Email signup is off, so nobody can claim a login through signup metadata. If the login changes on GitHub, the profile keeps the original login in P0 (Harness IDs must stay stable); a later phase may handle renames.
- **Sign-in (P0-07.2)**: Supabase Auth's GitHub provider with PKCE, run by the desktop app's Runtime (`apps/desktop/src/main/runtime/store-auth.ts`, Electron-free, plain `fetch` to Auth and PostgREST rather than supabase-js) and opened in the User's default browser with `shell.openExternal`, never in an app window. Auth redirects to the custom scheme `harnessstore://auth-callback` (in config.toml's `additional_redirect_urls`); the app registers it with `app.setAsDefaultProtocolClient` (and `protocols` in electron-builder.yml for packaged builds) and receives it through `open-url` on macOS and the `second-instance` arguments on Windows and Linux, under the existing single-instance lock. The PKCE verifier lives only in memory; a callback with no sign-in waiting is ignored; a sign-in times out after 5 minutes and is replaced by a newer one or by sign-out. The session (access and refresh token, expiry, user id and the last profile read; never GitHub's `provider_token`) is stored only through the P0-03.1 `SecretCipher` (`safeStorage`) in the `secrets` row `store:session`, and sign-in is refused with `encryption_unavailable` before the browser opens when the OS offers no encryption. The access token is refreshed lazily within 60 s of expiry (an expiry computed from Auth's `expires_in` on the local clock, not its absolute `expires_at`, so a skewed clock does not matter) and the rotated session re-encrypted, also while a newer sign-in is still waiting for its browser (the stored session changes only when that sign-in stores its own); a refused refresh deletes the session and emits `auth.changed` with `reason: session_expired`. Sign-out deletes the session at once and then revokes it at the Store, first refreshing an access token that has expired (Auth's logout needs a valid one). A session the OS cannot decrypt right now (a locked keychain, a denied prompt) counts as signed out but is kept for the next launch; a 401 from a Store call ends the session only while the token it used is still the stored one (`sessionRejected(accessToken)`). IPC: `auth.signIn`, `auth.signOut`, `auth.whoami` and the `auth.changed` event (api.md). The app's Store anon key is a constant next to `DEFAULT_STORE_BASE_URL` holding the local stack's (public) anon key, replaced at build time by `HARNESS_STORE_ANON_KEY`. The GitHub client id, secret and provider URL come from `env(...)` in config.toml; `supabase/.env.example` (committed) holds dummy values pointing at the fake GitHub of the tests, which `pnpm db:start` (scripts/supabase.ts) and CI use for any variable not set in the environment or in the gitignored `supabase/.env`.
- **Immutability**: an UPDATE trigger on `harness_versions` raises an error if any column other than `status`, `download_count`, `unpublished_at` and (P0-07.6) `takedown_note` changes, whatever the row's status (rows are only ever inserted as published), and lets `status` only move forward (`published` → `unpublished`, any → `taken_down`). The trigger holds for the service role too. DELETE is denied to everyone except the service role in a migration: anon and authenticated have no DELETE privilege and no policy.
- **Denormalisation**: `refresh_harness(id)`, called by an `after insert` and an `after update of status` trigger on `harness_versions` (so it holds whoever writes), recomputes on `harnesses`: `latest_version` (highest published version by `semver_key`, ties by latest `published_at`), `latest_published_at`, `name`, `summary`, `tags`, `icon_path`, `search` (from that version), and `download_count` (sum of versions). A Harness with no published version keeps `status = active` and its last listing fields but has `latest_version = null` and `latest_published_at = null`, and RLS hides it everywhere. It locks the Harness row before reading the versions, so concurrent writers of different versions of one Harness cannot leave a stale latest version or download count.
- **Semver ordering** uses a stored (generated) `bigint[]` key `[major, minor, patch, prereleaseFlag]` where a pre-release sorts below the same release; comparison "greater than all published versions" includes Unpublished and taken-down versions so a withdrawn version number can never be reused. The authoritative check is validatePackage's `publishedVersions` option (full semver, pre-release included), so client and server agree. Because every publish is greater than all earlier versions, publish order is semver order, and ties between pre-releases of one MAJOR.MINOR.PATCH (same key) are broken by `published_at`. An insert whose key sorts below an existing version is refused by a trigger as a backstop.
- **Search** (P0-07.5) is the `search_harnesses(q, tags, platform, limit, offset)` RPC: Postgres full-text over the `search` column (maintained by `refresh_harness`, not generated) using `websearch_to_tsquery('simple', q)` (language-neutral, so a word in any language is one exact, unstemmed token), ranked by `ts_rank` then `download_count` desc then the latest version's `published_at` (`latest_published_at`) desc, then `harness_id`. An empty query (null, blank, or one with no word in it) returns most downloaded. Tag filter is an array containment (all given tags; null or empty is no filter); platform filter checks the latest version's `platforms` (an unknown platform matches nothing). Page size default 24, `limit` clamped to 1…60 and a negative `offset` to 0, never refused. It returns `harness_id, publisher_login, name, summary, icon_path, tags, platforms, download_count, latest_version, latest_published_at` (a composite type: `RETURNS TABLE` would clash with the `tags` argument) and no total count. `icon_path` replaces api.md's former `icon_url`: the database does not know the Store's public URL, so the client prefixes it. It is `SECURITY INVOKER`, so the RLS rule that hides taken-down and Unpublished-only Harnesses is the only visibility filter, as for every other read; the desktop app calls it with the anon key. The `simple` parser does not segment Chinese: a whole Chinese name or word matches, a part of one does not (substring search in Chinese is not supported in P0); Manifest tags are a closed English list, translated by the client. The home rows (Featured, Most downloaded, New; 12 each) and the Publisher page are plain PostgREST reads listed in api.md, with no filter of their own (RLS again), served by the existing indexes on `featured_rank` (unique), `download_count` and `latest_published_at`.
- **RLS**: anon and authenticated roles can SELECT `harnesses` where `status = active and latest_version is not null` (one rule that hides taken-down and Unpublished-only Harnesses from every read), `harness_versions` where `status = published` and the parent is active, and the public columns of `profiles` (column privileges; `is_admin` is not readable). Publishers can UPDATE their own `profiles` row, and only `display_name`, `bio` and `avatar_url` (column privileges plus the owner policy), so they cannot set `is_admin` or `github_login`. A Publisher (authenticated) also reads every version of their own Harnesses in any status, `takedown_note` included (P0-07.6; P0-08's "My Harnesses" and P0-12 use it), through `private.own_harness_ids()`, a `SECURITY DEFINER` helper in a schema PostgREST does not expose (a subquery on `harnesses` would itself be hidden by that table's RLS). There is deliberately no owner policy on `harnesses`: the home rows, search and Publisher page repeat no visibility filter, so it would show a Publisher their own hidden Harnesses whenever those are read with their session (P0-07.5's tests guard this). No INSERT/UPDATE/DELETE privilege or policy on catalogue tables for any JWT role; the functions use the service role. Internal SQL functions have EXECUTE revoked from `public`, `anon` and `authenticated`, so PostgREST does not expose them as RPCs. Admins are recognised by `profiles.is_admin = true` looked up inside functions (not by a JWT claim, to keep P0 simple).
- **Edge Function contracts** follow `docs/tech/api.md`. Additional pinned behaviours:
  - `publish` (P0-07.3) refuses a Content-Length over 500 MB plus 64 KB of multipart framing (`413`) or none (`411`) before reading the body, then reads the zip into memory (an Edge Function has no disk to stream to), opens it with `ArchiveSource.open(bytes)` (bounded, #113) and runs `validatePackage()` with `publisher` and `publishedVersions` (every version of the Harness, any status). validatePackage's archive rules (500 MB, 20 000 files, symbolic links, absolute paths, `..` segments) run on the zip's listing before any file content is read; the function adds no rule of its own. The status comes from all the problems: 413 (`archive_too_large`, `archive_too_many_files`), else 422 `invalid_manifest`, else 403 `publisher_mismatch`, else 409 `version_not_greater`, each with the full `problems[]`. It then reads in full the icon, the screenshots it keeps (at most five, the first in package path order, skipping any over 2 MB: validatePackage only warns about more or larger ones, and the detail page shows up to five) and README.md, which checks their CRC-32 and size where validatePackage reads only a prefix or nothing: an unreadable one is 422 `invalid_manifest` with an `archive_invalid.entry` problem at its path, and an icon over 5 MiB (the `harness-assets` limit per object) is 413 `package_too_large`, both before any upload. Auth failing to answer `getUser` is a 500, never a 401, so the desktop app does not end the session. On success it uploads the package first, then assets, never overwriting an object (one already there is another publish of that version: 409, and it is not deleted), then `publish_version()` inserts the rows in one transaction; on any failure after the first upload it deletes the objects that request uploaded, and only those. The changelog is the Manifest's `changelog` (no `metadata` part), and the answer's `url` is the in-app route `/store/h/<publisher>/<slug>`. The `@harness-store/manifest` main entry is bundled into `supabase/functions/_shared/manifest.js` by `pnpm build` (Vite, gitignored), since a function sees only the files under supabase/functions; supabase-js comes from a pinned `npm:` specifier in `supabase/functions/deno.json`.
  - `publish` rate limit: 20 publishes per Publisher per rolling 24 h, counted from `harness_versions.published_at` whatever the version's status (`publishes_remaining()`), checked before the body is read and again by `publish_version()`. That SQL function (service role only) takes a per-Publisher advisory lock, re-counts, and refuses with `version_not_greater` when the number of versions of the Harness changed since the function read them for validatePackage, so concurrent publishes cannot pass the rate limit or the version check together.
  - **Known limitations (`publish`)**: the 500 MB package limit is above the memory and request size a hosted Edge Function allows, so publishing a package near that size fails there (the upload path is not redesigned in P0). The gateway buffers a request body, and the local edge runtime passes a response on only after the whole body, so the Content-Length refusal reaches the client only once the body has been sent; it still keeps the function from reading it. A package object left by a crash between upload and commit blocks that version number until removed by hand; so does one kept because `publish_version()` failed without an answer from PostgREST (a lost connection, a gateway timeout), whose transaction may still commit: deleting the objects then could leave a published version without its package.
  - `download` (P0-07.4) needs only the anon key and reads no `Authorization` header. It checks the body (`platform` one of the Manifest schema's platforms, `app_version` 1 to 64 characters: else `400 invalid_request`), resolves the version (the named one, else the Harness's `latest_version`; an unknown, taken-down or Unpublished-only Harness, or a named version that is not published, is `404 not_found`), refuses a platform the version does not declare with `422 platform_not_supported` before making a URL, signs a 60-second URL on the Store's public origin (`STORE_PUBLIC_URL`, since `SUPABASE_URL` inside the local edge runtime is the gateway's Docker-network address), and then `record_download()` (SQL, service role only) inserts the `download_events` row and increments `harness_versions.download_count` and `harnesses.download_count` in one transaction, re-checking under the row locks that the version is still published and its Harness visible (else `404`, nothing counted). It returns `{ url, sha256, size, manifest }`, the full Manifest so the client can render the consent dialog before unpacking. That Manifest is the stored `jsonb`, whose key order and whitespace differ from the package's `manifest.json`: P0-10 compares the two by deep equality, not bytes (the SHA-256 guards the package). `DOWNLOAD_URL_TTL_SECONDS` can only shorten the 60 s; the local stack sets it to 5 s in `supabase/functions/.env` for the expiry test, a deployed Store never sets it.
  - `latest_versions(harness_ids text[])` (P0-07.4) is an RPC for anon: one row per requested ID, in input order, at most 1000, shaped `{ harness_id, store_status: available | unpublished | taken_down | not_found, latest_version, manifest }`. `manifest` is the full stored Manifest of the latest published version (what `diffForReconsent` takes: permissions, runtime, Entry, and the changelog), and both it and `latest_version` are null unless `available`, so an Unpublished-only or taken-down Harness never looks installable. It is `SECURITY DEFINER` with a fixed `search_path` (RLS would hide the Harnesses whose status it reports). It reports the Harness's status only: no version-level Takedown is surfaced in P0, not even one of the latest version, which moves `latest_version` back to the previous published version (`available`, possibly lower than the installed version) or leaves none (`unpublished`); the takedown note is never public.
  - `unpublish` (P0-07.6) needs the owning Publisher's JWT; `unpublish_version()` (SQL, service role only) checks in one transaction: unknown Harness or version `404`, another Publisher's Harness `403 forbidden`, a taken-down Harness or version `409 harness_taken_down` (status unchanged), else sets `unpublished`. It is idempotent: unpublishing an already-unpublished version returns success. It answers `{ harness_id, version, status: 'unpublished', latest_version }`; the status trigger moves `latest_version` back, or to null (the Harness stays `active` but hidden).
  - `report` (P0-07.6) accepts anonymous calls (a valid Publisher JWT is recorded as `reporter_id`; anything else is anonymous, never a `401`). `reason` is one of the six `report_reason` values of data-model.md (P0-12's user story lists a "misleading listing" reason the enum does not have: data-model.md wins); `details` at most 2000 characters; `client_info` is reduced to `{ install_id, app_version, platform }`. The Harness may be in any status (unknown, or an unknown version of it, is `404`). Rate limit 5 per hour per IP using an in-memory counter per function worker (the first `X-Forwarded-For` address, spoofable, never stored; config.toml keeps workers with `policy = "per_worker"`) plus the table check in `submit_report()`: 5 per hour per `client_info.install_id` against the stored Reports, serialised by an advisory lock per install id, so it is exact for a client that sends its install id. Not perfectly strict by design: a client can change its address and install id. There is no anon INSERT policy on `reports`.
  - `admin/takedown` (P0-07.6) is served by one function named `admin` (a function's name cannot hold a `/`), routing on the path. It requires an authenticated caller with `profiles.is_admin`, looked up by the function (`403 forbidden` otherwise; `take_down()` checks again inside its transaction) and a `note` of 1 to 2000 characters. Without `version` it sets every version not yet taken down to `taken_down` and then the Harness; with `version` only that version. `take_down()` first takes `publish_version()`'s per-Publisher advisory lock, so a publish in flight cannot leave a version published under a taken-down Harness. The note is copied to `harness_versions.takedown_note` on every version it changes. It sets `status = resolved` with `resolution_note = note` and `resolved_at` on every open Report of the Harness, and writes one `admin_actions` row (`takedown_harness` or `takedown_version`) per call, also when it was already taken down. It answers `{ harness_id, version, status: 'taken_down', resolved_reports }`. The "admins all" access to `reports` of the data model is not a policy: administrators use Studio and service-role paths, and `admin_actions` has RLS on with no policy.
  - **Known limitations (`report`, `admin/takedown`)**: `latest_versions` reports a Harness-level status only, so a version-level Takedown of an older installed version is not surfaced to the desktop app in P0. The in-memory per-IP counter is per worker and lost when a worker stops.
- **Featured** is set by administrators directly in the database (Supabase Studio) in P0; no function. `featured_rank` unique among non-null values.
- **Storage paths**: `harness-packages/<publisher>/<slug>/<version>.zip`; `harness-assets/<publisher>/<slug>/<version>/icon.png` and `.../screenshots/<n>.<ext>` (`n`: 0-based index in package path order; `ext`: the original extension, lower-cased). Stored paths are relative to their bucket, without the bucket prefix. Asset bucket is public read, no listing. The buckets are created by a migration: `harness-packages` 500 MiB per object and `application/zip` only, `harness-assets` 5 MiB per object and `image/png` and `image/jpeg` only.
- **Environment**: functions read the Store's own service key from function secrets; nothing Provider-related exists anywhere in the Store.
- **Local development**: `supabase start` plus a seed script that publishes the two reference Harnesses from P0-06 (when available; until then, fixture packages from P0-01) and one synthetic third Harness, marks one Featured, and Unpublishes one version, so lists, detail pages and update checks all have data. Built in P0-07.1 as a Node script (`apps/store/scripts/seed.ts`; SQL cannot upload to Storage) that zips the P0-01 fixtures, validates each with validatePackage and writes rows and objects with the service role: three visible Harnesses (one Featured, one with a Chinese name under a second login, one whose newest version is Unpublished), one Unpublished-only Harness and one taken down, with download counts. It wipes the catalogue and both buckets first, so it is idempotent. `pnpm db:reset` runs it after `supabase db reset`.

## Testing Decisions

- **Seam**: the Store seam (architecture §8, item 4): run the Supabase local stack and exercise Edge Functions and PostgREST over HTTP. Tests never call internal function helpers; they observe HTTP responses and subsequent HTTP reads.
- **Good tests** assert externally visible behaviour: a publish with a mismatched publisher segment returns 403 with code `publisher_mismatch` and no rows appear; a second publish with an equal version returns 409; after Unpublish the detail read no longer lists that version but the previous one is `latest_version`; a sixth Report within an hour from one IP address and install is `429`; a takedown resolves the open Reports and writes exactly one `admin_actions` row; only the owning Publisher reads the takedown note; a download for an unsupported platform returns 4xx and does not increment counters; an anon UPDATE against `harnesses` via PostgREST is rejected; a signed URL fetched after its lifetime (5 s on the local stack, 60 s deployed; see Download tests) fails.
- **Sign-in tests**: real GitHub OAuth cannot run in CI, so the GitHub provider's `url` points at a fake GitHub (`test-store/fake-github-server.mjs`: token exchange and the GitHub Enterprise user API) that the store test starts in a container on the stack's Docker network (reusing the Storage image, which ships Node), reachable by Auth as `http://fake-github:8080` on every OS. The store test drives the desktop app's own auth module through the real Auth: a scripted browser follows the redirects and consents on the fake GitHub, the module exchanges the code, and the test checks the session against Auth, exactly one `profiles` row with the lower-cased login, a restart on the stored ciphertext, a refresh and a sign-out that revokes the refresh token. The desktop's Docker-free tests cover the same module against a fake Auth at the HTTP seam (PKCE check, callback errors, timeout, replacement, encryption refusal, refresh and expiry), and a restart on a real SQLite file over IPC.
- **Fixtures**: fixture packages from P0-01 (valid, each failure class, oversized, zip-slip); the publish tests zip the fixture folders with the test Publisher's Harness ID and compare each refusal's `problems[]` with what validatePackage reports locally for the same bytes and options. "Oversized" is a zip of 20 000 extra empty files (`archive_too_many_files`): no test uploads 500 MB, and the Content-Length rule is a unit test (`test/publish.test.ts`), since no response gets past the gateway or the local edge runtime before the whole body has. A test GitHub identity is simulated by creating auth users directly with the service role and minting JWTs, so tests do not hit GitHub.
- **Download tests** (`test-store/download.test.ts`) call `download` and `latest_versions` with the anon key against the seed catalogue, and re-run the seed afterwards (they change its counters). The signed URL's expiry is watched with the local stack's 5-second lifetime (`DOWNLOAD_URL_TTL_SECONDS` in `supabase/functions/.env`): the test reads `iat` and `exp` from the URL's token, fetches it at once (200) and again after `exp` plus a 2-second margin (400). That the deployed lifetime is 60 s, and that the variable cannot lengthen it, is a unit test of `signedUrlTtl`. Privacy is checked twice: the columns and the one foreign key of `download_events` (structure), and a scan of every row of the `public` and `storage` schemas for the IP address and the user id a download was sent with (behaviour).
- **Unpublish, Report and Takedown tests** (P0-07.6; `test-store/unpublish.test.ts`, `report.test.ts`, `takedown.test.ts`) publish through the real `publish` function where the ticket asks for it, and otherwise insert rows of a test Publisher with the service role. The rate-limit test relies on the per-install table check, which is exact; the per-IP counter is per worker, so its rules are unit tests (`test/moderation.test.ts`) and each other Report request sends an address of its own. Administrators are test Publishers with `is_admin` set by the service role. A whole-Harness Takedown that starts while a `publish_version()` transaction (held open in a psql session) has inserted a version is checked to take that version down too.
- **Search tests** (`test-store/search.test.ts`) use the seeded Chinese Harness and rows each test inserts with random English and Chinese words of their own (so a query finds only what that test put there), and check ranking order (name above summary above README, then downloads, then date), filters alone and combined, that Unpublished-only and taken-down Harnesses never appear for any query, and the clamping of `limit` and `offset` against more than 60 matches. `test-store/home.test.ts` runs the home rows and the Publisher page exactly as api.md writes them and checks their exact rows and order.
- **Prior art**: none in the repo yet; this spec establishes the pattern. Store tests live in `apps/store/test-store` and run with `pnpm test:store` against a running local stack (keys from `supabase status`); they are not part of the root `pnpm test`, which needs no Docker. A separate `store` job in the CI workflow starts the stack, applies the migrations from empty, seeds, serves the functions and runs them.

**Known limitation (Linux AppImage)**: electron-builder writes `MimeType=x-scheme-handler/harnessstore` only into the `.desktop` file embedded in the AppImage, which an AppImage does not install, and on Linux `app.setAsDefaultProtocolClient` needs an installed `.desktop` file too. A bare AppImage therefore never receives `harnessstore://auth-callback`, and sign-in ends with `sign_in_timeout`, unless the AppImage is integrated (appimaged, AppImageLauncher) or a `.desktop` file declaring the scheme is installed by hand. macOS and Windows builds are not affected. Writing the `.desktop` file at first run (or adding a deb target) is left to the packaging work (P0-13).

- The same `packages/manifest` code runs in Deno (Edge Functions) and Node (desktop); the package must stay free of Node-only APIs.
